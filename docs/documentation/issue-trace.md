# issue-trace

Issueを調査・計画・実装・人間の確認の順で進め、問題、重要な判断と理由、結果、残課題を他の人も追えるようにしたいときに使います。実施済みの記録だけを依頼することもできます。

## 渡す情報

対象リポジトリとIssue番号、進行か記録だけか、許可する操作を渡します。

## 依頼例

```text
issue-traceでIssue #123を調査から進めてください。計画を確認してから実装し、検証結果までIssueに残してください。
```

## 進め方

1. Issueの問題・完了条件・合意と実態を確認し、判断に影響する調査結果を記録します。
2. 人間が承認した計画と承認の根拠を一つのコメントへ記録します。
3. 実装・検証を記録し、人間の確認を受けます。修正結果は承認後にまとめます。
4. 最新の到達点と残課題の扱い、終了・中断理由をまとめます。本文更新の許可がなければ、関連記録へのリンクを含むコメントを入口にします。

## 簡潔な記録の作り方

重要な発見、合意、結果、残課題や状態が変わったときに記録します。テンプレートは必要情報の確認に使い、短い記録は見出しごとに分けず、一段落にまとめられます。既出の要件や検証はリンクし、今回の変更と判断に必要な根拠を加えます。

例えば次は、書き方を示す架空の例です。実際の記録では保存した確認結果へリンクします。

> **実行記録：評価画面の表示確認** — 評価画面の初期表示をChromeで確認した（根拠：保存した画面画像）。入力・保存操作と実モデルによる評価は未検証。残事項はこれらの検証と人間による成果物確認。

PRには差分やCIの詳細を置き、Issueには結果の要約と参照先を残します。投稿後の再取得や通常の起動・再試行は内部で確認し、再現や引き継ぎへ影響するときだけ経緯を記録します。重要な理由や未確認事項を削って短くすることは避けます。

### 実出力の抜粋

以下は保存した原本の冒頭です。全文は原本から取得できます。

````markdown
## 計画記録：実際のスキル実行成果物を閲覧・取得できる例へ変更する

### 要点
[直前の実装記録](https://github.com/yukihito-jokyu/context/issues/57#issuecomment-6100169462)の成果物例は説明用の創作であり、利用者が実行結果を確認する用途には不十分だった。ユーザーの変更指示に従い、スキルの正本を実際に使用して得た成果物と入力・検証記録を保存し、画像と原本ダウンロードで展示する。

### 対応する要件と完了条件
文章は実際の出力と原本、HTMLなど画面のある成果物は実ブラウザのスクリーンショットと元ファイル、複数ファイルはZIPで提供する。実行した入力、利用したSKILL.md、到達点、検証結果を確認できること。作成物の一覧・ダウンロード・画像参照が/context/配下で動き、ビルドと検証が成功すること。

### 進め方と判断理由
公開可能な題材として、このサイトの成果物閲覧と既存検索処理などを使う。正本や本作業を壊さないよう、サンプル実行は専用の作業領域へ分離する。実行時の入力と出力をそのまま保存し、表示のために出力を作り直さない。ファイル形式に合う画像・原本・ZIPをMarkdownから利用できる共通機構を作る。承認を要するスキルは実際に到達した段階を記載し、存在しない承認・投稿・検証を補作しない。

### 作業順序と検証方法
1. 各スキルの実行条件と保存物を確認する。
2. 正本に従って文章・図・画面・レビュー等の実際のサンプルを生成する。
3. 検証と画面撮影を行い、入力・出力・確認記録を保持する。
4. 公開機構と各ページを更新し、原本取得、画像、ベースパス、リンク、型、ビルドを検証する。
````

## 確認するポイント

問題・完了条件、重要な判断と理由、結果と残課題が分かり、根拠へ辿れるかを確認します。要件と実態、検証成功と人間の確認を区別し、同じ説明や判断に関係しない作業履歴を繰り返していないかを見ます。最新の到達点、残課題の扱い、終了理由も確認します。投稿結果の確認は内部で行い、クローズやラベル変更は別の操作です。

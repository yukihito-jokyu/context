受付後は、同じ job_17 の保存状態が変わります。サーバーが①を作り、ワーカーが②から成功③または失敗④へ進めます。

①から矢印を追ってください。②の成功は③へ、失敗は右側の枝で④へ進みます。③から④への遷移はありません。

① queued — サーバーが受付を保存
サーバーは初回の POST /jobs で job_17 を作成します。同じ requestKey の再送では、同じ jobId を返します。

② running — ワーカーが処理を開始
ワーカーが queued を running へ移します。クライアントの GET は保存状態を読み出すだけで、遷移を起こしません。

③ completed — 成功した結果を保存
ワーカーが変換に成功すると、completed と resultUrl を保存します。クライアントは GET で確認し、結果を表示します。

④ failed — 失敗した理由を保存
ワーカーが変換に失敗すると、failed と reason を保存します。クライアントは GET で確認し、理由を表示します。

③と④はこの架空例の終端です。終端から再開する処理はありません。POST の再送と、ワーカーによる状態変更は別の動作です。

HTTP の一般仕様では、202 は処理の完了を表さず、GET は現在の表現を取得します。四つの状態名や保存フィールドは、この教材だけの架空仕様です。RFC 9110 §15.3.3・§9.3.1（確認日：2026-10-14）

# 受付と変換を分ける全体図

問いは「誰が画像変換を受け付け、誰が処理し、利用者はどこから結果を知るか」。主体と受渡しを示すarchitecture型を選んだ。通信の時間順や成功・失敗の分岐は局所図へ委ね、この図は処理を直列実行する工程図としては読まない。

①利用者はクライアント、②APIは受付と状態照会、③保存はジョブの保存先、④変換はワーカー。結果は別の実体を捏造せず③に保存される値として扱う。製品や物理テーブルを想定しない。

図内には番号、主体の短名、依頼／応答／作成・参照／取得／保存だけを残す。POST /jobs、GET /jobs/job_17、202、requestKey、状態名、resultUrlとreasonは同じ番号のasideへ移す。①②は依頼と応答、③④は取得と保存の両方向を保つ。

最初の標準図はviewBox幅350で文字が小さかった。ノード幅100・高さ36、短名、凡例の意味を保った短い名称へ変更し、標準SVG幅153へ縮めた。390px表示でノード約24.6px・矢印ラベル約17.9pxとなり、本文19px基準に近づけた。標準SVGを改変せず、余白や凡例を残している。

PCは図と番号解説の横配置、狭幅は図→解説の縦配置。図＋凡例＋読み方は1440×900・390×900の高さに収まる。狭幅の全番号説明は縦スクロールで読む。

この架空APIでは、APIが依頼を受け付け、ワーカーが後から画像を変換します。利用者が202を受け取った時点と、画像が完成した時点を分けて読みます。

①利用者と②APIの間は依頼と応答の往復です。③保存と④変換の間はジョブの取得と結果の保存です。矢印は受け渡し方向であり、上から下へ一度だけ実行する工程を示していません。

①クライアントは画像IDとrequestKeyをPOST /jobsへ送ります。②APIは初回に③へjob_17を作り、①へ202とjobIdを返します。同じ依頼の再送では同じrequestKeyを使い、②は重複ジョブを作らず同じjobIdを返します。

④ワーカーは③のqueuedジョブを取得し、runningに変更して画像を変換します。④は成功ならcompletedとresultUrl、失敗ならfailedとreasonを③へ保存します。①は②へGET /jobs/job_17を送り、②が③から参照した状態を受け取ります。completedなら結果、failedなら理由を表示します。

②の202は受付の応答です。POSTが503の場合の最大2回の再試行、再試行後も503の場合の受付結果不明、および成功・失敗の分岐は、それぞれの詳説で扱います。③の保存技術、④の起動方法、resultUrlでの画像取得方式は架空仕様では未指定です。

202の一般的な意味はRFC 9110 §15.3.3で確認しました。job_17、requestKey、各状態、エンドポイントは提供された架空仕様です。

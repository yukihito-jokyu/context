同じ画像変換を再送するときは、初回と同じ requestKey を使います。ここでは画像 img_42 をキー req_A で依頼し、返される job_17 を追います。

①初回と②再送から出る線が、同じ job_17 に合流する点を読みます。主図の線は依頼とジョブの対応を示します。HTTP応答の向きや処理時間は表しません。③はそのjobIdを使う状態照会の局所投影です。

① 初回はジョブを作る

POST /jobs へ img_42 と req_A を送ると、サーバーは job_17 を作り、202とjobIdを返します。202は受付であり、変換の完了ではありません。

② 再送も同じジョブへ

同じ依頼を同じ req_A で送ると、サーバーは重複ジョブを作らず、同じ job_17 を返します。キーを新しく作り直さないことが対応を保つ条件です。

③ jobIdで状態を読む

クライアントは GET /jobs/job_17 で同じジョブの状態を取得します。202だけで成功を表示せず、取得した状態に応じた表示へ進みます。

完了・失敗の状態と表示内容は状態の図で説明します。

この図は、同じ依頼に同じrequestKeyを使う場合を扱います。同じキーで異なる画像を送った場合やキーの保存期限は未指定です。再送時のHTTPステータスも指定されていないため、ここでは同じjobIdだけを示します。503の再試行上限は別図の範囲です。

①②の具体的な入力と返り値

初回と再送で同じ本文を送ります。

POST /jobs
{"imageId":"img_42","requestKey":"req_A"}

①初回の応答は202、本文は {"jobId":"job_17"}。②再送の返すjobIdも job_17 です。②のHTTPステータスは原文で指定されていません。

出典：この架空APIの動作は依頼文、202の一般的意味は RFC 9110 §15.3.3、GETの一般的意味は 同 §9.3.1 に基づきます。同じキーを同じジョブに結び付ける規則は、この架空API固有の仕様です。

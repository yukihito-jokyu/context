# request 図の設計

問いは、同じ requestKey で再送したときジョブが増えるかどうかである。依頼文を架空APIの全仕様とし、HTTP 202の一般的意味だけをRFC 9110で確認した。

主図はarchitecture型による対応関係図とする。上部の2つの箱は2人のクライアントではなく、同じクライアントが行う①初回POSTと②同じ依頼の再送である。両方のreq_Aから同じjob_17へ結び付く関係を示す。矢印はこの対応を示し、HTTP応答の向きを示すものではない。①は作成、②は再利用という差を枝のラベルで残した。初回と再送は順に起きる具体例であり、同時実行や互いに排他的なalt分岐として描かない。

③GETの入口は同じ担当のarchitecture型局所投影getへ分ける。クライアントからサーバーへのGET /jobs/job_17を示し、状態を返すことと完了判定は対応する解説に置く。③は主図とは別ジョブを作る経路ではない。

図内には主体、req_A、job_17、①②③、作成/再利用、GETパスを残す。img_42、imageId/requestKeyという入力フィールド名、返すJSON、202の意味、再送応答ステータスの未指定は横へ移す。長いJSONは解説雛形の後続詳細に置き、横解説は短い段落にする。

①→初回img_42+req_A、job_17作成、202+jobId。②→同じimageId/requestKey、重複ジョブなし、同じjobId。③→GETで同じjob_17の状態を確認。data-flow-stage=1/2/3をそのまま記事側の強調に使える。

初稿sequenceは全9検査合格だったが、520pxのviewBox内のメッセージ9px/注記7pxが記事350pxで約6px/4.7pxとなるため採用しない。dataflow案も標準文字が小さく、stageの最低幅423pxが必要だったため採用しない。最終案は340px幅のarchitecture対応図と同じ幅のGET局所投影を使い、主要値を標準11pxの見出しで置く。独自SVG・切抜き・vendor変更は行わない。

ワーカーのqueued/running/completed/failed全遷移、503の再試行回数と受付結果不明の表示は別図の担当範囲。主図のcaptionと条件文にはその境界を短く残す。

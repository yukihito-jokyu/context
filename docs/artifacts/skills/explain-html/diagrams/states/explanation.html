受付後に追うのは、同じ job_17 の状態です。ワーカーが処理結果を保存し、クライアントはGETで読んだ状態に応じて表示を決めます。

①→②から、成功なら③、失敗なら④の矢印を追います。上下の位置は連続した遷移を意味せず、③と④はどちらかに至る代替の終端です。

① queued — サーバーが作った job_17 は処理待ちです。完了した結果はまだ表示しません。

② running — ワーカーが①から移して画像変換を実行します。クライアントは GET /jobs/job_17 で状態を読み、②も未完了として扱います。

③ 成功 completed — 成功したワーカーは completed と resultUrl を保存します。GETで③を読んだクライアントは結果を表示します。

④ 失敗 failed — 失敗したワーカーは failed と reason を保存します。GETで④を読んだクライアントは理由を表示します。

①queuedと②runningは未完了です。③completedでだけ結果、④failedでだけ理由を表示します。GETは状態を取得する操作であり、ワーカーの状態遷移を起こす矢印にはしていません。

この4状態、resultUrl、reason、GETのパスと表示条件は依頼文が定める架空仕様です。取得の一般的な意味は RFC 9110 §9.3.1、受付と処理完了の区別は §15.3.3 で確認できます。RFCはこの架空APIの状態名やJSON形式を定めていません。

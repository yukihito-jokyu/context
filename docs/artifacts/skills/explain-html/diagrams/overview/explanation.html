これは学習用の架空APIです。画像の変換依頼を受け付けるサーバーと、変換を進めるワーカーを分け、保存したジョブを通して状態を共有します。

①から②への線はHTTPの窓口、②と④から③への線はジョブ保存先の利用を表します。矢印はアクセス先であり、通信の厳密な時間順は別の通信例で確認します。

① クライアント — POST /jobsへimg_42とreq_Aを送ります。受け取ったjob_17を使い、GET /jobs/job_17で状態を読みます。

② サーバー — 初回はジョブを作り、202とjobId: job_17を返します。この受付応答は、画像変換の完了を意味しません。

③ ジョブ保存先 — サーバーが作ったjob_17を保持します。ワーカーが保存する状態を、サーバーが読み取ってクライアントへ返します。

④ ワーカー — 保存されたジョブを取得し、画像変換を進めて状態を更新します。クライアントは次の照会で、保存済みの状態を取得します。

この図は4主体の責務と接続点を示します。同じrequestKeyで同じjobIdを返すこと、保存状態の成功・失敗、503時の再試行上限は、この架空APIが定める個別の規則であり、それぞれの詳細で扱います。

202が処理の受付を示し、完了を保証しない一般的な意味は、RFC 9110 §15.3.3を参照しています。GETによる取得の一般的な意味は、同 §9.3.1を参照しています。

# overview の設計

問いは「全体で誰が何を受け持つか」。architecture を選び、①クライアント、②サーバー、③ジョブ保存先、④ワーカーを独立した4主体として配置する。受付側と処理側の責務を分け、共通の保存先に接続する構成を読み取れるようにする。

図内には番号、主体名、短い役割、POST / GET、作成・状態読取、取得・状態保存を残す。長いAPIパス、img_42、req_A、job_17と202の意味は同じ番号の横解説に置く。ノードを増やしてJSONや文章を一本道に変えない。接続はアクセス先を表し、時間順や後続の全状態分岐を表さない。その読み方は必要captionに常時表示する。

①はPOSTとGETの具体物、②は202+jobIdと未完了、③は同一ジョブの保存と照会、④は非同期の変換と保存へ対応する。各番号の横説明は1〜2文。状態分岐と503時の回数は他の専任図へ委ねる。ワーカーの起動方式や保存製品は依頼から決まらないため描かない。

幅350pxの図と横説明をPCに、幅390pxの画面では図→説明の順を使用する。SVGは無改変のArchify 2.16.0の標準serializeSvgを限定DOMアダプターで出力する。図内文字の大きさは標準レンダラーに依存し、実表示の実寸をreview.jsonへ記録する。

初回の自動ラベルで2件のノード重なり診断が出たため、その2接続にlabelDyだけを追加した。再検証で9項目、構成エラー0・警告0を確認した。独自SVGもvendor変更も行わない。

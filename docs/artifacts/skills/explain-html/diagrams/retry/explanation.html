クライアントはPOSTの503を受けたとき、同じ依頼として受付を確認し直します。この架空APIでは初回の後に最大2回だけ追加送信するため、送信は合計3回までです。

①から読み始めます。中央の①〜③は各POSTを送信した後の応答待ちです。右の戻り矢印は1・2回目の503で再送し、左の枝は3回目の503で⑤へ止まることを示します。どの回の202も上の④へ進む代替出口です。

① 初回。POST /jobsへ画像img_42とrequestKey=req_Aを送ります。

② 追加1回目。①が503なら、同じreq_Aで2回目を送ります。

③ 追加2回目。②も503なら、同じreq_Aで3回目を送ります。追加送信はここまでです。

④ 受付確認。①〜③のどこでも202なら再送をやめ、GET /jobs/job_17へ進みます。202は変換完了を表しません。

⑤ 受付不明。3回とも503なら「受付結果不明」と表示します。これは変換失敗のfailedとは別です。

例えば応答が503、503、202なら、同じreq_Aを3回送り、3回目に返されたjob_17の状態を取得します。503、503、503なら4回目を送らず、受付結果不明と表示します。同じrequestKeyでは同じjobIdを返すという架空仕様により、再送で重複ジョブを作りません。

この図はクライアントが受付を確認する範囲です。⑤はジョブの存在や変換失敗を断定する表示ではなく、ワーカーが保存するfailedと区別します。待ち時間、バックオフ、期限、通信断、503以外のエラーは原文に定義がありません。

回数とキーの規則は提供された架空仕様です。HTTPの202は処理の受付と未完了を表し、503は一時的に要求を扱えない応答です。RFCが定めるRetry-Afterは任意であり、この図に待ち時間は補いません（RFC 9110 §15.3.3、§15.6.4）。

# retry：受付を確認する1つの依頼

問いは「POSTの503が続くとき何回送り、どこで止まるか」。対象をjob_17の変換状態ではなく、クライアントが1つの依頼の受付を確認する範囲に限定する。したがって⑤の受付不明をジョブのfailedとして扱わない。

最終型はlifecycle schema v2。同じ依頼について、送信後の応答待ち、受付確認、受付不明というクライアント側の状態を追う。応答待ちには現在の送信回数n=1,2,3があり、503かつn=1または2なら同じキーで次のPOSTを送り、nを1増やして応答待ちに戻る。503かつn=3なら⑤で止まる。①〜③のどの応答も202なら④へ進む。条件付き自己遷移を、無条件の反復や無限再試行とは扱わない。

初稿のworkflow v2は、実ノードより大きい固定列の余白があり、350px掲載で主要ラベルが4.9pxになった。全送信を別状態にしたlifecycleの縦展開も長かった。このため、同じ意味の応答待ちを1状態へまとめ、再試行回数を枝の条件として保持した。意味モデルの型と条件を選び直したもので、標準SVG、vendor、serializerは変更しない。

図内に残すのは①〜③の応答待ち、④受付確認、⑤受付不明、202、503の1・2回目の再送、503の3回目の停止である。図は状態の可能な変化を表し、503→202→503の実行記録ではない。④と⑤の間に矢印を置かず、代替出口を保持する。

横へ移すのはPOST /jobs、imageId=img_42、requestKey=req_A、GET /jobs/job_17、同じキーの重複防止、202が未完了である理由、受付結果不明とfailedの区別。①は初回、②は追加1回目、③は追加2回目、④は202を受けた出口、⑤は503が3回続いた出口に対応する。図内の①〜③という範囲表記は、横の①②③をまとめた同じ応答待ちを指す。

図の直下には「①から開始。503の1・2回目は再送、3回目は⑤で停止。202は④へ。」を常時表示する。主要ラベルは350px表示で11.67px、枝は6.67pxとなるため、枝条件の理解を小さい文字やホバーだけに依存させず、19pxのcaptionと番号解説で対応を保つ。PCは図350pxと解説の横配置、390pxでは図・caption・番号解説の縦配置とする。

待ち時間、バックオフ、期限、通信断、503以外のエラーは架空仕様にないため追加しない。HTTP一般の202/503の意味だけをRFC 9110で補助確認した。主図だけで上限と両出口を保持できるため局所投影は作らない。

標準viewerのデスクトップ縦overflowは表示ゲートの未達としてreview.jsonに残す。記事の標準SVG＋caption＋短い解説は実ブラウザで別に確認した。viewerのCSSやソース、モデル、SVGを書き換えて検査を通さない。

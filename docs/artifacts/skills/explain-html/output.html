全体像

これは画像変換を受け付けて後から結果を確かめる、提供された架空APIの説明です。サーバーの202は受付であり、クライアントが結果を表示できる完了状態とは別です。

① クライアント — POST /jobsへimg_42とreq_Aを送ります。受け取ったjob_17を使い、GET /jobs/job_17で状態を読みます。

② サーバー — 初回はジョブを作り、202とjobId: job_17を返します。この受付応答は、画像変換の完了を意味しません。

③ ジョブ保存先 — サーバーが作ったjob_17を保持します。ワーカーが保存する状態を、サーバーが読み取ってクライアントへ返します。

④ ワーカー — 保存されたジョブを取得し、画像変換を進めて状態を更新します。クライアントは次の照会で、保存済みの状態を取得します。

受付と処理の完了を分ける理由

サーバーは画像変換の終了を待たずに202とjobIdを返します。クライアントは返されたjobIdで保存済みの状態を読み、変換の結果を判断します。202だけを受け取って結果表示へ進むと、クライアントは未完了のジョブを完了と誤認します。

実際の値を使う通信例へ。API固有の規則は提供された架空仕様です。HTTPの202も処理の受付と未完了を表します（RFC 9110 §15.3.3）。

この例が決めていない運用条件

架空仕様は認証、画像アップロード、保存先の実装、キューの方式、排他制御、削除、保持期間を定めていません。図の保存先は状態を保持する役割であり、特定のデータベース製品を要求しません。

通信を追う

同じ依頼を再送するとき、クライアントは同じrequestKeyを使います。サーバーは同じjobIdを返すため、再送によって重複ジョブを作りません。

番号付き解説を順に確認できます。再生の時間は処理時間を示しません。

① 初回はジョブを作る

POST /jobs へ img_42 と req_A を送ると、サーバーは job_17 を作り、202とjobIdを返します。202は受付であり、変換の完了ではありません。

② 再送も同じジョブへ

同じ依頼を同じ req_A で送ると、サーバーは重複ジョブを作らず、同じ job_17 を返します。キーを新しく作り直さないことが対応を保つ条件です。

③ jobIdで状態を読む

クライアントは GET /jobs/job_17 で同じジョブの状態を取得します。202だけで成功を表示せず、取得した状態に応じた表示へ進みます。

完了・失敗の状態と表示内容は状態の図で説明します。

状態と結果

状態はjob_17という同じジョブの進行を表します。ワーカーが状態と結果を保存し、クライアントはGETの値を読んで結果または失敗理由を表示します。

① queued — サーバーが作った job_17 は処理待ちです。完了した結果はまだ表示しません。

② running — ワーカーが①から移して画像変換を実行します。クライアントは GET /jobs/job_17 で状態を読み、②も未完了として扱います。

③ 成功 completed — 成功したワーカーは completed と resultUrl を保存します。GETで③を読んだクライアントは結果を表示します。

④ 失敗 failed — 失敗したワーカーは failed と reason を保存します。GETで④を読んだクライアントは理由を表示します。

再送と停止

クライアントがPOSTの503を受けたときだけ、提供仕様の再試行規則を使います。初回＋最大2回の追加送信でも503なら、クライアントは受付結果不明と表示します。

① 初回。POST /jobsへ画像img_42とrequestKey=req_Aを送ります。

② 追加1回目。①が503なら、同じreq_Aで2回目を送ります。

③ 追加2回目。②も503なら、同じreq_Aで3回目を送ります。追加送信はここまでです。

④ 受付確認。①〜③のどこでも202なら再送をやめ、GET /jobs/job_17へ進みます。202は変換完了を表しません。

⑤ 受付不明。3回とも503なら「受付結果不明」と表示します。これは変換失敗のfailedとは別です。

追加2回は、合計3送信まで

図の①〜③を同じキーで試し、応答がすべて503になる例です。クライアントは追加送信を2回に抑え、4回目を送信しません。

503が継続する説明用トレース
1回目 POST /jobs  requestKey=req_A → 503
2回目 POST /jobs  requestKey=req_A → 503
3回目 POST /jobs  requestKey=req_A → 503

クライアント表示: 受付結果不明

「受付結果不明」はジョブのfailed状態とは異なります。failedはワーカーが保存した変換の失敗であり、受付結果不明はクライアントが受付を確定できない表示です。クライアントは不明を画像変換失敗へ置き換えません。

HTTP一般の意味と、この架空APIだけの再試行規則

HTTPの503はサーバーが一時的に要求を扱えない応答です。サーバーはRetry-Afterで待ち時間を示せますが、この架空APIは待ち時間やバックオフを定めていません。同じrequestKeyを使う規則と追加2回の上限は提供仕様だけの規則です（RFC 9110 §15.6.4、架空仕様）。

503以外のPOST応答、通信断、タイムアウト、GETの失敗時は未定義です。この説明は未定義の条件へ再試行規則を拡張しません。

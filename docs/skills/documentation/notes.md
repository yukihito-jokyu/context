# notes

実装中に計画から外れた判断やエッジケースが見つかったときに使います。差分だけでは分からない「なぜ」を作業中に記録します。

## 渡す情報

計画、見つかった問題、選択した対応、代替案、後で確認すべきことを渡します。

## 依頼例

```text
notesを使って、担当者未割り当ての値をAPI条件へ変換する判断を記録してください。当初案との違い、採用理由、確認が必要な点を残してください。
```

## 進め方

1. 計画から変更した点と理由を記録します。
2. エッジケース、選択した対応、不採用案を分けます。
3. 後で確認する事項を残し、作業中に更新します。

## 成果物の例

修正中に実際に確認した制約と判断を記録しました。

**到達点：実装中の判断記録。**

**移行時の確認：既存の実行記録を移行しました。本文の一致は確認しましたが、過去の実行時の同梱資料全体は特定できていません。**

このハッシュは移行時の変更検出用の基準です。同梱資料全体をこの版で再実行した証拠ではありません。

### 実行した依頼

```text
実成果物展示の修正中に生じた判断、Registryの取得失敗、代替経路、原本配信と文書探索の区別を、作業と並行して記録してください。
```

### 実出力の抜粋

以下は保存した原本の冒頭です。全文は原本から取得できます。

````markdown
# Implementation Notes

成果物例への修正中に、確認した判断と制約を記録する。

## 1. 計画から変更した点

- React用Registryのdetail-page.jsonが404だったため、提供元のローカル正本を一時領域へコピーし、配布JSONを生成して導入する経路へ変更した。
- test.mdはユーザーの修正対象と無関係だったため削除した。

## 2. 変更理由

- RegistryのHTTP応答は404と確認した。同じ提供元のローカル正本にはdetail-pageのソースとRegistry定義が存在した。
- ユーザーは「docsのすべてのスキルの説明に対する成果物の例」を修正対象としている。別ファイルへの記録では実例が見られない。

## 3. 遭遇したエッジケース

````

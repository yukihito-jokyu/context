# issue-trace

Issueを調査・計画・実装・人間の確認の順で進め、明示的な記録依頼がある場合に、問題、重要な判断と理由、結果、残課題をIssueへ残します。実施済みの記録だけを依頼することもできます。

## 渡す情報

対象リポジトリとIssue番号、進行か記録だけか、許可する操作を渡します。

スキルの起動、Issue番号の指定、「Issueを進めて」だけでは投稿しません。方針への「OK」や実装・修正結果への承認も、投稿の許可とは区別します。「この計画をIssueに記録して」「調査結果と実装結果をIssueに残して」のように、記録する対象と範囲を明示してください。既に依頼した範囲で再確認は求めず、一度の記録依頼を以後の議論全体への投稿許可にも広げません。

## 依頼例

```text
issue-traceでIssue #123を調査から進めてください。計画を確認してから実装し、検証結果までIssueに残してください。
```

## 進め方

1. Issueの問題・完了条件・合意と実態を確認し、判断に影響する調査結果を会話で提示します。
2. 計画を会話で検討し、人間の承認を得てから実装します。
3. 成果物と検証結果を提示し、人間の確認を受けます。
4. 最新の到達点と残課題の扱い、終了・中断理由をまとめます。

各段階のIssueへの投稿は、明示的に依頼された対象・範囲・タイミングに限ります。承認済みの計画・修正結果を投稿するときは、承認の根拠も含めます。議論中の案は会話内に留め、途中案の記録を依頼された場合だけ、案・未合意と明記して投稿します。記録依頼がなくても、許可された調査や実装は進められます。

## 簡潔な記録の作り方

明示的な記録依頼の範囲で、重要な発見、合意、結果、残課題や状態の変化をまとめます。テンプレートは必要情報の確認に使い、短い記録は見出しごとに分けず、一段落にまとめられます。既出の要件や検証はリンクし、今回の変更と判断に必要な根拠を加えます。

例えば次は、書き方を示す架空の例です。実際の記録では保存した確認結果へリンクします。

> **実行記録：評価画面の表示確認** — 評価画面の初期表示をChromeで確認した（根拠：保存した画面画像）。入力・保存操作と実モデルによる評価は未検証。残事項はこれらの検証と人間による成果物確認。

PRには差分やCIの詳細を置き、Issueには結果の要約と参照先を残します。投稿後の再取得や通常の起動・再試行は内部で確認し、再現や引き継ぎへ影響するときだけ経緯を記録します。重要な理由や未確認事項を削って短くすることは避けます。

## 成果物の例

現行のissue-traceを使い、実際のIssue #79と計画コメントを読み取り、対応範囲と未確認事項を整理しました。

**到達点：調査済み・GitHub投稿と実装確認は未実施。**

### 実行した依頼

```text
# 入力

issue-traceを使い、yukihito-jokyu/contextのIssue #79の要件と承認済み計画を調査して、対応範囲と確認点を整理してください。

調査のみです。Issueの本文・コメントと関連PRを読み、適用されるAGENTS.md、記録フォーマットを確認してください。GitHubへの投稿・本文更新・クローズ・実装・テスト実行は行わないでください。検証済みかどうかは今回実際に確認した範囲で区別してください。
```

### 実出力の抜粋

以下は保存した原本の冒頭です。全文は原本から取得できます。

````markdown
Issue #79の対応範囲は、Skillとpluginのガイド・成果物を分け、Skill更新後の成果物をサブエージェントで作り直す運用を整えることです。今回は承認済み計画の調査まで進めました。

[Issue本文](https://github.com/yukihito-jokyu/context/issues/79)は空ですが、[計画コメント](https://github.com/yukihito-jokyu/context/issues/79#issuecomment-6194863317)に要件と完了条件があります。

> スキルとpluginの利用ガイド・導入案内・成果物を分ける。

計画が定める対応は次の5点です。

1. ガイドを `docs/skills/`・`docs/plugins/`、成果物を `docs/artifacts/skills/`・`docs/artifacts/plugins/` に分ける。
2. 既存の6分類・26スキルを移し、リンク・検索・ダウンロード・検証処理を合わせる。
3. Skill単体とpluginの導入案内を整え、skill-refiner・explain-htmlの用途、対応Agent、生成・導入、hooks、公開状況を説明する。
4. 本文と同梱資料の変更、古い成果物、記録外ファイルを検出し、更新時は該当成果物を全削除して再実行する。
5. 型検査・検索テスト・成果物検査・本番ビルド・サイトテストで確認する。

同じコメントの承認根拠には、会話内のユーザー発言「計画をissueに登録して対応してください」が記録されています。計画を再承認する段階ではありません。この調査依頼自体には投稿許可がないため、追加コメントは投稿していません。

````

## 確認するポイント

問題・完了条件、重要な判断と理由、結果と残課題が分かり、根拠へ辿れるかを確認します。要件と実態、検証成功と人間の確認を区別し、同じ説明や判断に関係しない作業履歴を繰り返していないかを見ます。最新の到達点、残課題の扱い、終了理由も確認します。投稿結果の確認は内部で行い、クローズやラベル変更は別の操作です。

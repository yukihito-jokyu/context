# 調査：スキルが前提にする事実を出典付きで確かめる（フェーズ2）

作るスキルのルールと固有のスクリプトは、道具のコマンドの引数、出力の形式、製品の仕様といった事実を前提にする。記憶にある事実は古いことがあり、古い事実で作ったスキルは、どの AI が使っても同じように間違える。この章では、事実をどこから取り、どう記録するかを決める。

この章は次の順に読む。1章で情報源の優先順位を、2章で確かめることを、3章で記録の書式と確認の状態を確かめる。4章が完了の条件である。

## 1. 情報源の優先順位

情報源が食い違ったら、上のものを採る。この順は、ルールの決めた根拠（[variance-axes.md](variance-axes.md) の2章の `basis`）の順と同じである。

| 順 | 情報源 | ルールの `basis` |
|---|---|---|
| 1 | ユーザーの依頼 | `user` |
| 2 | 後付け（`mode: retrofit`）なら、既存のスキル（`dev/original/SKILL.md` と、使っていたスクリプト） | `existing` |
| 3 | プロジェクトの既存の決まり（CLAUDE.md、AGENTS.md、設定ファイル）。書かれていなければ、既存の出力と `git log` に見える書き方を数えた多数派 | `project` |
| 4 | 出力を使う道具や形式の公式の文書（ガイド、リファレンス、仕様）と、その道具をこの環境で実行した結果（`--version`、`--help`、一覧を出すコマンド） | `official` |
| 5 | 公式のひな形・例 | `official` |
| 6 | 広く使われている非公式の情報（記事、コミュニティのガイド）。4と5に記述が無いときだけ使う | `common`（`reason` に「好みで決めた」と書く） |

4の中で、公式の文書と実行した結果が食い違ったら、実行した結果を採る。作るスキルはこの環境で動くからである。食い違ったことは、3章の「分かったこと」に両方を書く。

## 2. 確かめること

| 対象 | 確かめること | 確かめ方の例 |
|---|---|---|
| 出力を使う道具 | 版、コマンドの引数、終了コード | `<道具> --version`、`<道具> --help` |
| 出力の形式 | 公式の仕様（必須の項目、書き方の規則） | 仕様の文書の URL を読む |
| 公式が許す書き方 | 同じことに複数の書き方が許されているか。許されていれば全部を記録する。フェーズ3で1つに絞る | 公式の文書、公式のひな形 |
| 古い書き方 | 公式の今の決まりと、広く知られた古い書き方の違い。古い書き方はルールの `bad` と違反例にする（[variance-axes.md](variance-axes.md) の2章） | 公式の変更履歴、移行の手引き |
| 種類ごとの観点 | [skill-profiles.md](skill-profiles.md) の種類の節の「読み方」と「調べる先」に関わる事実（例：generate なら、lint の無効化コメントとテストの skip の書き方） | 種類の節の「調べる先」、道具の文書、`--help` |
| プロジェクトの書き方 | 決まりが書かれた場所。書かれていなければ、既存の出力の書き方ごとの件数（`basis: project` の根拠） | CLAUDE.md、AGENTS.md、設定ファイル、`git log --format=%s -200 \| grep -c '<書き方の正規表現>'` |
| 製品の機能 | 作るスキルが、skill-foundation の共通ランタイムに無い製品の機能（hooks の別のイベントなど）を使うときだけ、その仕様 | [platforms.md](platforms.md)、製品の公式の文書 |

調べる対象が3つ以上あるときは、対象ごとにサブエージェントへ並べて調べさせ、3章の書式で返させてよい。

## 3. 記録の書式（`dev/research.md`）

対象ごとに次の書式で書く。採った事実には出典を付ける。後でルールの理由を説明するときや、道具の版を上げるときに、どの情報に基づく判断かを辿れるようにするためである。

```markdown
## <調べた対象> <版>

- 確認方法：`<道具> --version` → 1.2.3（YYYY-MM-DD）、[<公式の文書の見出し>](URL)
- 確認の状態：確認済み
- 分かったこと：
  - <事実の要約>（[出典の見出し](URL)）
- 使ったルール：<この事実に基づくルールID。フェーズ3の後に埋める>
```

`basis` が `project` のルールに使う項目には、次のどちらかの行を足す。数えた結果を残すと、なぜその書き方を選んだかを後から確かめられ、別の AI が数えても同じ答えになる。

```markdown
- 決まり：<決まりが書いてあるファイルと場所>。「<決まりの文の引用>」
- 分布：<書き方 A> <件数>、<書き方 B> <件数>（数えたコマンド：`<コマンド>`）
```

確認の状態は、次の3つのどれかを書く。

| 確認の状態 | 意味 | 扱い |
|---|---|---|
| `確認済み` | コマンドの結果か、取得した公式の文書に基づく | そのまま使う |
| `確かめられない` | 確かめる手段が無い（ネットワークが無い、道具が入っていない）。理由を「確認方法」に書く | 使ってよいが、skill-foundation の最終報告の「確かめていないこと」に出る |
| `未確認` | 記憶に基づく | `skill_lint.py --final` が通らない |

後付けのときは、`init_skill.py` が「## 既存のスキル」の節を足す。元のスキルの手順、入力、出力、使っていたスクリプトを書き、元のやり方を残したルール（`basis: existing`）の ID を「使ったルール」に書く。

## 4. 完了の条件

- `確認の状態` が `未確認` の項目が無い
- `basis` が `official` のルールID が、どれかの項目の「使ったルール」にある
- `basis` が `project` のルールID が、「決まり：」か件数のある「分布：」を持つ項目の「使ったルール」にある
- 後付けなら、`basis` が `existing` のルールID が、「## 既存のスキル」の「使ったルール」にある

`skill_lint.py` が、この4つを確かめる。

# 利用中の指摘の収集

この資料は、skill-foundation で作ったスキルが、使われている間に受けた指摘を集める仕組みを説明する。AI は、hooks の案内（additionalContext）に従って操作するときと、記録を確かめるときに読む。スキルの手順（SKILL.md）からは参照しない。

この資料は次の順に読む。1章で何のために何を集めるかを、2章で本来の処理との分け方を、3章で集める時機を、4章で AI の操作を、5章で確認画面と承認を、6章で記録の形を、7章で止め方と限界を、8章で集めた指摘を改善に使う方法を確かめる。

## 1. 何のために、何を集めるか

スキルの Eval は、スキルを作るときにユーザーと価値を確かめて作る。作った後に実際に使った中で「ここが違う」と言われた内容は、会話の中で直して終わると、次の改善の材料として残らない。同じ指摘が別の人や別のセッションで繰り返され、後から「どの版に、何を言われ、どう直し、ユーザーが納得したか」を確かめることもできない。

そこで、スキルの利用中に次の4つを、すべてのスキルで同じ形で保存する。

- 指摘の原文（ユーザーの発言そのもの）
- 修正前の成果物（指摘を受けた版）
- 修正後の成果物（指摘に対応して提示した版）
- ユーザーの承認（確認画面のボタンで行ったものだけ）

承認された事例は、後で Eval と収束テストの候補を作る材料になる。

## 2. 本来の処理と分ける

収集は hooks が提供する追加機能で、スキル本来の処理とは完全に分けてある。

- SKILL.md・ルールの表・チェックリストには、収集の指示も専用のルールも書かない（`skill_lint.py` が検査する）。AI への案内は、hooks の additionalContext からだけ伝える
- `run.py` の start・check・finish は収集を呼ばない
- hooks を無効にすれば、収集も案内も消え、スキル本来の生成・検査・完了だけが動く
- 収集が失敗しても、本来の検査と完了は止まらない。`hook.py` が `feedback.py` の例外をすべて捨てる

分ける理由は、収集が本来の作業の邪魔をしないようにするためである。スキルの手順に収集が混ざると、出力のばらつきの元になり、収集の不具合でスキルが止まる。

## 3. 集める時機

`hook.py` が、hooks のイベントごとに `feedback.py` を呼ぶ。

| イベント | 動き |
|---|---|
| Stop（応答を終える前） | 実行が完了（`done`）したときに、提示した成果物（finish が記録した契約の出力）と、使ったスキルのファイル・契約を内容ごと保存する。これを「版」（delivery）と呼ぶ。対応中の指摘があれば、成果物が変わった版を修正版として指摘に足す |
| UserPromptSubmit（ユーザーの発言） | 同じセッションで成果物を提示した後の発言について、原文と、そのとき提示済みの版を記録する。AI には additionalContext で分類の方法を伝える。発言は止めない |
| PreToolUse（編集の前） | 収集の記録（`.skill-feedback/`）への編集ツールでの直接の編集を拒否する |

発言を記録する範囲は、次のように絞る。

- 実行中（`active`）と質問待ち（`waiting`）の発言は記録しない。作成の途中の依頼の続きであり、完了して提示した成果物への指摘ではないため
- 成果物を提示したセッションの発言だけを記録する
- 対応中の指摘が無いときは、提示の後の3つの発言までを記録する。それより後の発言は、別の話題とみなして記録しない

## 4. AI が行う操作

hooks の案内を受けたら、応答の前に発言を分類する。分類は AI が行ってよいが、要点で原文を置き換えない。

| 場面 | コマンド |
|---|---|
| 成果物への指摘（違う・足りない・直してほしい など） | 編集の前に `python3 <skill>/scripts/feedback.py feedback --event <message-ID> --summary "<要点>"` |
| 指摘ではない | `python3 <skill>/scripts/feedback.py ignore --event <message-ID> --reason "<理由>"`。原文は残る |
| 直すために読む入力ファイル | 変える前に `python3 <skill>/scripts/feedback.py context --file <パス>` |
| 直した後 | 応答の最後に `python3 <skill>/scripts/feedback.py review` を実行し、出た URL をユーザーに渡す |
| 記録の確認 | `feedback.py status`（未分類の発言と、対応中・承認済みの指摘）、`feedback.py validate`（形と参照の整合） |
| 改善に使う（ユーザーに頼まれたときだけ） | `feedback.py export --out <新しいディレクトリ>`（8章） |

指摘を記録すると、指摘を受けた版を修正前として、指摘（case）ができる。同じ版への指摘が続けば、同じ指摘に足す。直した成果物は、次の Stop か `feedback.py review` の実行で、修正版として自動で保存される。スキルを実行し直して直した場合も、完了した版が修正版になる。

承認は人だけが行う。AI は承認ボタンを押さず、承認の URL に送信しない。会話の「OK」、無回答、AI の判断は承認にしない。承認を待つためだけに、成果物の作成を未完了のままにしない。

## 5. 確認画面と承認

`feedback.py review` は、確認画面のサーバー（`feedback_review.py`）をバックグラウンドで起動し、URL を出して戻る。サーバーは `127.0.0.1` だけで待ち受け、操作が30分無いと止まる。止まった後は、同じコマンドで起動し直せる。

確認画面には、指摘ごとに、指摘の原文、版の流れ、修正前といちばん新しい修正版の実ファイルが並ぶ。テキストは差分と本文、HTML はスクリプトを止めたプレビュー、画像は画像、PDF などは実ファイルを開くリンクで見る。ユーザーが「この修正版を承認する」を押すと、その版を指摘への対応として記録する。

承認は、次のどれかに当たると拒否する。拒否したときは、画面を開き直して今の内容を確かめるよう伝える。

- 送信元（Origin と Host）が、この確認画面でない
- トークンが、その指摘の画面を最後に開いたときに発行したものでない。トークンは画面を開くたびに作り直し、一回だけ使える。サーバーを起動し直すと、前の画面からは承認できない
- 承認する版が、画面に出した版でない、またはいちばん新しい修正版でない
- 画面を開いた後に、プロジェクトの実ファイルが表示した版から変わった

画面は何回でも開き直せる。開き直すと、その時点の実ファイルが修正版として先に保存され、新しいトークンが発行される。

## 6. 記録の形

記録は、作業プロジェクトの `.skill-feedback/<スキル名>/feedback.json` に置く。成果物とスキルのファイルの実体は、`objects/<sha256>` に元のバイト列で保存するので、ファイル名や内容が変わっても前の版を失わない。`.skill-feedback/.gitignore` で、記録を Git の管理から外す。記録は足すだけで、新しい実行や再実行で上書きしない。形は `assets/feedback.schema.json`（`schema_version: 1`）で、`feedback.py validate` が検査する。

| 要素 | 保存する内容 |
|---|---|
| `messages` | 発言の原文と、確認画面での承認操作とコメント。時刻、製品、セッション、提示済みの版（`delivered`）、分類（`class`） |
| `deliveries` | 提示した成果物の集合（`files`）、実行（`run`）、元の依頼（`request`）、正規化した入力（`input`）、入力ファイル（`input_files`）、スキルの版（`skill`）、契約の版 |
| `cases[].issue` | 指摘の原文（`quotes`）・要点（`summary`）と、もとにした message ID |
| `cases[].before` | 指摘を受けた成果物の delivery ID |
| `cases[].revisions` | 指摘に対応して提示した版の履歴 |
| `cases[].after` | ユーザーが承認した delivery ID（未承認なら null） |
| `cases[].approval` | 承認の時刻・コメント・承認した delivery ID・送信元（未承認なら null） |

スキルの版は、スキルのファイル（`dev/` と `settings/user-setting.yaml` を除く）の一覧のハッシュである。一覧そのものも `objects/` に保存するので、その時のスキルを取り出せる。

テストで作った記録には `synthetic: true` を付け、承認にも同じ印を写す。実ユーザーの承認と区別するためで、環境変数 `SKILL_FEEDBACK_SYNTHETIC=1` のときに新しく作った記録に付く。

## 7. 止め方と限界

収集は、次のどれかで止まる。

| 止め方 | 結果 |
|---|---|
| spec の `control.feedback` を `false` にする | 契約に入り、`hook.py` が集めず、`install.py` が収集の hooks を登録しない |
| `install.py --no-feedback` | 収集だけを外して、出力の検査の hooks を登録する（登録の文字列に `--no-feedback` が付く） |
| `install.py --no-hooks` | 収集も含めて hooks を何も登録しない。検査は `run.py check` と `finish` だけで行う |

収集だけを使うときは `install.py --features feedback` で、編集の後の hook（PostToolUse）を除いた3つを登録する。

記録はローカルのものとして扱う。利用者の厳密な認証や、シェルからの記録の書き換えは防がない。本文だけのチャットの返答は保存しない。保存したいスキルは、出力の契約に保存先を定める。画像などのバイナリの出力は、契約の出力に `binary: true` を付ける。文字列としては検査せず、`command` の検査だけを使う。

## 8. 集めた指摘を改善に使う

`feedback.py export --out <新しいディレクトリ>` は、承認済みの指摘だけを取り出す。承認待ちの指摘と、承認していない修正版は入れない。取り出したものは次の形で、取り出した後に参照と実ファイルの中身（sha256）を確かめる。

| 置き場 | 中身 |
|---|---|
| `dataset.json` | 指摘ごとに、原文（`issue`）、承認（`approval`）、元の依頼と入力の値、修正前（`before`）と承認した版（`after`）のファイルの一覧、入力ファイル、その時のスキルの版 |
| `cases/<指摘>/before/`、`after/`、`inputs/` | 修正前と承認した版の実ファイルと、入力ファイル（いちばん前に保存したもの） |
| `skills/<版>/`、`skills/<版>.manifest.json` | 指摘を受けたときのスキルのファイルと、その一覧 |

取り出したものから Eval と収束テストの候補を作るのは、skill-foundation の `feedback_eval.py` である。正本のスキルを変えずに作業用コピーで進める手順と、承認を評価の条件への同意として扱わない理由は、skill-foundation の `references/eval.md` の9章にある。

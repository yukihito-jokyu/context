# prototype

言葉だけでは出てこない「無自覚の既知」を、軽量なモックアップやプロトタイプで引き出す。

## Purpose

- 見れば判断できるが、事前には言語化しにくい基準を可視化する。
- 本実装前に、情報量、並び順、導線、見た目、違和感を安く確認する。
- 期待とAIの推測のズレを早い段階で発見する。

## When to Use

- UI、画面、レポート、資料、体験に関する作業をする前。
- 複数案を比較したいとき。
- ユーザーが言葉では説明しにくいが、見れば判断できるとき。
- 実アプリや永続化へ触る前に、安く擦り合わせたいとき。

## Inputs

- 作りたいものの概要。
- 対象ユーザー。
- 必要な情報。
- 分かっている制約。
- ダミーデータの可否。
- 比較したい案の数。
- 反応してほしい観点。

## Process

1. 目的と確認したい未知を明確にする。
2. 本実装に入らず、軽量なプロトタイプ案を作る。
3. 必要に応じてダミーデータを使う。
4. 複数案が有効なら、差分が分かる形で提示する。
5. ユーザーが反応すべき観点を提示する。
6. フィードバックから仕様、制約、判断基準を抽出する。
7. 実装へ進める条件を明示する。

## Outputs

- Prototype。
- 確認してほしい観点。
- フィードバックから抽出した判断基準。
- 次に決めるべきこと。

## Output Format

```markdown
# Prototype

## 1. 目的

- ...

## 2. 前提

- ...

## 3. プロトタイプ案

- 案A: ...
- 案B: ...

## 4. 確認してほしい観点

- 情報量
- 並び順
- 見た目
- 導線
- 違和感
- 不足している項目

## 5. 次に決めるべきこと

- ...
```

## Rules

- 完璧な実装ではなく、判断基準を引き出すことを目的にする。
- バックエンド、永続化、外部連携を前提にしすぎない。
- ユーザーが反応できる具体物として出す。
- 実装に進む前に、何が決まったかを整理する。

## Anti-patterns

- 抽象的な議論だけを続ける。
- モックを本実装の品質まで作り込む。
- ユーザーの反応を仕様へ変換せずに進める。

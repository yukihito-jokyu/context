# 単一題材の図と具体物をつなぐ

| 読者の問い | 図 | 対応する具体物 |
| --- | --- | --- |
| 全体のどこに位置するか | architectureによる構成・包含 | 実際の構成要素、登場主体、担当範囲 |
| 誰と誰が何を受け渡し、いつ返すか | sequence | 要求・応答、書類・データ、具体値、同期と非同期 |
| どの手順・判定を経て結果に至るか | workflow | 主体の動作、判断条件、成功・停止・例外の経路 |
| 同じ対象の状態が何をきっかけに変わるか | lifecycle | 状態、イベント、成立条件、開始・終了・反復 |
| 情報や物質がどこを通り、どう変換されるか | dataflow | 入出力、保存先、変換、単位、観測範囲 |
| 条件で結果がどう変わるか | 分岐を持つworkflow | 判定条件、成功・停止・例外の具体例 |
| 情報の構造はどうなっているか | classまたはER（該当する題材のみ） | 型、データ構造、実際のテーブルと参照 |

構成、分類、因果、時間順を区別する。矢印は確認できた関係だけを示す。自然現象に意図を持つ実行主体を捏造しない。「水蒸気が冷える」のように、変化する対象を主語にして原因と結果を説明する。構成の型の制約で題材の意味を表せない場合は適切な別の型を選び、型のために事実を書き換えない。

## 概要から具体的な理解へ分ける

最初に主要な要素と関係を見渡し、その後、一つの具体例で仕組みを追う。全体図は関心全体を扱い、詳細図は読者が疑問を持つ関係を掘り下げる。通信なら要求と応答、手続きなら条件と停止先、状態なら変化のきっかけ、変換なら入力と出力を残す。各ページの全体図を一律にarchitectureへ固定せず、その関心を表す型を選ぶ。

一枚で主要な仕組みを説明できれば詳細図を重ねる必要はない。逆に、概要の主体名と短い動詞だけでは「なぜ・どの条件で・何が変わるか」に答えられない場合は、その関係を具体図へ分ける。登録と利用、定義と実行、正常と例外など、前提や時点が違うものは必要に応じて分割し、読者が図の間で対象を見失わない名前・識別子・値を引き継ぐ。

ノードには図の意味に合う種類を指定し、色やfrontend/securityなどの型を配置順で割り当てない。矢印の始点・終点・ラベルを読み、受け渡し・遷移・因果・参照など何の関係か分かる状態にする。通信操作、定義、出来事を無説明で同じ処理列に混ぜない。つながりがない要素は、独立した対象として必要な理由を示す。分類・層・包含を伝える場合は意味のある囲み・見出し・具体例で関係を示し、見た目のために実行順の矢印を足さない。

## Archifyへ渡す制作要件

各図の制作前に、次の情報を`diagram-plan.json`の`diagrams`配列へまとめる。これは同じ制作者がモデルを作る場合にも使う設計メモで、別エージェントへの依頼を必須にはしない。

| 項目 | 記録する内容 |
| --- | --- |
| id / page_id / role | 図の識別子、置くページ、overviewまたはdetail |
| question / takeaway | 読者の問いと、図を読んだ後に説明できる答え |
| type / selection_reason | Archifyの型と、その関係を表すために選んだ理由 |
| scope / sources | 描く開始・終了や範囲、根拠となる資料・箇所、説明用の仮定 |
| entities / relations | 主体・対象・具体値と、確認できる方向・関係の意味・条件 |
| parent_diagram_id | 詳細図が掘り下げる全体図。全体図ではnull |
| model_path / target_ids | 保存するモデルの相対パス、対応する本文・具体物のID |

依頼するときは、例えば「このページの問いは〈問い〉。全体図の〈領域〉を〈具体例〉で掘り下げ、〈型〉で〈関係〉を描く。〈条件〉では〈結果・停止先〉へ進む。〈資料〉を根拠にし、〈対象範囲外〉を描かない。本文の〈ID〉と同じ名前・値を使い、読者が〈答え〉を説明できる図を作成する」と渡す。図の枠数や座標を先に固定せず、選んだ型のスキーマ・例からモデルを作成する。

モデル検証後は計画と実際の図を照合する。理由のない型の変更、必要な関係を削った簡素化、主体・値・時点の不一致があれば修正する。計画を書いたこと自体を内容レビューの代わりにしない。

照合ではノード名だけでなく、標準出力の凡例と記号も読む。保存する記録があるだけではdatabase、人物や書類だからexternalと決めない。型の意味を裏付ける境界や役割を確認し、技術分類が題材に合わない場合はスキーマが許す中立表現や別の適切な型を検討する。対応できない制約は明記する。凡例の隠蔽や画像の書き換えで不一致を解消しない。

本文で図の主題として説明する結果・解除・状態変化は、図にも対応する終点・遷移・条件を残す。図の範囲外へ分ける場合はその範囲と移動先を明示する。条件が複数あるときは、すべてを無条件の一本道にまとめない。物質を追う具体例では到達先と相変化、データを追う具体例では採用・除外と最終出力まで照合する。

成功例だけの図へ空の例外レーンを残したり、要素を上部へ寄せたまま大きなviewBoxで縮小したりしない。モデル側の不要なレーン・余白を除き、標準出力で必要な文字と経路が読めるか確認する。読者の問いは見出しに定型の語尾を足して作らず、その図から説明できる具体的な疑問として書く。

## 一つの具体例を最後まで追う

開始条件 → 主体または対象の動作・変化 → 判定 → 結果を同じ例でつなぐ。各段階に短い識別子を付け、本文、図、具体物でも同じ識別子を使う。設定の登録と実行、制度の制定と運用、条件と観測結果を同じ時間軸に混ぜない。

技術題材では、図の③を実装する関数・引数・返り値を示す。一般題材では、図の③で作成する書類・記録・式や、その時点の観測値を示す。具体物の直前に前提と何を見るかを説明し、直後に値や条件が結果へつながる理由を書く。

最小コードは担当ページの初期表示に置く。言語、ファイル、入力、期待結果を添え、実行例・抜粋・擬似コードを区別する。一般題材にはコードを強制しない。書類は記入値とその意味、観測値は単位・測定条件・解釈の限界を添える。

## 詳細への入口

すべてのページに、その関心全体の図、読み方、詳細へのリンクを置く。図のノードから本文・具体物の該当箇所へ移動できるようにする。長い全文や追加条件はdetailsに置けるが、中心的な理由、成立条件、最小の具体例を隠さない。

段階再生は確認できた時間順や受け渡しを理解する場合に使う。構成・分類の図は静止表示でよい。図、説明、具体物の段階を同期し、自動再生や無限ループは使わない。比較列と比較相手は作らず、必要な対応表は項目・条件・説明先を整理するために使う。

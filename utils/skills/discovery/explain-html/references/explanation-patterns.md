# 単一題材の図と具体物をつなぐ

| 読者の問い | 図 | 対応する具体物 |
| --- | --- | --- |
| 全体のどこに位置するか | architectureによる構成・包含 | 実際の構成要素、登場主体、担当範囲 |
| 誰がいつ何をするか | workflowまたはsequence | 呼び出し、手続き、引数、書類、返り値 |
| 何がどう変化するか | lifecycleまたはdataflow | 状態、観測値、記録、変化の条件 |
| 条件で結果がどう変わるか | 分岐を持つworkflow | 判定条件、成功・停止・例外の具体例 |
| 情報の構造はどうなっているか | classまたはER（該当する題材のみ） | 型、データ構造、実際のテーブルと参照 |

構成、分類、因果、時間順を区別する。矢印は確認できた関係だけを示す。自然現象に意図を持つ実行主体を捏造しない。「水蒸気が冷える」のように、変化する対象を主語にして原因と結果を説明する。構成の型の制約で題材の意味を表せない場合は適切な別の型を選び、型のために事実を書き換えない。

## 一つの具体例を最後まで追う

開始条件 → 主体または対象の動作・変化 → 判定 → 結果を同じ例でつなぐ。各段階に短い識別子を付け、本文、図、具体物でも同じ識別子を使う。設定の登録と実行、制度の制定と運用、条件と観測結果を同じ時間軸に混ぜない。

技術題材では、図の③を実装する関数・引数・返り値を示す。一般題材では、図の③で作成する書類・記録・式や、その時点の観測値を示す。具体物の直前に前提と何を見るかを説明し、直後に値や条件が結果へつながる理由を書く。

最小コードは担当ページの初期表示に置く。言語、ファイル、入力、期待結果を添え、実行例・抜粋・擬似コードを区別する。一般題材にはコードを強制しない。書類は記入値とその意味、観測値は単位・測定条件・解釈の限界を添える。

## 詳細への入口

すべてのページに、その関心全体の図、読み方、詳細へのリンクを置く。図のノードから本文・具体物の該当箇所へ移動できるようにする。長い全文や追加条件はdetailsに置けるが、中心的な理由、成立条件、最小の具体例を隠さない。

段階再生は確認できた時間順や受け渡しを理解する場合に使う。構成・分類の図は静止表示でよい。図、説明、具体物の段階を同期し、自動再生や無限ループは使わない。比較列と比較相手は作らず、必要な対応表は項目・条件・説明先を整理するために使う。

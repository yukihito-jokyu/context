# 題材の情報を欠かさないための確認

説明の短さと情報の不足を混同しない。書き手は表示する文章量を抑えつつ、読者が必要な項目を関心別ページと展開する詳細で読めるようにする。単一の例から一般化した説明だけで完成させない。

## 制作前の項目一覧

1. 書き手は、一次資料の文書索引、概要、参照仕様、関連ガイドを確認し、対象と版・確認日を記録する。全体像、各機能、全イベント、設定の適用範囲と条件、入出力と判断、拡張とUI、状態、失敗・中断・制限、導入更新、実行環境、信頼・権限、運用と検証を洗い出す。題材に存在しない分類は「該当なし」の理由を記録する。
2. 書き手は、見出しだけでなく、イベント・API・フィールド・UI要素の表の各項目も一覧へ入れる。既定値・適用条件・制限・例外を落とさない。ページが改版された場合は既存一覧をそのまま流用せず差を確認する。
3. 各項目は安定ID、題材、仕様名、出典URLと節、重要な条件、HTMLの説明先を持つ。対応状態は「説明済み」「名前のみ」「リンクのみ」「未対応」「未確認」「明示的対象外」のいずれかにする。明示的対象外はユーザーが範囲を限定した場合だけ使い、除外理由を記録する。

## HTMLでの説明

各項目の説明には、その項目が何か、誰がいつどう使うか、入力と結果、必要な条件・制約を含める。コードが理解に必要な項目には最小の具体例を示す。API識別子の列挙と外部資料へのリンクだけで説明済みにしない。概要は大きい文字で短く示し、細部は担当ページのdetailsへ置く。全項目を初期表示へ並べたり、文字を小さくしたりしない。

書き手は、題材に存在しない機能や手続きを捏造しない。個別の構成要素は、誰が／何が、どの条件で、どう動くかを説明する。詳細ページでも、題材と関心を見失わないナビを残す。技術用の分類は一般題材へ強制せず、登場主体、背景、条件、手続き、観測結果、例外へ置き換える。該当しない項目は理由を記録する。

## 完成前の照合

- 構造確認は、項目一覧の項目数と状態、HTMLの説明先の存在、リンク先、同じ項目の重複を検査する。
- 意味レビューは、説明文の主体・動作・対象・条件・結果が仕様に一致し、重要な例外が欠けていないかを確認する。
- レビュー担当者は、項目一覧そのものを一次資料の見出しと表へ逆照合する。一覧が欠けている場合、HTMLに一覧の全項目があるだけでは合格にしない。
- 書き手は、名前のみ・リンクのみ・未対応を補完し、説明先へ移動できることを再確認する。
- 読者が確認できる対応表をHTMLまたは同梱JSONとして保存する。対象資料・確認日・仕様版と確認の限界を明記する。

「全て」は、確認した一次資料と明記した版の範囲で使う。将来版、非公開仕様、未確認の型定義まで網羅したとは報告しない。資料へアクセスできない場合は、確認できた部分を先に作り、未確認を残したことを正確に報告する。無理に説明済みへ分類しない。

## チェック項目

全体の構成要素だけでなく、項目一覧の各項目が説明済みであること。説明先の存在と意味の正しさを分けて検証したこと。文書索引・参照表から一覧への欠落を確認したこと。説明を一つの例へ縮めていないこと。読者が詳細を探せること。版・例外・制限を隠していないこと。

## 対応表の形式と検査

対応表JSONはscope、sources、itemsを持つ。sourcesはURLと資料名、itemsはkey、topic、source_url、target_id、statusを持つ。statusの値はexplained、name_only、link_only、missing、unverified、explicitly_out_of_scope。各target_idはHTMLに実在する説明のidへ向ける。深いidを設けた場合はページと閉じたdetailsを開く動作も確認する。

```sh
python3 scripts/check_coverage.py explanation.html coverage.json
```

この検査は、説明先・出典・重複と未完了状態を確認する。未確認や未対応が残る場合は終了値1を返す。終了値0でも意味と元資料の一覧を逆照合したことにはならない。書き手は機械検査の結果と意味レビューを分けて保存する。

資料をユーザーが与えた架空仕様に限定する場合、その原文を一次の入力資料として保存し、架空であることを本文にも明記する。source_urlには読者が開ける原文の相対リンクまたはURLを置く。実在制度や自然現象の説明では架空例を一次資料の代わりにせず、現実の事実と説明用の仮定を区別する。

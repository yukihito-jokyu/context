# 1図を1人の専任エージェントが完成させる

## 記事統合担当と図担当の境界

記事統合担当は、読者・説明範囲・一貫した具体例・ページ構成を決め、必要な図を意味の単位で列挙する。図が答える問い、前後の文脈、共有する用語/部品ID/値、必要な条件、出典の入口、保存先をbriefとして渡す。図のノード・座標・文言を完成させて渡し、担当に色付けだけさせない。

**1つの論理図に1つの新規エージェントを起動する。** 1人に複数図をまとめて割り当てず、別図へ再利用しない。PC/スマートフォンの配置違いや同じ図の修正は、その図の担当が扱う。同じ意味を持つレスポンシブ版は1図であり、別の意味モデルを持つ独立した部分図は別担当を持つ。担当は調査から作図・解説雛形まで一貫して行い、さらに別の作図担当へ委譲しない。

同じ記事・具体例・「例外」という分類を共有するだけでは1図とは扱わない。独立した発火条件・対象・周期を説明する部分図には、それぞれ新規担当を置く。例えばStrictModeの追加検査、Activityの表示切替、Suspenseの初回待機、非同期応答の除外は、共通のChatRoomを例に使っても独立して制作する。

図の数は品質指標ではない。前稿の情報・条件・コードを保持したまま重複図を統合する場合は、その理由と説明先を記録する。各イベントに局所図が必要な依頼では、その対象を省略しない。

記事統合担当は返却された図の本文との整合、図間の用語、全体/局所のつながりを確認し、解説雛形を記事の流れへ組み込む。図の事実・型・ノード・矢印・具体値・座標・付随する読み方を修正する必要があれば、**その図を作った担当へ戻す**。記事統合担当が代わりに図を描き直したり、まとめて汎用図を生成したりしない。IDの衝突回避やHTMLへの埋込など機械的な組立ては統合担当が行える。

サブエージェントを起動できない場合は停止し、図の専任制作を実行できない理由を報告する。単独制作を専任担当による制作と報告しない。

## 図担当の仕事

1. **実際にネットで調べる。** 公式資料・原文などの一次資料を開き、その図の対象固有の入力、処理主体、条件、戻り、終了/失敗、値の変化、適用範囲を細部まで確認する。親の要約や既存図だけで済ませない。提供された固定資料との版差分は混ぜず記録する。閲覧できない情報は未確認とし、推測を仕様と呼ばない。
2. **具体的に表す設計を決める。** 読者の問いに必要な事実と対応する図中表現、図の型を選んだ理由、具体値/条件/境界を置く場所、分割の必要性を短い設計記録にする。思考過程の逐語記録ではなく、調査結果に基づく設計判断を残す。同じ箱の型や文字数へ情報を押し込めない。
   時間順に起きる処理と、条件によって選ばれる代替結果を区別する。代替結果は実際の分岐、またはシーケンス図の `alt` 領域と選択条件で表し、裸の連続矢印にしない。「順次実行ではない」という説明文だけでは図の誤った関係を補えない。狭幅の表示でもこの関係を保つ。
3. **その図を作り切る。** 同梱Archifyの手順・適切な型・標準エクスポートを使用する。可読性や配置を理由に独自SVGへ切り替えない。Archifyを利用できない場合は未完了として停止し、不足を報告する。理由の記録だけで制作方式の例外を認めない。本文へ移した条件・値を図の対応識別子へ結び付け、関係や成立条件の区別を保つ。指定された広幅/狭幅で図全体と読み方を表示確認し、直す場合も同じ担当が直す。
4. **付随する解説の雛形を作る。** 下記の契約で、前提から具体例・条件・結果へつながる文章を図の担当自身が書く。図と関係のない一般論を添えない。解説の各まとまりに図中と同じ対応識別子を表示し、どのノード・枝の説明か明記する。
   表示確認では、SVGの端点だけでなく、図を読むために必要な範囲説明・凡例まで指定画面内で読めるかを測る。出典URLの全文や後続の詳説とは区別し、図の底位置と必要説明を含む底位置を確認記録へ残す。記事への統合後は実際の縮尺でも確認する。
5. 調査・設計・意味モデル・出力図・解説雛形・確認記録を1つの成果物束として返す。出典、表示確認、実行確認と未確認を区別する。

## 図内を短くし、横の解説へ具体を結び付ける

図の中には、関係を追うための短い名称・動作・判定・必要な値を置く。基本は1つの短句、必要なら2行とし、長い入力JSON・フィールド列挙・理由・例外・コードをノード内へ詰め込まない。識別子を途中で改行したり、小さい文字で文字数を維持したりしない。長いコード識別子は横の解説へ置き、図中では短い意味の名前と対応番号を使う。

一つの箱に異なる主体・入力・処理・判定・結果が混ざる場合は、実際の関係に沿ってノードやレーンへ分ける。文章を一文ずつ箱へ置換しただけの長い一本道にしない。非同期のfork、代替結果の分岐、境界、状態の戻りを保ち、説明用に順序や主体を発明しない。

図には①②などの番号または短い識別子を付け、付随解説の各まとまりでも同じ記号を使う。例えば図の「③ 実行を拒否」へ、横の「③ Bashは実行されず、permissionDecision: denyの理由がClaudeへ渡る」を対応付ける。短い枝の条件と、詳しい成立条件・例外の説明を結び付ける。色やホバーだけを対応の手掛かりにせず、常時読める記号と参照先を残す。必要ならクリック/キーボードで相手を強調するが、JavaScript無効と印刷でも対応が分かるようにする。

広幅では図と対応解説を横に配置する。狭幅では図、番号付き対応解説の順に並べる。横配置のために図の文字を縮小したり、必要な関係を削ったりせず、元担当が図の余白・構成・ノードの分割を設計し直す。対応解説は長い総論を丸ごと横へ移すのではなく、図の部品/矢印と結び付いた短い段落にする。資料の全文、長いコード、補足は後続の詳細へ置ける。

design.mdに、図内に残すもの、横へ移すもの、ノードを分けた理由、図と解説の対応を記録する。review.jsonでは、前版の必要な意味・条件・値の説明先、図中記号と解説参照の欠落/不一致、PC横配置/狭幅縦配置、表示後の文字・枝・全体の収まりを確認する。文字数の減少やノード数の増加だけで品質を合格にしない。

## 解説雛形の契約

`explanation.html`には、図の前に置く短い導入、図の読み方、具体的な入力→処理→結果の説明、図中の部品/矢印/値とコードまたは具体物の対応、条件と例外、出典リンクを含める。図中の具体値を繰り返すだけでなく、なぜその結果になるかをつなぐ。書類や自然現象の題材にコードを強制しない。親が整文した場合も出典と図の条件が保持されることを確認する。

雛形の各まとまりへ `data-diagram-intro`, `data-diagram-reading`, `data-diagram-explanation`, `data-diagram-conditions` の属性を付ける。例えば `<p data-diagram-intro>前提とこの図で確かめること。</p>` とする。属性の存在は検査できるが、文章のつながりと具体性は内容で確認する。

## 起動と証跡

Codexでは `collaboration.spawn_agent` を `fork_turns="none"` で使い、実際に返されたagent名/IDを、図IDとともに起動直後に`diagram-agent-manifest.json`へ保存する。Claude Codeでは新規Agentを起動して同じ対応を記録する。架空の担当IDを作らない。チケット/起動だけで作成済みにせず、担当の最終応答と全成果物を確認してcompleteにする。

親エージェントと記事統合担当の実行枠を含めて空き枠を確認する。上限4枠で、親1人＋記事統合担当1人の場合、同時に動かす図担当は最大2人。残る図はキューに置き、1図ずつ新規担当を起動する。空き枠がない時に統合担当が代行しない。

起動文の例（内容は図ごとに作り、評価基準は加えない）:

```text
あなたは1つの図の専任担当です。再委譲せず、この図だけを完成させてください。
制作手順: <skill>/references/diagram-delegation.md
作図スキル: <skill>/vendor/archify-jp/SKILL.md
図ID・問い・共有用語・条件・出典の入口: <brief.json>
ネットで一次資料を実際に読み、対象固有の具体値/条件/境界を調査してください。
表現方法の設計、図の生成・表示確認、付随解説の雛形まで一貫して行ってください。
保存先: <article-output>/diagrams/<diagram-id>/
research.json, design.md, model.json, figure.html, explanation.html, review.jsonを返してください。
```

manifestの各行は `id`, `agent_id`, `assigned_diagram_ids:[id]`, `status`, `outputs` を持つ。outputsのresearch/design/model/figure/explanation/reviewは記事出力先からの相対パス。research.jsonは `sources` 配列に実際に開いた `url`, `checked_at`, `finding`（その図に関わる具体的な知見）, `location`（資料内の場所）を持つ。review.jsonは表示/意味/実行の確認と未確認を分ける。

```sh
python3 scripts/check_diagram_delegation.py <article-output>/diagram-agent-manifest.json --article <article-output>/output.html
```

このCLIは1図1担当の契約検査に加え、[Archify必須ゲート](archify-gate.md)で同梱CLIの実再生成、標準SVG、記事画像の一致を必須検査する。単にArchifyと記載したmetadataやレシートを信用しない。**実際のエージェント起動・ネット閲覧の実行や調査/図/文章の品質を、manifestだけから認証するものではない。** 実際のツール応答と担当の最終応答へ照合し、必要なら実在する担当一覧を`--observed-agents`で渡す。形式検査の成功を内容品質の合格としない。

各行の`archify`に`type`, `viewer`, `svg`, `receipt`を記録する。outputs.modelは実際の型付き入力JSON、outputs.figureとarchify.viewerはdeliverの出力HTMLとする。標準SVGと記事の画像をバイト照合する。独自SVG・未確認PNG・未検証のSVG overlayを加えて検査を通さない。

## 統合へ返す図と解説の配置契約

`panel.html`には主図と全局所投影を含める。投影ごとに `<div data-archify-variant="primary">` またはvariantsのidを持つコンテナを置き、直下にfigureとasideを並べる。asideは同じ番号の具体説明を持つ。主図の説明だけを返し、局所投影の横には関係のない注記だけを置かない。標準SVGは無改変のimgとモデル生バイトのhashで埋め込む。

完了はファイルの存在や途中のMESSAGEから推測しない。統合担当は実際の最終応答、必須成果物、各投影の再生成ゲートと実表示の報告を照合して受領する。論理図数・標準投影数・同じ図の再掲載数を区別し、制作量を品質点に置き換えない。

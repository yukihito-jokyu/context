# 理解に必要な情報から表示を決める

Claude風の配色は、白に近い暖かい背景・淡い面・濃いグレーの文字とする。ライトに固定し、OS設定で黒へ変えない。既存generative-claude-uiの部品・配色を使うが、文字サイズは今回のユーザー指定を優先して大きくする。

## 書く前に決めること

1. 読者に最後に理解してほしい違いを一文にする。
2. その違いを理解するために必要な前提を選ぶ。知らない専門語は先に普通の文字で説明する。
3. 同じ入力の一例から、差が生まれる場所と結果までをつなぐ。
4. 常に表示する情報と、必要になってから開く情報を分ける。
5. 各文章・図・コードが何を理解させるかを確認する。同じ内容を同じ粒度で繰り返すものは削る。

## 関心ごとのページ

一つの画面にすべてを常時表示しない。最初の入口となるページは次の役割を持つ。題材の仕様一覧に合わせて詳細ページを追加する。

| ページ | 読者の問いと表示内容 |
| --- | --- |
| 全体像 | 何が似ていて、どこが違うか。短い答え、比較の前提、実行場所の図。 |
| 同じ例の動き | 同じ入力を渡すとどう動くか。入力、境界、矢印、結果とその意味。 |
| コードと設定 | どう実装するか。図との対応、左右の最小コード、配置と設定。 |
| 使い分け | 自分の目的ならどちらを選ぶか。用途と理由。 |
| 公式資料 | 根拠と確認範囲をどこで確かめるか。資料、版・確認日、未確認事項。 |

各対象のイベント、処理方式、設定と入出力、UI・API、状態、失敗・制限、導入・運用を詳細ページへ分ける。仕様の対応表から各説明先へ移動できるようにする。短い初期表示と、必要な情報の保持を両立する。

ページ数が増えた場合は「全体像」「動作と設定」「拡張」「導入と運用」「資料」のような関心グループでまとめ、選択したグループのページ選択だけを表示する。多数のタブを常時並べてヘッダーを大きくしない。共通領域には比較対象と確認範囲、関心とページ選択だけを残す。短い結論・前提・最小コードはそれぞれ担当するページで見せる。各ページへ直接移動した人にも必要な前提が分かるよう、短い文や前のページへのリンクを置く。情報を重複してすべてのページへ詰め込まない。

選択したページのみ表示し、現在位置をaria-currentでも示す。ページ名付きの前後リンクを置く。ハッシュによる直接表示、再読み込み、戻る・進むを同期し、別ページのコード行へ移動したら対象ページと閉じたdetailsを開いて注目位置へ移動する。印刷時とJavaScript無効時は全内容を読めるようにする。

全体像は実行場所・構成、次のページは入力から結果というように図の役割を分ける。図だけでつかめるよう、入力の形、処理を囲む境界、矢印、結果を使う。関数名を箱に並べるだけにしない。比喩を使う場合は実物との対応を図外で短く説明する。

## 開いて読む情報

担当ページ内でも、ファイル構造、設定、長いコード全文、追加条件、別入力の追跡はdetailsに置ける。公式資料は専用ページで直接読めるようにし、長い引用や追加の検証記録だけを必要に応じて折りたたむ。補足を常時表示したい場合は、読者が今の説明を理解するために必要な理由があるか確認する。必要なら本文と同じ大きさで説明し、不要なら初期表示から外す。

小さく表示して情報量を増やさない。核心の理由や比較範囲を出典欄や閉じたdetailsへ逃がさない。たとえばHooks全体ではなくcommand型に比較を絞るなら、前提の段階で明記する。

## 文字の強弱

| 役割 | 基準 |
| --- | --- |
| 最も伝えたい違い | 26〜30px / 500 |
| ページの見出し | 28px前後 / 500 |
| 節・比較対象の見出し | 22〜25px / 500 |
| 説明本文 | 19px / 行間1.8 / 400 |
| 図・UI・出典を開いた本文 | 18〜19px |
| コード | 17〜18px / 行間1.8 |

文字の役割を決めてから大きさを決める。見出しだけを大きくするのでなく、差が生まれる場所・入力や結果の重要値を読みやすくする。13pxの補足や小さい凡例は使わない。太さは400と500とし、色・余白・サイズで優先順位を示す。小さい画面でも本文は縮小しない。

説明文は動作の主体と対象を省略しない。文章は「Claude Codeが入力を渡す → スクリプトが判定する → Claude Codeが実行を止める」のように、主体の切り替わりと因果をつなぐ。短さのために主語を削らず、主体が変わる位置で文を分ける。図の動作文と表の説明にも同じ基準を使う。

字数は不足なく説明できる最短を目指す。一段落は一つの内容、通常1〜2文を出発点とする。字数制限のために前提やつなぎを削らない。図前には何を見るか、図後には見えた違いがどんな意味を持つかを置く。

## 横比較

説明本文は約760px、比較領域は約1220pxを基準にする。広い画面はAを左・Bを右へ固定する。同じ観点の見出し、図、コード、説明、設定を行ごとに揃え、視線を横へ動かすだけで比較できるようにする。

文字が窮屈なら比較領域を広げ、図を分割し、コードを意味のある短い単位にする。文字を小さくしない。狭い画面では縦配置へ変え、矢印の向きも配置に合わせる。SVG全体を縮小して文字を小さくする方法を避ける。

## 動きで視線を案内する

実行図では、短い線分が矢印に沿って入力の受け渡しを追い、枠が現在の主体を示す。文字・配置・境界は固定し、読者が動いた場所を探し直す必要をなくす。短い段階選択と大きな現在段階の説明を使い、画面に出す操作を絞る。詳しい設計と操作の確認は[flow-motion.md](flow-motion.md)に従う。

## コードの導線

ファイル名を読みやすい大きさで示し、元の行番号、控えめな構文色、差が生まれる注目行を付ける。説明から注目行へ移動できるリンクを置く。設定パス、関数名、入力と結果を図とそろえる。

同梱テンプレートのA/B_CODE_PANEL_HTMLには、code-panel → code-heading + code-lines → code-lineの構造を入れる。code-lineは元の文字列をHTMLエスケープしてcodeに入れ、行番号はaria-hiddenの空spanとdata-lineから表示する。元の字下げを変えない。DOMライブラリで再保存する場合は、空白だけのテキストノードが正規化されないか実際のソースと照合する。

POSITION_OVERVIEW_HTMLは全体像ページの構成図、SCENARIO_BRIDGE_HTMLは動きのページの前提、OVERVIEW_HTMLは同じ入力の実行図、DIAGRAM_EXPLANATION_HTMLは図の意味を担当する。CONFIG_AND_FILES_HTMLはコードページの配置と設定、TRACE_AND_LIMITS_HTMLは動きのページの追加条件、SOURCES_HTMLは公式資料ページの根拠と確認範囲を担当する。長い全文や追加条件は担当ページのdetailsへ置き、抜粋と実行可能な最小例を区別する。

## 確認

[prose-review.md](prose-review.md)に従って全説明文を読み直し、主体・対象・指示語・文のつながりを確認する。構造検査や主語らしい語の検索を、文章の合格判定の代わりにしない。

最初の表示だけで比較の中心と必要な前提が分かるか、図から注目コードへ進めるか、不要な小さい文字を残していないかを確認する。通常文字のコントラスト比4.5以上を確認し、既存UI lintのERRORを直す。ユーザー指定で文字を大きくしたことを、既存スキルの22/18/16pxからの意図的変更として記録する。

公式情報の版・確認日・比較範囲を記録する。閲覧した公式資料と、説明用に自作した条件・コードを区別する。ブラウザが利用できない場合は静的な確認・模擬実行を実際の表示・製品上の実行と扱わない。

## 関心が増えた場合のテンプレート

CONCERN_NAV_HTMLは関心グループのnav.concern-navを持つ。各aはdata-groupと最初の担当ページへのhrefを持つ。TOPIC_NAV_HTMLはグループごとのnav.topic-navで、data-topic-groupとページリンクを持つ。DETAIL_PAGES_HTMLは仕様一覧に必要な全詳細ページを持ち、各sectionにdata-page、data-group、data-label、固有idと説明名を付ける。共通ナビはグループを示し、詳細ナビは選択ページをaria-currentで示す。説明先の固有idは対応表から使う。

最初の4ページはstart、資料はreferenceへ割り当てる。別のグループ名を使う場合はnavとpageのdata-groupを一致させる。詳細ページを追加した後、前後リンク、直接ハッシュ表示、コード行・詳細へのリンク、印刷とJavaScript無効の全情報表示を検証する。プレースホルダーだけを埋めて仕様の網羅を確認したと扱わない。

## 関心別ページの冒頭の全体図

すべてのページを「このページの問い → 必要な前提と図の読み方 → 常時表示の全体図 → 領域ごとの説明 → 個別図・コード」の順に組み立てる。全体図ではそのページの主要領域と関係を示し、読者が詳細を読む前に位置を把握できるようにする。資料一覧と対応表も対象に含める。

イベントの全体図は、代表的な一回の流れだけで済ませない。主な節目と、ファイル変更・設定変更など独立して発生する領域を区別して網羅する。個別イベント図へのリンクを置き、図のノードと下の説明の名称をそろえる。初期表示の図をdetailsへ隠さない。

テンプレートの`OVERVIEW_WHOLE_MAP_HTML`、`SCENARIO_WHOLE_MAP_HTML`、`IMPLEMENTATION_WHOLE_MAP_HTML`、`CHOICE_WHOLE_MAP_HTML`、`SOURCES_WHOLE_MAP_HTML`には、各ページの全体図と読み方を入れる。追加の`DETAIL_PAGES_HTML`内の全ページにも同じ要素を置く。制作時に空欄へ置換して済ませない。全体図のコンテナへ`data-concern-overview="ページID"`を付け、ページ数と全体図数を照合する。

全体図の各スロットには、Archifyで生成したSVG/PNG画像をimgで埋め込む。画像には`data-archify-model-sha256`を配布レシートの仕様SHA-256で設定する。モデル、CLIの検証・配布レシートを残し、画像化の調整と元の配布HTMLを区別する。画像内のノードを詳細の入口にする場合、生成された座標からHTMLのリンク領域を重ね、アクセシブルな説明名を付ける。枠の位置を推測で置かない。

## 標準エクスポートの保持

Archifyの`editorial`モデルを検証・配布した後、標準のSVG/PNGエクスポートを使う。画像を生成するために凡例・記号・背景・グリッドを除去したり、viewBoxを切り詰めたり、配色・文字サイズ・フォントをHTML側に似せて上書きしたりしない。HTMLのimgには`data-archify-preset="editorial"`と、出力経路を表す`data-archify-export`を付ける。元の配布HTMLと生成元モデルを保持する。ブラウザ以外で検査用PNGを作った場合は検査用と明記し、標準PNGとして埋め込まない。

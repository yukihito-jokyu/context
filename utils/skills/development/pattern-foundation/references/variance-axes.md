# 揺れの軸：何を決めれば「誰が書いても同じ」になるか

フェーズ3で読む。**揺れ**とは、同じ指示と同じ資料を渡された有能な作者2人が、違うものを書きうる点のことである。揺れを1つ残すと、収束テストでその点の差が必ず出る。この文書の軸を全部見て、その分野で揺れうる軸すべてに答えを1つ決める。

## 目次

1. 答えの決め方
2. ルールの書き方
3. ルールIDの接頭辞
4. 軸のカタログ（A〜H）
5. 変更に強い構造の決め方
6. 完了条件

## 1. 答えの決め方

軸ごとに、次の順で答えを決める。上で決まったら下は見ない。

1. ユーザーの指示に答えがある → それに従う
2. 公式に推奨がある → それに従う（エージェントが最も自然に書く形だから）
3. 候補のうち、機械で強制できるものがある → それを選ぶ（強制できない答えは揺れが残るから）
4. 依存を増やさない答えがある → それを選ぶ（指示に無いライブラリを足すと、どれを足すかで作者ごとに分かれるから）
5. 変更が局所に収まるものを選ぶ（5章）
6. 概念の数が少ないものを選ぶ（覚えることが少ないほど守られるから）
7. それでも決まらなければ、その分野で最も普及しているものを選び、ADR に「好みで決めた」と書く

**公式の現行の推奨と、広く知られた旧来の書き方が食い違う場合**（例：公式が命名の接頭辞の慣習をやめた、ファイルの分け方を変えた）は、公式の現行に従う。そのうえで、旧来の書き方を悪い例に書き、機械で止める（probe を書く）。エージェントは旧来の書き方に引き戻されやすいため、文書だけでは揺れが残るからである。公式が複数の書き方を許している場合は、1〜7の順で1つに絞る。

**「場合による」は答えではない。** 条件で答えが変わる軸は、条件を列挙した決定表にする。決定表は、どの行にも当たらない入力が無いように最後に「上のどれでもない → 〇〇」の行を置く。

```markdown
| 状態の性質 | 置き場所 |
|---|---|
| サーバーから取得したデータ | TanStack Query のキャッシュ |
| URL で共有・復元したい（検索条件、ページ番号、タブ） | ルートの search params |
| フォームの入力中の値 | フォーム要素自身（非制御。送信時に FormData で読む） |
| 複数の画面をまたぐ UI の状態（サイドバーの開閉） | Zustand のストア |
| 上のどれでもない（1つのコンポーネントの中だけの状態） | useState |
```

**揺れない軸は書かない。** formatter が自動で決める点（インデント、引用符、改行位置）は、formatter に任せたことを1つのルールとして書くだけにし、個別のルールにしない。

## 2. ルールの書き方

ルールは `docs/design/rules.md` に、ひな形の書式で書く。`rules_check.py` がこの書式を読んで検査するため、項目名を変えない。

### 2.1 粒度と番号

ルールの数や番号が作者ごとに分かれると、ID で参照する仕組み（レビュー指摘、probe、検査のエラー）全体がずれる。そこで次のとおり機械的に決める。

- **1つの軸に1つのルールを既定にする**。同じ軸の中で、(a) 強制の段が違う決定がある場合、(b) 片方だけ破られうる独立した決定がある場合に限って、ルールを分ける。分けたルールは同じ軸の記号を持つ
- 1つのルールが複数の軸に答える場合は、軸を全部書き、ルールは1つにする
- **番号は節ごとに 01 から振る**。カタログの軸の順（A1、A2、…）に並べ、同じ軸の中では決定の順に振る。追加した軸（X）のルールは、「追加した軸」表の「置く節」の最後に並べる
- ルールが0件の節は見出しごと消し、その軸を「対象外とした軸」表に書く

### 2.2 各項目の書き方

- **決定**は、検証できる1文で書く。読んだ2人が同じ判定をできる文にする
  - 悪い例：「コンポーネントは適切な粒度に分割する」
  - 良い例：「1ファイルが公開するコンポーネントは1つとし、ファイル名はそのコンポーネント名と一致させる」
- 条件で答えが変わる決定は、**決定**の行の次から2字下げで決定表を書く
- あいまいな語（なるべく、できるだけ、適切、適宜、必要に応じて、基本的に、原則として、推奨、望ましい、場合による、柔軟に、可能であれば、など、その他）を**決定**に使わない。`rules_check.py` がエラーにする。例外があるなら、例外を全部列挙する
  - ルール名・識別子・パスは `` ` `` で囲む。囲んだ部分は検査から除かれる
  - 「を含む」「ほか」は列挙が閉じていない可能性があるので、警告が出る。全部を列挙しているなら、そのままでよい
- **軸**には、そのルールが答えている軸の記号（4章の `A2`、`C1` など）を書く。`rules_check.py` は、全軸がどれかのルールか「対象外とした軸」表に現れることを検査する
- **理由**には、何が揺れ、何が壊れるのを防ぐのかを書く。理由の無いルールは、困ったときに破られる
- **良い例・悪い例**を必ず付ける。それぞれ5行以内にし、長くなるなら「見本: <参照実装のパス>」と書く。悪い例は「実際に書かれがちなもの」にする。収束テストで見つかった揺れは、そのまま悪い例になる

## 3. ルールIDの接頭辞

ID は `<接頭辞>-<2桁以上の連番>` とする（例：`DEP-03`）。接頭辞は下の表から選ぶ。分野固有の軸が多い場合に限り、2〜6文字の英大文字で新しい接頭辞を足してよい。足したら rules.md の冒頭の表にも足す。ルールを廃止しても ID は再利用せず、「廃止」と書いて残す。レビュー指摘や probe が古い ID を参照していても辿れるようにするためである。

| 接頭辞 | 軸のグループ |
|---|---|
| `STR` | A 配置と構造 |
| `DEP` | B 境界と依存 |
| `NAM` | C 命名 |
| `CODE` | D 書き方 |
| `ERR` | E1〜E2 エラー・入力検証 |
| `STATE` | E3 状態・データの流れ |
| `ASYNC` | E4 非同期・並行 |
| `OPS` | E5〜E8 ログ、設定、セキュリティ、i18n など |
| `TEST` | F テスト |
| `PROC` | G 作業手順 |
| `TOOL` | H 道具・自動化 |

## 4. 軸のカタログ

各軸について「その分野で揺れるか」を判断する。揺れない、または対象外なら、rules.md の末尾の「対象外とした軸」表に、軸の記号と理由を1行で書く。何も書かずに飛ばさない。検討漏れと区別できなくなるからである。

カタログはコードを書く分野を基準にしている。そのため、分野ごとの読み替えと追加の軸は [domain-profiles.md](domain-profiles.md) の該当節に従う。

- **軸の読み替え**：例として、data 分野では D2 を「`ref` の書き方」と読む。domain-profiles の表どおりに読み替え、表で「対象外」とされた軸は、その理由のまま「対象外とした軸」表に写す
- **追加の軸（X）**：domain-profiles が定める X 軸は、記号と名前をそのまま「追加した軸」表に写す。それ以外に足すのは、domain-profiles に無い固有の軸がある場合だけで、続きの番号を振る
- **分野が複数の場合**：domain-profiles の分野の順に X 軸を並べ、X1 から通しで振り直す

### A. 配置と構造（STR）

| 軸 | 決めること |
|---|---|
| A1 ディレクトリの切り方 | 機能別か層別か、その組み合わせ方。階層の深さの上限 |
| A2 新しい単位の追加形 | 機能・画面・エンドポイント・リソース・モジュールを1つ足すときに作るファイル一式の、パスと名前の完全な一覧 |
| A3 ファイルの粒度 | 1ファイルに置く公開要素の数。分割する条件 |
| A4 共有コードの置き場と昇格条件 | 共有ディレクトリの位置。どの条件を満たしたら機能内から共有へ移すか（例：2つ目の利用者が現れた時点） |
| A5 付随物の置き場 | テスト、fixture、型定義、定数、スタイル、ストーリーを、対象の隣に置くか別ディレクトリに置くか |
| A6 生成物・設定・スクリプトの置き場 | コード生成の出力先。生成物を手で編集してよいか |
| A7 入口ファイル | index・barrel・main・`__init__` などの入口ファイルを置くか、何を書いてよいか |

### B. 境界と依存（DEP）：変更に強い構造の核

| 軸 | 決めること |
|---|---|
| B1 依存の向き | 層・モジュール間で import してよい組み合わせの許可表（許可されていないものは全部禁止） |
| B2 公開面 | モジュールの外から触ってよい入口。内部を外から触れなくする方法（可視性、internal、公開ファイル） |
| B3 横の参照 | 同じ層の機能同士が直接参照してよいか。いけないなら代わりの手段（上の層で組み合わせる、イベント、共有へ昇格） |
| B4 外部ライブラリの使い方 | 使ってよいライブラリの一覧。ラッパー経由を義務にするライブラリ（HTTP クライアント、日時、ログなど）と、ラッパーの置き場 |
| B5 副作用の置き場 | I/O、時刻、乱数、環境変数、グローバル状態に触れてよい層 |
| B6 依存の追加 | 新しいライブラリを足す手順（ADR を必須にするか、誰が承認するか） |

### C. 命名（NAM）

| 軸 | 決めること |
|---|---|
| C1 ファイル・ディレクトリ名 | ケース（kebab、snake、Pascal）、接尾辞（`.test`、`.schema`、`_handler`） |
| C2 識別子 | 型、クラス、関数、変数、定数、列挙値のケース |
| C3 役割の語彙 | 役割ごとの接頭辞・接尾辞（例：`use〜`、`〜Repository`、`〜Handler`）を表にする |
| C4 動詞の語彙 | 同じ意味の動詞を1つに絞る（get、fetch、load、retrieve のどれを使うか。create と add、update と edit、delete と remove） |
| C5 型が分かる名前 | 真偽値（`is`、`has`）、集合（複数形か `List` か）、非同期（接尾辞を付けるか）、単位（`timeoutMs`） |
| C6 略語と大文字 | 略語の可否と表記（`Id` と `ID`、`Url` と `URL`） |
| C7 外部と内部の対応 | API・DB・設定の名前（snake_case など）とコード内の名前の変換規則、変換する場所 |

### D. 書き方（CODE）

| 軸 | 決めること |
|---|---|
| D1 宣言の形 | 関数宣言かアロー関数か、class か関数か、メソッドかレシーバ関数か |
| D2 import と export | default と named のどちらを使うか、相対パスか alias か、並び順、型だけの import |
| D3 型の書き方 | type と interface のどちらを使うか、any・unknown の扱い、null と undefined、enum とその代替、戻り値の型を明示するか |
| D4 制御フロー | 早期 return、三項演算子の可否、ネストの上限、switch の網羅性 |
| D5 不変性 | 再代入、引数の変更、配列・オブジェクトの破壊的操作の可否 |
| D6 大きさの上限 | 関数の行数、引数の数、複雑度、ファイルの行数 |
| D7 コメント | 書くこと（なぜ）と書かないこと（何をしているか）、ドキュメントコメントの対象、TODO の書式 |
| D8 マジック値 | リテラルを定数にする条件と、定数の置き場 |

### E. 振る舞いの方針

| 軸 | 接頭辞 | 決めること |
|---|---|---|
| E1 エラー | ERR | 表現（例外、Result、エラー値）、どの層で捕まえるか、ユーザー向け表示・HTTP ステータスへ変換する場所、エラーの種類の定義場所 |
| E2 入力の検証 | ERR | 検証する場所（境界でスキーマ検証）、スキーマの置き場、検証後の型の流し方 |
| E3 状態とデータの流れ | STATE | 状態の種類ごとの置き場（1章の決定表の例）、キャッシュのキー、データ取得を書く場所 |
| E4 非同期・並行 | ASYNC | async/await か Promise チェーンか、キャンセル、並列実行、再試行、タイムアウト |
| E5 ログ・観測 | OPS | ロガー、ログレベルの使い分け、構造化ログのキー名 |
| E6 設定と秘密情報 | OPS | 環境変数を読む場所（1か所に集める）、検証、既定値 |
| E7 日時・数値・文字列 | OPS | タイムゾーン、日付ライブラリ、金額、i18n の仕組み、表示文字列の置き場 |
| E8 セキュリティの定型 | OPS | 認可を確かめる場所、出力のエスケープ、秘密情報をログに出さない方法 |

### F. テスト（TEST）

| 軸 | 決めること |
|---|---|
| F1 何をテストするか | 対象の種類ごとのテストの粒度を決定表にする（純粋関数は単体、境界は結合、画面は操作ベース など） |
| F2 テストの形 | 構成（AAA、テーブル駆動）、テスト名の書式、1テストの検証数 |
| F3 偽物の作り方 | mock・fake・stub のどれを使うか、作る場所、HTTP のモック方法 |
| F4 テストデータ | factory・fixture の作り方と置き場 |
| F5 必須条件 | 新しい単位を足したときに必須のテスト。カバレッジの閾値を設けるか |

### G. 作業手順（PROC）

| 軸 | 決めること |
|---|---|
| G1 新規追加の順序 | 作るファイルの順番（内側から外側へ など）、生成器の使用 |
| G2 波及の対応表 | 一緒に変えなければならないファイルの組（例：エラー型と HTTP 変換表と API 仕様） |
| G3 依存・バージョンの更新 | 更新の手順と、更新後に回す検査 |
| G4 ルール自体の変更 | ADR → rules.md → 検査・probe → 参照実装、の順で変える |
| G5 完了の定義 | 完了と言ってよい条件（check が通る、チェックリストを満たす） |

### H. 道具・自動化（TOOL）

| 軸 | 決めること |
|---|---|
| H1 整形 | formatter に任せる範囲（全部）。エディタ設定（`.editorconfig`） |
| H2 自動実行 | 編集直後（hooks）、コミット前、CI のそれぞれで何を回すか |
| H3 抜け道の禁止 | 抑止コメント、設定の緩和、テストの skip の扱い |
| H4 実行環境の固定 | ランタイムとパッケージマネージャのバージョン、lockfile |

## 5. 変更に強い構造の決め方

「変更に強い」を感覚で判断しないために、次の3つを `docs/design/architecture.md` に書き、構造の判断の根拠にする。

1. **変更シナリオ表**：この基盤で今後よく起きる変更を5〜10個挙げ、それぞれで触るファイルを列挙する。触るファイルが多い、または予測できないシナリオがあれば、構造を見直す
   ```markdown
   | 変更 | 触るファイル | 触らないもの |
   |---|---|---|
   | API のレスポンスに項目が1つ増える | `features/users/api/schemas.ts`、それを表示するコンポーネント | ほかの機能、共有コンポーネント |
   ```
2. **依存の許可表**（B1）：層やモジュールを行と列に並べ、import してよい組だけに印を付ける。この表は構造検査（lint の境界ルール、アーキテクチャテスト）でそのまま強制する
3. **公開面の一覧**（B2）：各モジュールの外から使ってよい名前・ファイル。それ以外は外から触れないようにする

変更シナリオ表の行は、収束テストの「変更」課題の材料にもなる。

## 6. 完了条件

- A〜H の全軸に、ルールIDか「対象外の理由」がある（`rules_check.py` が検査する）
- 決定表に「上のどれでもない」行がある
- `architecture.md` に変更シナリオ表、依存の許可表、公開面の一覧がある
- `python3 <root>/.foundation/bin/rules_check.py --root <root> --phase 3` が通る（書式、あいまいな語、全軸の網羅を検査する。probe とスキルの検査はフェーズ4・5で加わる）

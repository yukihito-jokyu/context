# エージェント向けの入口：AGENTS.md・実装用/レビュー用スキル・hooks

フェーズ5で読む。ここで作るものは、**初めてこの基盤を触る作者（人またはエージェント）が最初に読む道筋**である。収束テストで独立エージェントが同じものを書けるかどうかは、ルールそのものに加えて、この道筋で必要な情報に迷わず辿り着けるかで決まる。

## 目次

1. 情報の置き場（重複させない）
2. AGENTS.md と CLAUDE.md
3. 実装用スキル
4. レビュー用スキル
5. hooks と保護ファイル
6. 完了条件

## 1. 情報の置き場（重複させない）

同じ情報を2か所に書くと、片方だけが更新されて食い違い、作者がどちらに従うかで揺れる。そこで、情報ごとに正本を1つに決め、ほかの場所からは参照する。

| 情報 | 正本 | ほかの場所での扱い |
|---|---|---|
| ルールの全文（決定、理由、例） | `docs/design/rules.md` | ID で参照する。AGENTS.md には最重要ルールの1行要約だけを置く |
| 構造の理由・依存の許可表・変更シナリオ | `docs/design/architecture.md` | スキルからリンクする |
| パターンごとの手順と作るファイル一覧 | 実装用スキルの `references/patterns.md` | AGENTS.md からスキルへ案内する |
| コードの書き方の見本 | 参照実装（実際に動くコード） | patterns.md は見本ファイルのパスを示す。コード片は、見本だけでは分からない部分に限る |
| 検査の仕組みとの対応 | `docs/design/enforcement-matrix.md`（生成物） | — |
| コマンド | manifest の `commands` と AGENTS.md のコマンド表 | 両者を同じ値にする |

## 2. AGENTS.md と CLAUDE.md

- `CLAUDE.md` は `@AGENTS.md` の1行だけにする。Claude Code はこれで AGENTS.md を読み込み、ほかのエージェントは AGENTS.md を直接読む。中身を1か所にまとめるためである
- `AGENTS.md` は、ひな形（`assets/templates/AGENTS.md.tmpl`）の節の順番を変えずに埋める。長さは 150 行以内を目安にする。毎回読まれる文書なので、長いと重要な部分が埋もれる
- 「守ること」には、ID 付きで10〜15個のルールを選ぶ。全ルールを並べない。フェーズ5では、違反すると影響が大きいルールで選ぶ。フェーズ6の後に、収束テストで揺れたルールへ入れ替える
- 強制に `doc` を含むルールは、AGENTS.md の「守ること」か、実装用スキルの手順・チェックリストに ID 付きで書く。文書でしか守らせないルールは、作者の目に入る場所に無ければ効かないからである（`rules_check.py` が検査する）
- 「してはいけないこと」には、抜け道（設定の緩和、抑止コメント、依存の勝手な追加、見本と違う新しいパターンを作ること）を必ず書く
- 作業の入口として、実装なら実装用スキル、レビューならレビュー用スキルを使うことを冒頭に書く。Claude Code は、起動したディレクトリの `.claude/skills/` を読む。そのため README に「この基盤のディレクトリで Claude Code を起動する」と書く

## 3. 実装用スキル

`assets/templates/impl-SKILL.md.tmpl` と `impl-patterns.md.tmpl` から作る。節の構成は変えない。この構成は、作者ごとに判断が分かれる場面を、1つずつ表と手順で塞ぐように並べてあるからである。

| 節 | 塞ぐ揺れ | 書き方 |
|---|---|---|
| description | スキルが使われない | 「この基盤で何かを実装・変更・追加・修正する依頼では必ず使う」と書く。依頼の言い方の例を5つ以上並べる |
| 1. 振り分け表 | 依頼の解釈が分かれる | 依頼に含まれる語句・状況と、patterns.md の節を対応させる。複数に当たる場合の順序と、どれにも当たらない場合の扱い（実装せずに、新しいパターンの提案として報告する）を書く |
| 2. 決まらない値の表 | 作者ごとに違う値を推測する | 依頼から決まらない値（長さの上限、ページの件数、削除時の扱い、表示文言など）を、「何に響くか」と既定値付きで書く。聞けるなら聞き、聞けないなら既定値にして報告に書く |
| 3. 書く前に読む | 読む資料が人によって違う | 読むファイルを具体的なパスで列挙する（patterns.md の該当節、rules.md の該当する接頭辞、見本ファイル） |
| 4. 作る順序 | 作る順番と、途中の形が違う | 番号付きの手順にする。生成器があれば必ず使う。手順ごとに、通るべき検査を書く |
| 5. 検証 | 完了の基準が違う | check コマンドを書く。落ちたときは、エラーのルールIDか lint ルール名から rules.md を引いて直す。設定・保護ファイル・抑止コメントで黙らせない |
| 6. 完了前チェックリスト | 機械が拾えない漏れ | ファイルをまたぐ対応（G2 の波及の対応表）を、両側のファイルを開いて突き合わせる項目にする。強制に `review` を含むルールの自己確認もここに入れる |
| 7. 報告 | 報告の中身が違う | 固定の順序：作ったもの、変更ファイル（作る順序の順）、2で決めた値とその根拠、check の結果、残したこと |

`references/patterns.md` の各節は、次の書式にそろえる。

```markdown
## <番号>. <パターン名>

- 使う場面：<振り分け表の行と同じ言葉>
- 見本：<参照実装のファイルパスの一覧>
- 作る・変えるファイル：
  | 順 | パス（<feature> などのプレースホルダ付き） | 見本との対応 | 守るルール |
- 手順：<番号付き。見本をどう写し、何を置き換えるか>
- この場面で間違えやすいこと：<収束テストで出た揺れ>
```

## 4. レビュー用スキル

`assets/templates/review-SKILL.md.tmpl` から作る。レビューで揺れるのは「何を指摘するか」と「どう書くか」である。そこで、指摘をルールIDに結び付け、出力の形を固定する。

- **機械が拾うものを人手で重複して指摘しない**。最初に check を回し、落ちていれば出力をそのまま載せる。人手で見るのは、強制に `review` を含むルールと、ファイルをまたぐ対応と、抜け道だけにする
- **確認項目は、rules.md で強制に `review` を含むルール（最も強い段が別でも含む）と1対1にする**。各項目を表の1行にし、1列目にルールID、続けて確認方法（どのファイルの何を見るか）と違反の典型例を書く。`rules_check.py` は、該当する全ルールIDが、このスキルの表の1列目にあることを検査する
- **指摘は必ずルールIDを持つ**。ルールに無い気づきは、指摘ではなく「ルール追加の提案」節に書く。ルールに無いことで差し戻すと、レビュアーごとに基準が変わるからである
- **判定は機械的に決める**：check が通り、かつ違反の指摘が0件なら「承認」、それ以外は「差し戻し」
- **出力の形は固定する**（ひな形の 6 節）。収束テストのレビュー検出率の採点は、出力に含まれるルールIDを数えて行う

## 5. hooks と保護ファイル

`init_foundation.py` が `.claude/settings.json` を作る。中身は次の2つである。

| hook | 起動するタイミング | 動作 |
|---|---|---|
| PreToolUse（Edit・Write など） | ファイルを編集する前 | `hooks.py pre-edit`：対象が manifest の `protected` に当たれば、ユーザーに確認を求める（`permissionDecision: "ask"`）。画面の無い実行（`claude -p`）では確認できないため拒否になり、独立エージェントが設定を緩めて検査を通すことを防ぐ |
| PostToolUse（Edit・Write など） | ファイルを編集した後 | `hooks.py post-edit`：manifest の `hooks.post_edit` のうち対象パターンに合う項目のコマンドを実行する（例：そのファイルの format と lint）。失敗すれば出力をエージェントに返す（終了コード2） |

hooks が働くのは、Edit・Write などのファイル編集ツールに対してだけである。Bash のコマンドでファイルを書き換えることは止められない。そこで、収束テストの runner の `--allowedTools` は検査コマンドに絞り、保護ファイルの差分は収束テストの diff とレビュー用スキルでも確かめる。

`hooks.post_edit` の各項目は `{"glob": "src/**/*.ts", "command": "npx oxfmt {file} && npx oxlint {file}"}` の形にする。`{file}` には、編集したファイルの基盤ルートからの相対パスが入る。重い検査（型検査の全体、テスト）は入れない。編集のたびに待たされ、作業が遅くなるからである。

## 6. 完了条件

- `CLAUDE.md` が `@AGENTS.md` の1行だけになっている
- AGENTS.md に TODO の目印が残っていない
- 実装用スキルの振り分け表の全行が、patterns.md の節に対応している
- manifest の `status` を `ready` にした
- `rules_check.py` が通る（status が ready なのでフェーズ5の範囲を検査する。review を含むルールがレビュー用スキルの表に、doc を含むルールが AGENTS.md か実装用スキルにある）
- hooks が動く。hook の入力を模した JSON を `hooks.py` に渡し、post-edit が編集したファイルの検査を走らせること、保護ファイルで確認を求める出力が出ることを確かめる（例：`echo '{"tool_input":{"file_path":"<保護ファイルの絶対パス>"}}' | python3 .foundation/bin/hooks.py pre-edit`）

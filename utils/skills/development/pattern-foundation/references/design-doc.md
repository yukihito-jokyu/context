# 設計ドキュメント：何をどこに、どう書くか

フェーズ3で書き始め、フェーズ7で仕上げる。設計ドキュメントの読み手は、この基盤を初めて見る人である。その人が、なぜこの構造とルールなのかを理解し、ルールを変えたくなったときに正しい手順で変えられる状態を目指す。

## 1. ファイルの構成

`docs/design/` に置く。ひな形は `init_foundation.py` が作る。

| ファイル | 内容 | 書く時期 |
|---|---|---|
| `overview.md` | この基盤のゴール、前提（指示、制約）、全体像（主な技術とその役割）、読む順番 | 3 で骨格、7 で仕上げ |
| `research.md` | 技術ごとのバージョン、公式の推奨、出典、採否（[research.md](research.md) の書式） | 2 |
| `architecture.md` | ディレクトリ構造と各層の役割、依存の許可表、公開面の一覧、変更シナリオ表、データの流れ | 3 |
| `rules.md` | 全ルール（ひな形の書式）、追加した軸、対象外とした軸 | 3〜6 |
| `enforcement-matrix.md` | ルールと強制の対応表（`rules_check.py` が生成する。手で編集しない） | 4〜7 |
| `adr/NNNN-<kebab-title>.md` | 主な選択の記録。1つの決定につき1ファイル | 随時 |
| `convergence-report.md` | 収束テストの経過と結果 | 6 |

基盤のルートの `README.md` には、人間向けの最短の入口を書く。何の基盤か、最初に実行するコマンド（依存の導入、check）、この基盤のディレクトリで Claude Code を起動すること、設計ドキュメントへの案内である。

## 2. ADR を書く場面

次の決定は ADR にする。後から「なぜこうなっているのか」と問われ、答えが無いと変更の判断ができなくなるものだからである。

- 技術・ツールの選択（指定されたもの以外。指定されたものは「指定による」と1行で書く）
- ディレクトリの切り方、依存の向きなど、構造の選択
- 公式の推奨から外れた決定
- 既定値で決めた事項（[intake.md](intake.md) の2）
- 収束テストを受けて大きく変えた決定

書式は `assets/templates/adr.md.tmpl` を使う。

## 3. 書き方

読み手とこの文書を書いたエージェントとでは、持っている前提が大きく違う。エージェントが当然と思っている前提が書かれていないと、読み手は文と文のつながりを追えなくなる。次を守る。

- **前提から結論へ順に書く**。結論 C を説明したいなら、前提 A と、A と C をつなぐ B を先に書く。たとえば「機能間の import を禁止する（C）」を説明するなら、先に「機能ごとに変更の頻度と担当が違う（A）」、次に「直接 import すると、片方の変更がもう片方を壊す（B）」を書く
- **根拠は実際の記述と場所を示す**。設計の根拠として基盤内のファイルを示すときは、リンクと引用を並べる
  ```markdown
  [eslint.config.ts の12行目](../../eslint.config.ts#L12)

  > 'no-restricted-imports': ['error', { patterns: ['@/features/*/*'] }]
  ```
  外部の根拠は、research.md の出典を参照する
- **表と決定表を優先する**。散文で条件分岐を書くと、読み手ごとに解釈が分かれる
- **用語を統一する**。rules.md の冒頭に用語の表を置き、全文書でその語を使う
- 文書の言語は manifest の `language` に従う

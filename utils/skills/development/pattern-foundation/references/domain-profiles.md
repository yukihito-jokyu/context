# 分野別の観点

フェーズ0・2・3で、該当する分野の節だけを読む。ここに書いたツール名は**候補**であり、存在・現行バージョン・設定方法はフェーズ2で必ず確かめる。ユーザーが指定したツールがあれば、ここの候補より優先する。

各節は次の項目で書いてある。

| 項目 | 使うフェーズ | 内容 |
|---|---|---|
| 語尾 | 0 | 基盤名の末尾（[intake.md](intake.md) の2章） |
| 聞くべき事項 | 0 | 後から変えにくく、指示に無ければ聞く事項 |
| 調べる先 | 2 | 公式情報の当たり先 |
| 検査の候補 | 2・4 | 使える検査ツール |
| 軸の読み替え | 3 | カタログの軸をこの分野でどう読むか。「対象外」は、その理由のまま「対象外とした軸」表に写す |
| 追加の軸 | 3 | 記号・名前・置く節。rules.md の「追加した軸」表にそのまま写す |
| 重点軸 | 3 | 特に揺れやすい軸 |
| 構造検査の典型 | 4 | 機械で縛る代表的な規則 |
| 参照実装の題材 | 4 | 見本として作る機能 |
| 収束テストの課題例 | 6 | 独立エージェントに解かせる課題 |

読み替えと追加の軸を表で固定しているのは、同じ分野の基盤を別々に作っても、ルールの構成とIDがそろうようにするためである。

## 目次

- frontend（Web フロントエンド）
- backend（API・サーバー）
- iac（インフラのコード化）
- data（データ基盤・分析・ML パイプライン）
- mobile（モバイルアプリ）
- cli-library（CLI・ライブラリ・SDK）
- docs（技術文書）
- 分野が複数にまたがる場合

## frontend

- **語尾**：`web`
- **聞くべき事項**：実行環境とパッケージマネージャ、レンダリングの方式（SPA か SSR か）、スタイルの方式、認証の方式、対応ブラウザ
- **調べる先**：UI ライブラリ・ルーター・データ取得・状態管理の公式ガイドと公式 examples。ルーターがファイルベースなら、ファイル名の規約がそのまま A2 と X1 の答えになる
- **検査の候補**：
  - 型：TypeScript の strict 設定
  - lint と format：oxlint・ESLint・Biome、oxfmt・Prettier・Biome
  - 境界：dependency-cruiser、eslint-plugin-boundaries
  - 未使用の export：knip
  - テスト：Vitest と Testing Library、MSW（HTTP のモック）
  - スタイル：Stylelint
- **軸の読み替え**：

  | 軸 | 読み方 |
  |---|---|
  | A7 | index.ts（barrel）を置くか、何を再 export してよいか |
  | E3 | 状態の種類ごとの置き場の決定表（サーバー状態、URL 状態、フォーム、画面をまたぐ UI 状態、ローカル状態） |
  | E4 | データ取得以外の非同期（イベントハンドラ、タイマー）の書き方 |

- **追加の軸**：

  | 軸 | 内容 | 置く節 |
  |---|---|---|
  | X1 | ルートファイルの書き方（ファイルベースルーティングで許される複数の書き方のうち、置き場・ファイル名・ネストの表し方を1つに絞る） | STR |
  | X2 | スタイルの書き方（方式、クラス名、デザイントークンの参照方法） | CODE |
  | X3 | アクセシビリティの定型（ラベル、ロール、フォーカスの扱い） | OPS |

- **重点軸**：A1、A5、B1〜B3、C3、D2、E2、E3、F1、X1
- **構造検査の典型**：
  - `features/<a>` から `features/<b>` への import を禁止する（a ≠ b。lint の import 制限だけでは a ≠ b を表せないことが多いので、構造検査で縛る）
  - API 呼び出しを書けるのは `api/` 配下だけにする
  - hooks のファイル名は `use-*.ts` にする
  - ルートファイルには、データ取得とレイアウトの組み立てだけを書く
- **参照実装の題材**：一覧と詳細の2画面。取得、URL の検索条件、作成フォームと更新、エラーとローディングの表示、テストまで含める
- **収束テストの課題例**：
  - 追加：新しい画面を足す（作成フォーム）
  - 変更：一覧に検索条件を足す（URL 状態）
  - 横断：2つの機能のデータを1画面に並べる

## backend

- **語尾**：`api`
- **聞くべき事項**：DB の種類、API の形式（REST、gRPC、GraphQL）、認証の方式、デプロイ先
- **調べる先**：言語の公式スタイル（Effective Go、PEP 8 など）、フレームワークの公式ガイド、DB ドライバ・マイグレーションツールの公式ドキュメント、OpenAPI・gRPC のスタイルガイド
- **検査の候補**：
  - 言語ごとの formatter と linter：gofmt と golangci-lint、ruff と mypy または pyright、ESLint・oxlint と tsc、Spotless と Checkstyle、rustfmt と clippy
  - 依存の境界：depguard、go-arch-lint、import-linter、ArchUnit
  - API 仕様の lint：Spectral、Redocly
  - SQL の lint：sqlfluff
- **軸の読み替え**：

  | 軸 | 読み方 |
  |---|---|
  | E3 | トランザクションとデータの流れ（どの層でトランザクションを開くか、読み取りと書き込みの分け方） |

- **追加の軸**：

  | 軸 | 内容 | 置く節 |
  |---|---|---|
  | X1 | API 仕様の書き方（仕様ファイルの置き場、コードとの同期方法：生成か手書きか） | PROC |
  | X2 | マイグレーション（ファイル名、可逆性、データ移行の扱い） | PROC |
  | X3 | ID と日時の型（UUID・ULID・連番のどれを使うか、時刻の型とタイムゾーン） | CODE |

- **重点軸**：B1、B5、C7、E1、E2、F3、G2、X1、X2
- **構造検査の典型**：
  - domain 層は外部パッケージを import しない
  - handler は repository を直接呼ばない
  - エラー型ごとに、HTTP 変換表の行がある
  - ルート定義と API 仕様の paths が一致する
- **参照実装の題材**：1つの集約（リソース）の作成・取得・更新・削除・一覧。トランザクション、エラーの変換、テストまで含める
- **収束テストの課題例**：
  - 追加：新しい集約の CRUD
  - 変更：既存の集約に項目を足す（マイグレーションと API 仕様に波及する）
  - 横断：別の集約を参照する処理と、外部サービスの呼び出し

## iac

- **語尾**：`infra`
- **聞くべき事項**：クラウドとアカウントの構成、state の保存先、環境の数、適用を実行する主体（CI か手元か）
- **調べる先**：Terraform・OpenTofu・Pulumi・CDK の公式スタイルガイドと module の構成規約、各クラウドのタグ付け・命名の推奨、Kubernetes の公式ベストプラクティス
- **検査の候補**：
  - 整形と検証：`terraform fmt`、`terraform validate`
  - lint：TFLint
  - セキュリティ：Trivy、Checkov
  - 独自ポリシー：Conftest（OPA）
  - Kubernetes：kube-linter、`helm lint`
- **軸の読み替え**：

  | 軸 | 読み方 |
  |---|---|
  | D1 | リソースを直接書くか、module を呼ぶか |
  | D2 | module の入出力（variables と outputs）の書き方 |
  | D3 | 変数の型と validation の書き方 |
  | D4 | `count`、`for_each`、`dynamic` の使い分け |
  | D5 | 対象外（宣言的に書くため。state の手動操作の禁止は H3 で扱う） |
  | E1 | `validation`・`precondition`・`postcondition` の使い分け |
  | E4 | 対象外（非同期の処理を書かないため） |
  | F1〜F4 | plan に対するテスト、ポリシーのテスト |

- **追加の軸**：

  | 軸 | 内容 | 置く節 |
  |---|---|---|
  | X1 | タグとラベル（必須のタグとその値の規則） | NAM |
  | X2 | state と環境の分け方（backend の構成、workspace を使うか、環境ディレクトリ） | STR |
  | X3 | 権限ポリシーの書き方（最小権限、ワイルドカードの禁止、ポリシーの置き場） | OPS |

- **重点軸**：A1、B1、B6、C1、C2、E6、E8、G1、X1〜X3
- **構造検査の典型**：
  - 必須のタグがある
  - リソース名が `<env>-<service>-<role>` の形になっている
  - provider のバージョンを固定している
  - 環境ディレクトリには module の呼び出しだけを書く
- **参照実装の題材**：1つのサービスを、ネットワーク、計算資源、権限、監視をそろえて1環境に置く module の呼び出し
- **収束テストの課題例**：
  - 追加：新しいサービスの module を足す
  - 変更：既存のサービスに環境を1つ足す
  - 横断：2つのサービスの間に通信の許可を足す

## data

- **語尾**：`data`
- **聞くべき事項**：本番の DWH、生データの入手元と更新頻度、seeds を使うか、Python のモデルを使うか（変換処理を SQL だけで書くか）
- **調べる先**：dbt・Airflow・Dagster などの公式ベストプラクティス、SQL のスタイルガイド、使う DWH の公式ドキュメント
- **検査の候補**：sqlfluff、dbt の project evaluator とテスト、ruff、nbQA（ノートブック）、Great Expectations・Soda（データ品質）
- **軸の読み替え**：

  | 軸 | 読み方 |
  |---|---|
  | A7 | 対象外（入口ファイルの仕組みが無いため） |
  | D1 | CTE の構成（import CTE、変換の CTE、最後の select の順） |
  | D2 | `ref` と `source` を呼んでよい場所（先頭の import CTE だけ、など） |
  | D3 | 列の型変換をする場所（staging だけで cast する、など） |
  | D5 | DML・hooks・post-hook による書き換えの禁止 |
  | E3 | 層ごとの materialization と incremental の扱い |
  | E4 | 対象外（非同期の処理を書かないため。Python のスクリプトがある場合は読み替えずに使う） |
  | F1〜F4 | データテスト（必須のテスト、テストの置き場、テストデータ） |

- **追加の軸**：

  | 軸 | 内容 | 置く節 |
  |---|---|---|
  | X1 | 粒度と主キー（各モデルの1行が何を表すかの書き方、主キーのテスト） | STR |
  | X2 | 取り込み元と形式（source の定義、生データの置き場と形式） | STR |
  | X3 | YAML の書き方（properties ファイルの単位、キーの順、必須の記述） | CODE |
  | X4 | Jinja とマクロの使用範囲 | CODE |

- **重点軸**：A1、B1、C1、C2、D1、D2、F1、X1、X3
- **構造検査の典型**：
  - mart から source を直接参照しない
  - モデル名の接頭辞が層と一致する
  - 主キーに、一意性と非 null のテストがある
  - YAML の設定を緩める記述が無い（複数行にまたがるので、guard ではなく構造検査で縛る）
- **参照実装の題材**：1つの取り込み元から、staging、中間、mart までの一連のモデルとテスト
- **収束テストの課題例**：
  - 追加：新しい取り込み元を足す
  - 変更：既存の mart に指標を足す
  - 横断：2つの取り込み元を結合した mart を作る

## mobile

- **語尾**：`app`
- **聞くべき事項**：対応する OS の最小の版、ネイティブかクロスプラットフォームか、配布の方法
- **調べる先**：Apple・Android・Flutter・React Native の公式アーキテクチャガイド
- **検査の候補**：SwiftLint と swift-format、ktlint・detekt と Konsist、`dart analyze`・`dart format` と custom_lint、ESLint・oxlint（React Native）
- **軸の読み替え**：

  | 軸 | 読み方 |
  |---|---|
  | E3 | 画面の状態の型と、状態を持つ層（ViewModel など） |

- **追加の軸**：

  | 軸 | 内容 | 置く節 |
  |---|---|---|
  | X1 | 画面遷移の書き方（ルートの定義、引数の渡し方） | STR |
  | X2 | リソース（文字列・画像・色）の置き場と参照方法 | CODE |
  | X3 | プラットフォームごとの差分の扱い | STR |

- **重点軸**：A1、B1、C3、E3、E7、X1
- **構造検査の典型**：
  - UI 層からデータ層を直接呼ばない
  - 画面ごとに状態型がある
  - 文字列をハードコードしない
- **参照実装の題材**：一覧と詳細の2画面に、取得とエラー表示、オフライン時の扱いを含める
- **収束テストの課題例**：
  - 追加：画面を足す
  - 変更：項目を足す
  - 横断：2つの機能をまたぐ画面遷移

## cli-library

- **語尾**：CLI なら `cli`、ライブラリ・SDK なら `lib`
- **聞くべき事項**：配布先（npm、PyPI、Homebrew など）、サポートする言語の版、ライセンス
- **調べる先**：言語の公式ライブラリ設計ガイド、セマンティックバージョニング、CLI の公式・定番ガイド（clig.dev など）
- **検査の候補**：API Extractor（TypeScript）、apidiff・gorelease（Go）、cargo-semver-checks（Rust）、ドキュメントコメントの lint
- **軸の読み替え**：

  | 軸 | 読み方 |
  |---|---|
  | E3 | CLI では設定ファイルと状態ファイルの置き場。ライブラリでは内部状態を持つか |

- **追加の軸**：

  | 軸 | 内容 | 置く節 |
  |---|---|---|
  | X1 | 終了コードと出力の形式（標準出力と標準エラーの使い分け、機械可読の出力） | OPS |
  | X2 | 公開 API の互換性（semver の上げ方、非推奨にする手順） | PROC |

- **重点軸**：B2、C2、C4、D7、E1、F1、G3、X1、X2
- **構造検査の典型**：
  - 公開 API の差分ファイルが更新されている
  - 公開されたすべての名前に、ドキュメントコメントがある
  - サブコマンドのファイル配置と命名がそろっている
- **参照実装の題材**：1つのサブコマンド、または1つの公開関数群。エラー、ヘルプ、テストまで含める
- **収束テストの課題例**：
  - 追加：サブコマンドを足す
  - 変更：オプションを足す
  - 横断：複数のサブコマンドで使う共通処理を足す

## docs

- **語尾**：`docs`
- **聞くべき事項**：公開先とビルドツール、対象読者、既存の文書ルール
- **調べる先**：組織の既存の文書ルール、使う文書基盤（Docusaurus、MkDocs など）の公式ガイド。日本語であれば JTF 日本語標準スタイルガイドなど
- **検査の候補**：markdownlint、textlint（日本語の表記ゆれは prh 辞書）、Vale、リンク切れの検査
- **軸の読み替え**：

  | 軸 | 読み方 |
  |---|---|
  | A1 | 文書の分類とディレクトリ |
  | A2 | 文書の種類ごとのひな形 |
  | B1 | 文書間のリンクの向き（概要から詳細へ、など） |
  | C1 | ファイル名 |
  | C4 | 用語の統一 |
  | D7 | 見出しの構成と front matter |
  | E7 | 表記（日付・数値・単位） |
  | F1 | 検査の対象（lint とリンク検査） |
  | B4〜B6、D1〜D6、D8、E1〜E6、E8、F2〜F5 | 対象外（コードを書かないため） |

- **追加の軸**：

  | 軸 | 内容 | 置く節 |
  |---|---|---|
  | X1 | 用語辞書（表記ゆれの正と誤の対応） | NAM |
  | X2 | 図とコード例の扱い（形式、置き場、更新の責任） | CODE |

- **重点軸**：A2、C1、C4、D7、E7、X1
- **構造検査の典型**：
  - 文書の種類ごとに、必須の見出しがそろっている
  - front matter に必須の項目がある
  - 用語辞書に反する表記が無い
- **参照実装の題材**：文書の種類ごとに1本の見本
- **収束テストの課題例**：
  - 追加：同じ仕様メモから文書を1本書く
  - 変更：既存の文書に節を足す
  - 横断：2つの文書を参照する手順書を書く

## 分野が複数にまたがる場合

フルスタックやモノレポのように複数の分野を含む場合は、分野ごとの節を全部読み、ルールIDの接頭辞は共通のままにする。

- 軸の読み替えが分野ごとに違う場合は、分野を書き分けた1つのルールにする
- 追加の軸は、分野の順（この文書の目次の順）に並べ、X1 から通しで振り直す
- 分野をまたぐ境界は、B 群の軸として決める。例として、API の型をフロントエンドとバックエンドで共有する方法（生成するのか、手で書くのか）がある

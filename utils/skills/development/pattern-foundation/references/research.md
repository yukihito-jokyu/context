# 調査：公式設計と最新版を出典付きで確かめる

フェーズ2で読む。目的は2つある。1つは、ルールを公式の推奨に沿わせて「エージェントが自然に書く形」と一致させること。もう1つは、記憶にある古いバージョン・設定キー・ルール名で基盤を作らないことである。

## 1. 調べる順序と情報源の優先度

情報源が食い違ったら、上のものを採用する。

1. ユーザーの指示
2. 公式ドキュメント（ガイド、API リファレンス、マイグレーションガイド）
3. 公式のテンプレート・examples・スターター（公式の「書き方」が最もよく表れる）
4. パッケージレジストリとリリースノート（バージョン、破壊的変更）
5. メンテナー本人の記事・講演
6. 広く使われるコミュニティのガイド（例：フロントエンドの bulletproof-react や Feature-Sliced Design）。公式に記述が無い軸を決めるときだけ使う

## 2. 技術ごとに確かめること

技術（ライブラリ、ツール、言語）ごとに次を確かめる。技術が3つ以上あるときは、技術ごとにサブエージェントへ並列で調べさせ、結果を3章の書式で返させると、速く漏れも少ない。

### 2.1 バージョン

先に実行環境（Node、Python、Go などのランタイム）の版を決め、その版で動くものの中の最新の安定版を、レジストリのコマンドで確かめる。記憶で書かない。

| 生態系 | コマンドの例 | 注意 |
|---|---|---|
| npm | `npm view <pkg> version`、`npm view <pkg> peerDependencies`、`npm view <pkg> time --json` | — |
| Python | `curl -s https://pypi.org/pypi/<pkg>/json` の `info.version` と `requires_python`、`pip index versions <pkg> --python-version <版> --only-binary=:all:`、`uv pip compile` | `--python-version` を付けない `pip index versions` は、手元の Python で入る版しか返さないため、古い版が最新に見える |
| Go | `go list -m -versions <module>`、`go list -m <module>@latest` | — |
| Rust | `cargo search <crate> --limit 1`、`cargo info <crate>` | — |
| Terraform | 各プロバイダのレジストリページ、`terraform version` | — |
| その他 | 公式のリリースページ | — |

採る版は次の順で決める。決めた理由は ADR に書く。

1. プレリリースは、ユーザーの指示が無い限り使わない
2. 名指しされた技術と必須の部品の対応範囲（peerDependencies、`requires_python`、公式の対応表）に入らない版は使わない。範囲内の最新にする
3. 最新の安定版が新しいメジャー版で、公開から90日未満であり、名指しされた技術の公式テンプレートがまだその版を使っていない場合は、1つ前のメジャー版の最新にする。出たばかりのメジャー版は、周辺の対応が追いついていないことが多いからである
4. 上のどれにも当たらなければ、最新の安定版にする

### 2.2 公式が推奨する構成

ディレクトリ構造、ファイル規約（ファイルベースルーティングの命名など）、推奨パターンと非推奨パターンを調べる。公式が同じことに複数の書き方を許している場合（例：ルートファイルの置き方が3通り許されている）は、その全部を記録する。フェーズ3で1つに絞る対象になる。

### 2.3 設定キーとルール名

使う型・lint・format の設定キーとルール名が実在するかを、ツール自身のコマンドで確かめる。存在しないルール名を書いても、黙って無視されるツールがあるためである。

依存を入れるのはフェーズ4だが、ルール名はフェーズ3で必要になる。そのため、この段階でツールを一時実行して、ルール一覧を取る。

- 一時実行の例：`npx <tool>@<版> ...`、`uvx <tool>==<版> ...`、`go run <module>@<版> ...`
- 一覧の取り方の例：ルール一覧を出すコマンド、設定を出力するコマンド、`--help`
- 一覧のコマンドが何も出さない場合は、JSON 出力のオプションを試す。端末でないと何も出さないツールがあるからである

### 2.4 抑止記法

ツールの抑止記法（lint 無効化コメント、型チェック無視コメント、テストの skip など）を調べ、`guard.suppressions` に入れる。

### 2.5 ツールにできないこと

import の境界検査、命名パターン、ファイル配置の検査など、ツールにできないことを調べる。できない部分は、フェーズ4で構造検査スクリプトやカスタムルールで補う。

## 3. 記録の書式（docs/design/research.md）

技術ごとに次の書式で書く。採用した推奨には必ず出典の URL を付ける。後でルールの理由を説明するときや、バージョンを上げるときに、どの情報に基づく判断かを辿れるようにするためである。

```markdown
## <技術名> <固定したバージョン>

- 確認方法：`npm view <pkg> version` → 1.2.3（YYYY-MM-DD）
- 確認の状態：確認済み
- 公式の推奨：
  - <推奨の要約>（[出典の見出し](URL)）
- 採用するもの：<ルールIDまたは ADR 番号。フェーズ3の後に埋める>
- 採用しないもの：<推奨のうち採らなかったものと、その理由>
- ツールにできないこと：<補う方法>
```

確認の状態は、次のどちらかを書く。

- `確認済み`：コマンドの結果か、取得した公式ページに基づく
- `未確認`：記憶に基づく

`未確認` の項目が残っていると、`rules_check.py --final` は通らない。

retrofit モードでは、冒頭に「現状」節を置き、既存の書き方の分布（[intake.md](intake.md) の5）を書く。

## 4. 完了条件

- manifest の `stack` と `tools` のすべてに、確認済みのバージョンがある
- フェーズ3で使うルール名を、ツールの一覧で確かめた
- フェーズ3で使う推奨に、出典がある
- ツールの抑止記法を `guard.suppressions` に入れた

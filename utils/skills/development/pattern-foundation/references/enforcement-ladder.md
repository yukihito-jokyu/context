# 強制の順位：ルールをどの仕組みで縛るか

フェーズ4で読む。ルールは、書いただけでは守られない。この文書の順位に従って、各ルールをできるだけ上の段の仕組みに載せる。載せた段は rules.md の**強制**に書き、`rules_check.py` がその対応を検査する。

## 目次

1. 段の一覧
2. 段の選び方
3. 証明：probe の書き方
4. 自動実行の配線
5. 抜け道を塞ぐ
6. ツールに無いルールを足す方法
7. 完了条件

## 1. 段の一覧

上ほど強い。rules.md の**強制**には、左端のキーワードを書く（複数可、カンマ区切り）。

| 段 | キーワード | 仕組み | 強さの理由 | probe |
|---|---|---|---|---|
| 1 | `type` | 型システム、可視性（internal、非公開）、コンパイラ | 違反がそもそも書けない | 必須 |
| 2 | `format` | formatter | 違反しても自動で直る。議論の余地が無い | 必須 |
| 3 | `lint` | linter の組み込みルール・プラグインルール | 違反を書くと検査が落ちる | 必須 |
| 3 | `structure` | 構造検査（依存の向き、配置、命名を、ファイルと import から検査するスクリプトやアーキテクチャテスト） | 同上 | 必須 |
| 3 | `test` | テスト（振る舞いの契約、公開 API の差分、スナップショット） | 同上 | 必須 |
| 4 | `generator` | 生成器・ひな形（新しい単位をコマンドで作る） | 正しい形から始まるが、後から崩せる | 不要（3段目か `review` と併用する） |
| 5 | `review` | レビュー用スキルの確認項目 | 人やエージェントの判断に頼る | 不要（レビュー用スキルの表の1列目に ID があることを検査） |
| 6 | `doc` | 文書だけ | 読まれなければ効かない | 不要（AGENTS.md か実装用スキルに ID があることを検査し、件数を報告して最小化する） |

1つのルールに複数のキーワードを書いた場合、`rules_check.py` は機械の段（`type`、`format`、`lint`、`structure`、`test`）のそれぞれについて、その段を証明する probe を求める。強制に `review` を含むルールはすべてレビュー用スキルの表に、`doc` を含むルールはすべて AGENTS.md か実装用スキルに書く。

機械の段を含まないルールには、**機械化しない理由**を必ず書く。「機械で判定できない（意味の判断が要る）」「判定ツールを作る費用が効果に見合わない」のどちらかになるはずである。理由が書けないなら、機械化できる見込みがある。

## 2. 段の選び方

ルールごとに、次の質問を上から順に当てる。

1. 型や可視性で、違反を書けなくできるか → `type`
2. formatter の設定で決まるか → `format`
3. 使うツールに、そのルールそのもの、または近いルールがあるか（フェーズ2で、ルール一覧のコマンドで確かめた名前だけを使う） → `lint`
4. ファイルパス・ファイル名・import 文・識別子の形といった**字面**で判定できるか → `structure`（6章の方法で作る）
5. 実行すれば判定できるか（戻り値、例外、公開 API の形） → `test`
6. ここまでで機械にできない。意味の判断が要る（命名が中身と合っているか、責務の分け方など） → `review`。新規追加の形が絡むなら `generator` も併用する
7. レビューでも判定が割れる → ルールの決定文を書き直す。判定が割れるルールは揺れを止めない

**字面で判定できるのに `review` に回さない。** たとえば「hooks は `use` で始まる」「`features/` 同士で import しない」「API 呼び出しは `api/` ディレクトリにだけ書く」は、どれも字面で判定できる。

**`review` と `doc` の分け方**：違反が差分に痕跡として残るなら `review`、残らないなら `doc` にする。たとえば「作る順序」「報告に書くこと」「作業の前に読むもの」は差分を見ても判定できないので `doc` である。

判断に迷いやすいものは、次のとおりに書く。

| 仕組み | キーワード |
|---|---|
| `guard.py`（抑止コメントの検出） | `structure` |
| lockfile とバージョン固定の検査（`npm ci`、`uv lock --check` など） | `structure` |
| 生成物が最新かの検査（再生成して差分が無いこと） | `structure` |
| 保護ファイルの変更の禁止 | `review`。機械化しない理由は「hooks はエージェントの編集にだけ確認を求め、人の編集は止められないため、差分のレビューで確かめる」 |
| 作業の順序、報告の中身 | `doc` |

## 3. 証明：probe の書き方

設定を書いても、ルール名の誤り、対象ファイルの漏れ、ignore 設定などで効いていないことがある。そこで、機械で縛るルール（段1〜3）には、違反例を **probe** として `.foundation/probes.json` に書く。`violation_probe.py` は、基盤の一時コピーに probe を1件ずつ入れて検査コマンドを回し、検査が**落ちること**と、出力に期待した文字列が含まれることを確かめる。元のディレクトリには触れない。

```json
{
  "probes": [
    {
      "id": "<ルールID>-a",
      "rule": "<ルールID>",
      "level": "<この probe が証明する段：type / format / lint / structure / test>",
      "description": "<どんな違反を入れるか>",
      "command": "<省略可。その段の検査だけを回すコマンド>",
      "files": [
        {"path": "<基盤のルートからの相対パス>", "mode": "create", "content": "<違反を含む内容>"}
      ],
      "expect": "<検査の出力に現れるはずの文字列の正規表現。ルールIDか lint のルール名>"
    }
  ]
}
```

- `level` は必須。複数の段で縛るルールは、段ごとに probe を書く
- 検査コマンドの既定は manifest の `commands.check` である。probe ごとの `command` で、その段の検査だけに絞れる。全件を回す時間が短くなる。絞った場合、`violation_probe.py` は、絞ったコマンドごとに代表の probe を1件、check 全体でも回し、その検査が check に組み込まれていることを確かめる（wiring）
- `mode` は `create`（新規作成。既にあれば失敗）、`replace`（既存ファイルを丸ごと置き換え）、`append`（既存ファイルの末尾に追加）のどれか。`replace` と `append` は参照実装のファイルを前提にするので、参照実装を作った後（フェーズ4）に書く
- `expect` は正規表現である。検査の出力（標準出力と標準エラー）に一致しなければ、probe は失敗になる。たまたま別の理由で落ちたのを、合格と取り違えないためである
- probe は、**対象のルールだけを破り、ほかのルールはすべて守る**内容にする。ほかのルールも破ると、check の前の段で先に落ち、目的の段まで届かないからである
- 依存の一覧ファイルや検査の設定ファイル（package.json など）を `replace` すると、検査コマンドそのものが変わることがある。置き換える場合は、元の内容を写して必要な箇所だけを変え、その probe の `command` には検査のスクリプトを直接書く
- probe は「実際に書かれがちな違反」にする。収束テストで見つかった違反は probe に足す
- 1つのルールに抜け道が複数あるなら、probe も複数書く（`<ルールID>-a`、`<ルールID>-b`）

最初に、何も入れない状態で検査が**通ること**を確かめる（baseline）。baseline が落ちる状態では、probe が落ちても何も証明しないからである。

## 4. 自動実行の配線

機械の検査は、走らなければ効かない。次の3か所で必ず走るように配線する。

| タイミング | 回すもの | 仕組み |
|---|---|---|
| 編集の直後 | そのファイルの format と lint（数秒で終わるもの） | `.claude/settings.json` の PostToolUse hook → `hooks.py post-edit`。対象と実行コマンドは manifest の `hooks.post_edit` に書く |
| 完了の前 | 全検査 | check コマンド（manifest の `commands.check`）。format は `--check` 系にして、check がファイルを書き換えないようにする |
| 共有の前 | 全検査 | CI や pre-commit。ユーザーが求めた場合か、リポジトリに既に仕組みがある場合に足す |

check コマンドには、次の5つを必ず含める。

- formatter の確認（書き換えない形）
- linter
- 型検査
- 構造検査とテスト
- `python3 .foundation/bin/guard.py --root .` と `python3 .foundation/bin/rules_check.py --root . --no-write`（`--no-write` は対応表を書き換えず、最新でなければ落ちる。`--phase` を省くと、manifest の status が building の間はフェーズ4、ready になるとフェーズ5の範囲を検査する）

自動修正は別のコマンド（manifest の `commands.fix`）にする。

スクリプトの生成物と入力（`docs/design/enforcement-matrix.md` と `.foundation/**`）は、formatter と linter の対象から外す（各ツールの ignore の設定に書く）。formatter が対応表の空白をそろえると、`rules_check.py --no-write` が「最新ではない」で落ちる。`fix` で直すと対応表が書き換わり、check を回すとまた落ちる、という往復が止まらなくなるからである。`probes.json` が整形されると、そのハッシュが変わって probe の結果も「古い」扱いになる。

## 5. 抜け道を塞ぐ

| 抜け道 | 塞ぎ方 |
|---|---|
| 抑止コメント（lint 無効化、型無視、カバレッジ除外） | `guard.py`。禁止パターンを manifest の `guard.suppressions` に `{"pattern", "rule"}` の形で書く。`rule` には、そのパターンを禁じたルールIDを書く（`rules_check.py` が実在を検査する）。どうしても必要な例外は `guard.allow` に理由付きで書く。`guard.py` は1行ずつ照合するので、複数行にまたがる緩和（YAML で次の行に書く設定など）は構造検査で縛る |
| 設定の緩和（ルールを off にする、ignore に足す、型の strict を外す） | manifest の `protected` に設定ファイルを入れる。PreToolUse hook（`hooks.py pre-edit`）が、エージェントがそれらを編集する前にユーザーへ確認を求める。レビュー用スキルも、保護ファイルの差分を必ず指摘する |
| テストの skip・only・削除 | linter に該当ルールがあればそれを使い、無ければ `guard.suppressions` にパターンを足す（例：`\.only\(`、`\.skip\(`、`t\.Skip\(`、`@pytest\.mark\.skip`） |
| 生成物の手編集 | 生成物に「生成物・編集しない」のヘッダーを付け、check で再生成して差分が無いことを確かめる |
| 依存の勝手な追加 | 依存の一覧ファイル（package.json、go.mod など）を `protected` に入れる |

## 6. ツールに無いルールを足す方法

使うツールに無いルールは、次の順に検討する。

1. **同じツールの別ルールや設定の組み合わせ**で表せないか（例：import の制限ルールにパターンを列挙する）
2. **ツールのプラグイン機構**（独自ルールを書ける仕組み）があり、それが安定版の機能か。フェーズ2で確かめたものだけを使う
3. **構造検査スクリプト**を、基盤の主言語で書く。最も確実で、どの分野でも使える

構造検査スクリプトは次のように作る。

- 置き場は `scripts/` か、分野の慣習に合う場所。check コマンドから呼ぶ
- 規則はコードの中に**表**として書く（例：依存の許可表、置き場所と命名パターンの表）。`architecture.md` の表と1対1で対応させ、どちらかを変えたらもう一方も変える
- エラーは `<ルールID> <パス>:<行> <説明>` の形で出し、終了コード1で終わる。ルールIDを出すのは、probe の `expect` とレビュー指摘とで同じ ID を辿れるようにするため
- ネットワークに触れず、同じ入力なら同じ結果を出し、数秒で終わるようにする

依存の境界を検査するツールの候補（存在と最新の使い方はフェーズ2で必ず確かめる）：dependency-cruiser、eslint-plugin-boundaries（JavaScript/TypeScript）、import-linter（Python）、depguard、go-arch-lint（Go）、ArchUnit（Java）、Konsist（Kotlin）。

## 7. 完了条件

- 全ルールの**強制**にキーワードがある
- `review` と `doc` のルールに**機械化しない理由**がある
- 機械の段を含むルールすべてに、段ごとの probe があり、`violation_probe.py` が全件「成功」（検査で落ちた）と報告し、組み込みの確認（wiring）も成功する
- `guard.py` が通る
- formatter と linter の ignore に生成物と `.foundation/**` が入っており、`fix` を回した直後にも check が通る
- `rules_check.py --phase 4` が通り、`docs/design/enforcement-matrix.md` が生成されている

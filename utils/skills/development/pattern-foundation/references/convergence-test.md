# 収束テスト：独立エージェントで揺れを測り、締め込む

フェーズ6で読む。ルールを書いた本人には行間が見えているため、ルールが十分かどうかを自分では判定できない。そこで、**この会話の履歴を持たない独立エージェント**に同じ課題を解かせ、出力の違いを測る。違いが残っていれば、その原因を突き止めてルールや仕組みを足し、もう一度測る。

## 目次

1. 全体の手順
2. 課題の作り方
3. 独立エージェントの起動
4. 計測
5. 原因の分類と対処
6. レビュー用スキルの検出率
7. 合格基準と打ち切り
8. 記録

## 1. 全体の手順

```
ラウンド R（1 から始める。上限は manifest の convergence.max_rounds）
  1. 課題を用意する（初回のみ。ホールドアウト課題は最終ラウンドまで使わない）
  2. prepare：課題ごとに、基盤のコピーをエージェントの人数分作る
  3. run：各コピーで独立エージェントに課題を解かせる
  4. diff：コピー同士を比べて揺れを計測し、レポートを出す
  5. レポートの揺れを1件ずつ原因に分類し、基盤を直す
  6. 基盤の check、probe、rules_check を通す
  7. 次のラウンドを決める（下の表）
```

「最終ラウンド」は、ホールドアウト課題を加え（`prepare --include-holdout`）、レビュー検出率（6章）も測るラウンドである。上限の回数に含める。

| 状況 | 次にすること |
|---|---|
| ラウンド R が最終ラウンドではなく、合格基準を満たした | R+1 を最終ラウンドにする |
| ラウンド R が基準を満たさず、R+1 が上限 | R+1 を最終ラウンドにする |
| ラウンド R が基準を満たさず、R+1 が上限より前 | R+1 を通常のラウンドにする |
| 最終ラウンドで基準を満たした | 終える（8章の記録へ） |
| 最終ラウンドで基準を満たさず、R が上限より前 | 直して、R+1 を再び最終ラウンドにする。ホールドアウト課題は既に見た課題になったことを記録に書く |
| R が上限に達した | 打ち切る（7章） |

既定値は、エージェント3人、課題3つ（追加・変更・横断）、ホールドアウト1つ、上限3ラウンドである。manifest の `convergence` で変えられる。1ラウンドのセッション数は「課題数 × 人数」になる。始める前に、この回数をユーザーに伝える。

## 2. 課題の作り方

課題は `<root>/.foundation/convergence/tasks.json` に書く。

```json
{
  "tasks": [
    {"id": "T1-add", "kind": "add", "prompt": "..."},
    {"id": "T2-change", "kind": "change", "prompt": "..."},
    {"id": "T3-cross", "kind": "cross", "prompt": "..."},
    {"id": "H1-holdout", "kind": "holdout", "prompt": "..."}
  ]
}
```

| 種類 | 何を測るか | 材料 |
|---|---|---|
| `add` | 最も頻繁な「新しい単位を足す」作業の揺れ | 振り分け表で最も使われるパターン |
| `change` | 既存コードの変更が局所に収まるか、波及の対応表が守られるか | architecture.md の変更シナリオ表 |
| `cross` | 機能・層をまたぐ処理で、境界のルールが守られるか | 依存の許可表で禁止された近道が誘惑になる題材 |
| `holdout` | 締め込みが課題への過剰適合になっていないか | 上の3つと違うパターン。締め込みの途中では使わず、最終ラウンドで初めて使う |

課題文の書き方：

- **実際のユーザーが言いそうな依頼文**にする。ルール、ファイルパス、関数名、使うスキルを書かない。それらを自力で見つけられるかも測定の対象だからである
- 業務上の事実（項目名、上限値、画面の文言など）のうち、実装に必要で基盤からは決まらないものは書く。書かないと、揺れの原因が基盤なのか課題なのか区別できない
- ただし、実装用スキルの「決まらない値の表」にあるものは、あえて書かない課題を1つ混ぜる。既定値表が機能するかを測るためである
- 規模は、3〜10ファイルを触り、1人のエージェントが30分以内で終わる程度にする

## 3. 独立エージェントの起動

独立性の条件は3つある。

- この会話の履歴を持たない
- 他のエージェントの出力を見ない
- 課題文以外のヒントを受け取らない

そのため、エージェントごとに基盤のコピーを作り、そこで1つのセッションを起動する。

### 準備

```bash
python3 <root>/.foundation/bin/convergence.py prepare --root <root> --round <R> [--include-holdout] [--workdir <W>]
```

- 作業用ディレクトリ `<W>` の既定は、OS の一時ディレクトリの下の `pattern-foundation/<name>/` である。基盤の中に置かないのは、linter やテストがコピーまで読みに行くのを防ぐためである。セッションにスクラッチパッドがあれば、そこを指定する
- コピーには、依存のディレクトリ（`node_modules`、`.venv` など）をシンボリックリンクで張る。ビルド成果物やキャッシュはコピーしない。git があれば、各コピーで `git init` して基準のコミットを作る。エージェントが `git diff` で自分の変更を確かめられるようにするためである
- `.foundation/convergence/`（前のラウンドの差分、課題一覧、レビューの正解表）と `.foundation/probe-results.json` はコピーしない。前のラウンドの答えや他の課題がエージェントに見えると独立性が崩れ、前のラウンドの識別子が「既存の名前」に数えられて names 指標も水増しされるからである
- 依存のディレクトリはリンクなので、元の基盤と全コピーで共有される。runner の `--allowedTools` に、依存を追加・更新するコマンドを入れない
- `<W>/round-<R>/plan.json` に、実行の一覧（課題、エージェント、ディレクトリ、プロンプト）が書かれる

### 実行（既定：`claude -p`）

```bash
python3 <root>/.foundation/bin/convergence.py run --workdir <W> --round <R> [--parallel 3] [--timeout 1800]
```

1ラウンドには最長で「課題数 × 人数 ÷ 並列数 × timeout」の時間がかかる（既定で最長90分）。Bash ツールの前景の実行は時間の上限（最大10分）で打ち切られるので、`run` はバックグラウンドで実行して終了の通知を待つ。分けて回したい場合は、`--only <実行ID,…>` で実行を選べる。

manifest の `convergence.runner` のコマンドを、各コピーを作業ディレクトリにして実行する。`{prompt}` は課題文に置き換わる。`claude -p` は、起動したディレクトリの CLAUDE.md（`@AGENTS.md` の読み込みを含む）、`.claude/skills`、`.claude/settings.json` の hooks を自動で読む。これは、新しい開発者がこのリポジトリで Claude Code を起動したときと同じ条件である。runner の注意点は次のとおり。

- `--permission-mode acceptEdits` と `--allowedTools` で、編集と検査コマンドだけを許可する。画面の無い実行では確認が出せないため、許可されていない操作は拒否される。保護ファイルの編集は、PreToolUse hook によって拒否される
- ユーザー単位の設定（`~/.claude/CLAUDE.md` など）も読み込まれる。実際の開発者の条件に近いが、結果を左右した可能性があれば記録に書く
- 結果は `<W>/round-<R>/_results/<実行ID>.json` に保存される

### 実行（代替：Agent ツール）

`claude -p` が使えない環境では、`plan.json` の各実行について、Agent ツールのサブエージェントを**1つのメッセージでまとめて**起動する。プロンプトは `plan.json` の `agent_tool_prompt` をそのまま使う。サブエージェントは別のディレクトリの CLAUDE.md を自動では読まないため、このプロンプトには次の2つが含まれている。

- 「コピーの CLAUDE.md を読み、その指示に従って作業する」という一文
- 「そのディレクトリの外を読み書きしない」という制約

この方法では、コピー側の hooks（保護ファイルの確認、編集後の検査）とスキルの自動読み込みが働かない。そのため、保護ファイルを変えて検査を通すことを止められない。diff は、どの実行方法でも保護ファイル（manifest の `protected`）を変えたエージェントを報告し、その課題を基準を満たさない扱いにする。この方法で実行したことを、記録に書く。

## 4. 計測

```bash
python3 <root>/.foundation/bin/convergence.py diff --workdir <W> --round <R> --out <root>/.foundation/convergence/round-<R> --check
```

課題ごとに、エージェント同士を総当たりで比べる。

| 指標 | 意味 | 計算 |
|---|---|---|
| `files` | 作った・変えたファイルの集合が同じか | ファイルパスの集合の Jaccard 係数（共通部分 ÷ 和集合）の平均 |
| `names` | 新しく作った名前（基盤に無かった識別子）が同じか | 新しい識別子の集合の Jaccard 係数の平均 |
| `content` | 同じファイルの中身がどれだけ近いか | 共通して変えたファイルの、行単位の類似度の平均 |
| `check` | 各エージェントの出力が check を通るか | `--check` を付けたとき、各コピーで `commands.check` を実行した結果 |

レポート（`report.md`）には、指標のほかに次を載せる。

- 一部のエージェントだけが作ったファイル
- 一部のエージェントだけが作った名前
- 類似度が低いファイルの差分の抜粋
- 保護ファイルを変えたエージェント（変えた場合、その課題は基準を満たさない）

これが、次の分類の材料になる。各エージェントの変更は `<実行ID>.patch` として保存される。

変更ファイルは、各コピーの `git status`（`.gitignore` を反映したもの）で判定する。エージェントが検査を回したときにできるキャッシュなど、`.gitignore` に無い生成物が揺れとして出た場合は、manifest の `convergence.ignore` に glob を足して計測から除く。ただし、本来 `.gitignore` に入れるべきものなら、基盤の `.gitignore` を直す方を選ぶ。

## 5. 原因の分類と対処

レポートの揺れを1件ずつ、次のどれかに分類する。分類せずに次のラウンドへ進まない。原因が分からないまま直すと、効かないルールが増えるだけだからである。

| 分類 | 状況 | 対処 |
|---|---|---|
| R1 軸が決まっていない | その点について、ルールが何も言っていない | [variance-axes.md](variance-axes.md) でその軸を決め、ルールを足す |
| R2 ルールがあいまい | ルールはあるが、エージェントごとに読み方が違った | 決定の文を書き直し、揺れた実例を悪い例として足す。条件があるなら決定表にする |
| R3 強制が無い | ルールは明確だが破られ、検査も通ってしまった | [enforcement-ladder.md](enforcement-ladder.md) で上の段に移し、その違反を probe に足す |
| R4 道筋が無い | エージェントがルールやスキルに辿り着かなかった（スキルを使わなかった、該当節を読まなかった） | AGENTS.md の案内、実装用スキルの description と振り分け表、読むファイルの列挙を直す |
| R5 見本が無い | 該当するパターンの見本が無く、各自が発明した | 参照実装、patterns.md、生成器を足す |
| R6 依頼が足りない | 業務上の判断が課題文に無く、基盤でも決まらない | 一般に起きる判断なら、実装用スキルの既定値表に足す。この課題に固有なら、課題文を直す |
| R7 害の無い揺れ | 保守性に影響しない違い（テストデータの具体的な値など） | 受け入れて記録する。ただし、R1〜R6 で止められないか先に検討する |

あわせて、AGENTS.md の「守ること」を見直し、このラウンドで揺れたルールを入れる（[agent-surface.md](agent-surface.md) の2章）。

直したら、次の4つが通ることを確かめてから次のラウンドへ進む。

- check
- `violation_probe.py`
- `rules_check.py`
- 直した内容が参照実装と食い違っていないこと

## 6. レビュー用スキルの検出率

最終ラウンドで、レビュー用スキルが違反を見逃さないか、判定がエージェントごとに揺れないかを測る。違反を仕込んだ差分を独立エージェントにレビューさせ、出力に含まれるルールIDを数える。

1. `<root>/.foundation/convergence/review-seeds.json` に、仕込む違反を probe と同じ書式で書く。対象は、強制に `review` を含むルール全部と、ファイルをまたぐ対応の破れ、抜け道（保護ファイルの変更、抑止コメント）である。1件の seed には1つの違反だけを入れ、`rule` にその ID を書く。複数の seed で同じファイルを作成・置換しない（後の seed が前の違反を消すため、review-prepare が止める）
2. 準備と実行
   ```bash
   python3 <root>/.foundation/bin/convergence.py review-prepare --root <root> --round <R> [--workdir <W>]
   python3 <root>/.foundation/bin/convergence.py run --workdir <W> --round <R> --kind review
   python3 <root>/.foundation/bin/convergence.py review-score --workdir <W> --round <R> --out <root>/.foundation/convergence/round-<R>
   ```
   review-prepare は、基準のコミットの上に seed を未コミットの変更として置く。プロンプトは「未コミットの変更をレビューして」という依頼文だけにする
3. 採点結果のうち、次の3つを見る
   - 検出率：seed のルールIDのうち、出力に現れた割合
   - 余計な指摘：seed に無いルールIDが出力に現れたもの
   - エージェント間の一致：検出したルールIDの集合が、エージェント同士で同じか

見逃しは R2（確認方法があいまい）か R4（確認項目に載っていない）として扱い、レビュー用スキルを直す。

## 7. 合格基準と打ち切り

既定の合格基準は次のとおり。manifest の `convergence.thresholds` で変えられる。数値は傾向を見るための目安であり、最終的には「R1〜R6 の未対処が0件」で判断する。

- 全エージェントの出力が check を通る
- 全課題で `files` が 1.0（作るファイルの集合が完全に一致する）。ただし R7 と分類したものは除く
- 全課題で `names` が 0.8 以上
- 残った揺れがすべて R7 に分類され、R1〜R6 の未対処が0件
- ホールドアウト課題でも上の4つを満たす
- レビュー検出率が全エージェントで 100%

`names` は、変えたファイルの中の英字の語をすべて識別子として数える。英語の文章を書く分野（技術文書など）では語彙の一致率に近くなるので、分野に合わせて `thresholds.names` を見直し、変えた理由を記録に書く。

上限ラウンドに達しても満たせない場合は、そこで止める。残った揺れを分類付きで報告し、ルールを足し続けるかをユーザーに判断してもらう。ルールを増やすほど覚えることが増えるという費用があるからである。

## 8. 記録

`docs/design/convergence-report.md` に、ひな形の書式でラウンドごとに次を書く。

- 指標
- 揺れの一覧と分類
- 行った対処（足したルールID、probe、スキルの変更）
- 実行方法（runner の種類）

`.foundation/convergence/round-<R>/` の report と patch は、記録の根拠として残す。

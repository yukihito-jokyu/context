# LLM Eval：信頼できる評価基盤を作る

## 目的・適用条件
- 対象は **1つの機能・ユースケース**。例：問い合わせ分類、コード修正、RAG回答、Agentによるファイル更新。
- 「どちらのモデルがよいか」を決める**前**に、その判断に使える評価を作る。
- 既存の評価がある場合は置き換える前に監査し、使えるケース・grader・runnerを再利用する。
- Skillsも対象にできる。発動の適切さ、手順の遂行、成果物の品質を分け、文書の静的監査と実際に使わせた評価を区別する。
- 評価の反復最適化は `llm-hillclimb` の責務。ここでは妥当なbaselineまで作る。

## 開始時に確認すること
1. 対象の入力→実装入口→出力を特定する。プロンプトだけではなく、リトライ、検索、ツール、履歴組み立てを通る**実際の処理**を対象にする。
2. 1ケースに必要な情報を明示する。ユーザー文だけか、ファイル・画像・プロフィール・会話履歴・作業環境を含むか。
3. 品質基準と失敗コストを確認する。正解率、制約遵守、安全性、遅延、費用などを区別する。
4. 入力の出自（実運用ログ/バグ/人手/合成）と個人情報・保持制限を確認する。機密情報を無断でコピーしない。
5. 既存evalの有無を調べ、実行可能か少数ケースで検証する。

## 実行手順
1. **ケースを用意する**：実運用を代表する正常系、境界、失敗例、難例を含める。合成例は現実のケースに基づく。重複、カテゴリ偏り、欠損を確認する。
2. **入力の確認用HTMLを作る**：ケース一覧の実文面・出典・想定結果・根拠と、代表性・不足を確認する欄を用意する。ケース別に「未確認/妥当/要修正」と理由を記録できるようにする。
3. **graderを選ぶ**：型・正規表現・厳密な構造・ユニットテスト・状態検査で判断できるものは決定的に採点する。自然文の質は明示rubricと人間で校正したjudgeを使う。agentの変更結果は会話上の自己申告ではなく**実行後の環境状態**で検査する。
4. **ケースとgraderをHTMLですり合わせる**：成功・部分点・失敗の実例、採点器の校正結果、評価の限界、回数・費用を同じHTMLに提示する。採点器が正解と不正解を判別できることと、評価基準が実際の仕事を測れていることを区別する。修正を反映し、対象版のケース・採点基準・実行範囲への利用者の明示的な合意を確認してから評価実行へ進む。詳細は [HTMLでのすり合わせ](references/html-review.md)。既に同じ範囲への合意があれば再利用する。
5. **runnerを作る**：本番入口をテスト用権限・隔離環境で呼ぶ。cases・反復番号・モデル実ID・usage・grade・latency・traceを記録する。失敗APIと切れた出力を品質0点に混ぜない。仕様は [データ契約](references/data-contract.md)。
6. **監査する**：[品質監査](references/audit-checklist.md) をケース・実装・grader・計測・検出力に適用する。特に、正解基準がモデルから見えないこと、baselineの再計算、環境独立性を確認する。
7. **まず少数で検証する**：実行結果のフィールドが埋まるか、traceと原文から採点を追えるか確認する。コストの発生する評価は回数・費用を見積もり、承認の範囲内で実行する。
8. **結果をHTMLですり合わせる**：期待結果・実出力・採点根拠をケース単位で提示し、結果への異議・追加確認・再評価希望を記録できるようにする。全体とケース別の点数推移をグラフで示し、エラー、反復のばらつき、品質/コスト/レイテンシーと判断上の制約を併記する。確認内容を保存・コピーできるようにし、フィードバックを反映した判断を残す。

## HTMLの生成
同梱の `assets/review.html` を `scripts/build_review.py` で組み立てる。入力契約と実行例は [HTMLでのすり合わせ](references/html-review.md) を参照。テンプレートは基準・結果確認、点数推移、保存・コピー・読込を含む。runnerやgraderの実行は行わない。

## 出力物
- `eval-plan.md`：対象、入力出典、守る品質、採点ルール、確認済み事項。
- `cases.jsonl` または既存形式のケースデータ。
- `runner` と `grader`（言語・テストフレームワークは既存コードに合わせる）。
- `baseline/results.jsonl` とケース別の実行ログ。失敗試行は別ファイル。
- `review.html`：評価前のケース・採点基準のすり合わせ、評価後の結果確認、点数推移のグラフ。段階ごとに更新してよい。
- `evaluation-review.json` または既存形式：対象版、確認者、合意内容、ケース別コメント、結果への判断。HTMLから保存・コピーできるようにする。
- `report.html`（`review.html`と兼用可）：スコア、変動幅、採点根拠、不確実性、再実行方法。必要ならMarkdownも併記する。

## 必須の注意
- **テストが存在すること ≠ 評価が正しいこと**。ケース・grader・runnerのバグで改善が逆転する。
- モデルの応答不完了、API失敗、judge失敗はモデルの不正解とは区別する。
- モデルに正答ファイルをマウントしない。作業副作用があるAgentは必ず隔離する。
- 初期の少数例から精密な優劣を断定しない。差がノイズ以内なら保留する。
- 「試してほしい」という依頼だけで、AIが作ったケース・採点基準まで合意済みと扱わない。未合意の動作確認が必要なら目的と範囲への明示的な許可を得て、正式評価と区別する。後からの合意で過去の実行を事前承認済みに変更しない。
- HTML上のボタンや読み込んだJSONだけで人間の承認を確定しない。利用者が共有した確認内容または会話上の明示的な合意を対象版に紐付ける。基準変更時は合意を再確認し、過去の点数は上書きしない。

## 出典と改変境界
Anthropic `shared/evals/build-eval.md` と `shared/evals/eval-audit.md` の評価設計原則を汎用化したもの。Claude固有のモデル名・`AskUserQuestion`・ディレクトリの固定規約・Node runnerのAPIは移植していない。元のレポートschemaを使う場合は原本を確認する。

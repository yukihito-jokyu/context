# HTMLでの評価基準・結果のすり合わせ

## 評価実行前
単体で開けるHTMLに、目的、対象の実行経路、ケースの実文面・出典・期待結果・根拠、採点項目と配点、成功・部分点・失敗の例、代表性と未検証事項、実行回数・費用を載せる。モデルjudgeを使う場合は、人の評価との校正状況も示す。

ケースごとに「未確認/妥当/要修正」とコメントを記録し、ケース集合の代表性・不足も確認できるようにする。AIがケース・正答・採点器を作った場合、その事実と独立検証の有無を明示する。

全ケースの確認と採点基準への合意を得てから対象の評価を実行する。採点器の既知正解・不正解による校正は先に進めてよいが、それだけで評価の妥当性を保証したとしない。ケース、期待結果、採点方法・配点・集計、実行範囲を変更したら対象版を更新し、影響する合意を再確認する。

## 評価実行後
ケース別に入力、期待結果、実出力または環境状態、得点と採点根拠、反復番号、実行状態、マスク済みtraceへの参照を示す。採点への異議、追加確認、基準修正、再評価希望を記録できるようにする。評価基準への合意と結果に対する判断は分けて保存する。

予定ケース数、採点ケース数、除外・欠測・実行エラー数、反復回数、集計方法と未検証事項を説明する。合格率だけでSkillの品質や改善効果を断定しない。Skillなしとの比較がない場合は因果効果を主張しない。

## 点数推移のグラフ
- 保存済みの実測だけを使い、全体とケース別の指標を選べるようにする。1回しかなければ1点のみを描き、推移は判断できないと説明する。
- 横軸は実行日時または記録した実行順、縦軸は点数と範囲を明示する。0〜1から100点へ換算した場合は式を示す。ケース平均・試行平均などの集計方法を明記する。
- ケース集合・採点基準・指標の版が違う結果を同一の改善曲線としてつながない。別系列または別パネルに分ける。
- エラー・未完了・欠測を0点にしない。反復がある場合はばらつきや区間推定、反復数・対応比較の対象数を示す。算出不能な場合は制約を記す。
- 元データの表も残し、グラフから実行を特定できるようにする。基準修正後の再採点は新しい記録として保存し、旧点数を上書きしない。

## 保存・コピーと合意の記録
HTMLに「確認内容を保存」「確認内容をコピー」を設け、両方で同じ構造化データを出力する。ケース・採点基準の版、確認者、確認日時、ケース別判断と理由、代表性へのコメント、合意範囲、実行IDごとの結果への判断を含める。コピー内容は会話に貼り付けて扱える形式にする。

コピーAPIが使えなければ、読み取り専用のテキスト欄に内容を表示して選択し、手動コピーの方法を案内する。成功通知はコピー完了後に出す。「要修正」の理由など必須内容が欠けていれば保存・コピー時に説明する。未合意の途中経過は保存できるようにし、保存を合意と扱わない。

メモリ内だけの状態は、ページを閉じると消えることを案内する。保存した記録の読込時は対象版との一致と形式を検証し、別の基準・結果へ誤って合意を適用しない。ブラウザ上の記録は自己申告であり、認証された承認ではない。利用者が会話で共有した記録・合意と照合し、事前に合意した実行範囲を評価計画へ記録する。

## 実装と確認
同梱の `assets/review.html` は、そのまま開いて操作できるオフラインのテンプレート。初期表示には架空の2ケースと3回分の点数推移を入れ、すべてサンプルと表示する。`scripts/build_review.py` はJSONから単体HTMLを生成する。既存のHTML基盤があれば本仕様を満たす形で再利用できる。

scripts/report.pyは保存済み結果の集計表を作る補助であり、確認フォーム、合意管理、推移グラフ、区間推定は実装していない。これだけで確認用HTMLが完成したとしない。

保存とコピーの内容一致、コピー失敗時の代替、記録の再読込、未確認時の合意防止、基準編集後の合意解除を検証する。グラフと元データを照合し、表示できる環境ではライト・ダークと狭い画面も確認する。表示確認ができなければ制約を報告する。

## 同梱テンプレートの使い方
スキルのディレクトリを起点に、次のコマンドで未実行の確認用HTMLを生成する。

```sh
python3 scripts/build_review.py --data assets/example-review-data.json --output /tmp/eval-review.html
```

直接開いたテンプレートの見本データは、生成時に `review-data` のJSONブロック全体を実際のデータへ差し替える。データ未置換でも表示切替・全タブ・保存・コピーが動くことを検証する。

実際の利用では例を作業ディレクトリへコピーし、対象のケースと評価計画に置き換える。例の期待値は架空の案であり、そのまま正答や合意済み基準にしない。入力JSONは以下を持つ。

- title、description、basis（ケース集合・採点基準・集計方法の版）、plan（実行計画）、limitations（制約の文字列配列）。
- cases: id、label、input、expected、basis（期待値の根拠）、rule（採点方法）。idは英数字・ハイフン・アンダースコアで、overallは予約語。
- runs: 評価前は空配列。保存済みの実測結果を記録順に追加する。各実行はid、basis、purpose（evaluation/exploratory）、errors（別ファイル等の実行エラー件数）、detailsを持つ。evaluationには、事前に利用者が合意した記録を示すapproval_refが必要。参照の文字列だけで承認が認証されるわけではない。
- details: case_id、rep（0始まり）、status（ok/refusal/truncated/error）、actual（実出力または最終状態）、score（0〜1の正規化点数、未採点はnull）、reason（採点根拠）。truncated/errorに点数を付けない。errorsはdetails内のerrorとは別の試行として記録し、二重計上しない。
- 過去実行のbasisが現在と違う場合、その実行時のcasesをスナップショットとしてrunに含める。期待値を現在のものへ差し替えない。同じbasisでcasesが違う入力は拒否される。

点数はdetailsから再集計し、ケース内の反復平均をケース間で等重み平均した値を100倍する。case_id/repの重複を拒否し、欠測は0点にしない。basisまたはケース内容が違う実行は線で結ばない。元指標が0〜1以外の場合は正規化方法をplanに記録する。

この軽量テンプレートは区間推定を計算しない。必要なばらつき・誤差区間は別途計算してplanやlimitationsに明示するか、テンプレートを拡張する。確認記録のfingerprintは基準と結果を含むため、新しい実行を追加すると古い確認JSONは直接読み込めなくなる。既存の合意は評価計画へ参照として保持し、確認記録を黙って書き換えない。

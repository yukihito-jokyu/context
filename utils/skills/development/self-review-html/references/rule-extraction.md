# ルール抽出

ユーザーが明示したスキルとルールファイルだけを読む。インストール済みスキルの自動探索や、指定外ファイルの暗黙的な追加を行わない。

## 抽出手順

1. 指定パスを絶対パスへ解決する。
2. スキルディレクトリでは`SKILL.md`を読み、そこから今回の差分に必要な参照だけを読む。
3. 命令、禁止、必須条件、出力契約をルール候補にする。
4. 説明、背景、例示だけの文を強制ルールとして扱わない。
5. ルール本文を短く言い換えず、判定根拠となる原文を`text`へ記録する。
6. 出典の絶対パス、スキル名、見出しを保持する。
7. 同じ意味の重複ルールは一件へまとめるが、出典が異なる競合ルールは残す。
8. 差分と直接関係しないルールを、変更行へ無理に割り当てない。

## 判定方針

- `rule_in`: 差分からルール適合を直接確認できる。
- `rule_out`: 差分から具体的な違反を直接確認できる。
- `unknown`: 依頼内容、実行時情報、競合解消情報などが不足している。
- `no_rule`: 指定された全ルールを照合したが、直接対応するルールがない。
- `rule_gap`: 実装が具体的な方針を選んでおり、別の妥当な選択肢が存在するのに、指定された全ルールから選択根拠を確認できない。

ルールの目的とコードの意味を評価する。キーワードが一致するだけで適用せず、存在しないルールや出典を作らない。

## ルール不足候補をあぶり出す

通常評価で全変更行を覆った後、全変更行をもう一度、規約不足の視点だけで走査する。次のように実装が方針を固定しやすい変更を優先して確認する。

- allowlist、denylist、既定値、閾値、固定定数、enum
- HTTP status、error code、認可結果、validation結果の対応
- fail-open、fail-closed、fallback、retry、timeout
- public API、画面操作、状態遷移、互換性の追加または変更
- 秘密情報、永続化、origin、外部通信、生成物のtrust boundary
- concurrency、double submit、stale response、unmount、cache、migration
- テストだけが期待値として固定している挙動
- 「安全」「許可」「必ず」「現在は」など規範を表すコメント

`rule_gap`にするには、次のすべてを満たす必要がある。

1. 変更行が具体的な方針を選択している。
2. 別の妥当な選択肢を具体的に説明できる。
3. 指定ルールにその選択根拠がない。
4. 不足している判断を`reason`、検討用の提案ルールを`suggestion`へ具体的に記録できる。

単なるimport整理、改行、名前変更、機械的なfixture設定は`rule_gap`にしない。実行時情報が足りないだけなら`unknown`、規約化すべき判断がなければ`no_rule`を使う。既存ルールで判断できる内容を、同じ不足理由で`rule_out`と`rule_gap`へ重複させない。別の不足判断が同じ行に存在する場合だけ、通常評価とは別review IDの`rule_gap`を追加する。

`rule_gap`は指定ルールに根拠がないことを示す評価であり、外部の未指定ルールを探索して出典へ追加しない。提案ルールを承認済みルールとして扱わず、ユーザーの明示指示なしにルールファイルやコードへ適用しない。

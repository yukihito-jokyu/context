# 配信契約

## 検証と配信

候補を編集するたびに `validate` を使用します。候補を確定した後にのみ、最終的なアトミック配信を使用します。

```bash
node bin/archify.mjs deliver <type> <candidate.json> <output.html> --quality showcase --json
```

Deliverは仕様を一度だけ読み、その正確なバイト列を同じディレクトリの非公開候補スナップショットへ書き込み、そのスナップショットをレンダリングし、完全な成果物チェッカーを実行します。すべての成果物検査に合格した場合にのみ対象を置き換えます。JSONレシートには、`specification` と `artifact` の両方についてSHA-256とバイト数が含まれます。レンダラー、チェッカー、レシート、またはコミットが失敗すると0以外で終了し、非公開状態を削除し、以前の信頼済み成果物を保持し、オープナーを決して起動しません。

現在の候補に対して `deliver` が0で終了した後にのみ、`visual-check` を実行してください。配信に失敗し、出力パスがすでに存在する場合、そのパスは以前の信頼済み成果物を指したままです。その時点で `visual-check` を実行すると、拒否された候補ではなく古い出力を計測・取得してしまいます。新しい視覚的証拠を収集する前に、配信診断を報告してソースを修復してください。

決定論的レシートが証明するのはバイト同一性と自動検査です。決定論的レシートに視覚レビューが含まれると主張してはいけません。

## 自動視覚証拠

配信後、再レンダリングや変更を行わず、信頼済みHTMLそのものを検査します。

```bash
node bin/archify.mjs visual-check <output.html> --json
```

依存関係のないこのコマンドは、DevToolsパイプ経由でChrome／Chromiumを使用します。1440×900、1600×1000、1920×1080、2048×1320でライトテーマの収まりを計測し、続いて1440×900と2048×1320でライト／ダークのスクリーンショットを取得します。成果物の隣に、4つのPNGサイドカー、相対パスのHTMLコンタクトシート、1つのJSONレシートを書き込みます。レシートはソース成果物のSHA-256とバイト数を関連付け、READおよびStillのランタイム状態を記録し、常に `visualReview: "pending"` を報告します。自動証拠が知覚的レビューを主張することはできません。

終了コード0は、すべての収まり計測と取得に合格したことを意味します。終了コード1は、オーバーフローまたは取得失敗を意味します。終了コード2は、Chrome／Chromiumが利用できず、レシート状態が `skipped` であることを意味します。失敗またはスキップした取得実行では、以前の証拠を現在のものとして提示しないよう、古い画像／コンタクトシートのサイドカーを削除します。

## 任意のオープン

ユーザーが即時ローカルプレビューを望む場合にのみ `--open` を追加します。アトミックコミット後に実行され、引数配列を1つ渡すOSオープナーを5秒の制限付きで使用し、`open.status` を記録します。CI、無人エージェント、非対話環境では無効のままにします。失敗または未対応のオープン処理によって配信が無効になることはありません。その状態が証明するのは、ローカルオープナーの起動に成功したかどうかだけです。

## 最終正常状態を保つライブプレビュー

アクティブなデスクトップ作成ループでのみ使用します。

```bash
node bin/archify.mjs preview <type> <input>.json <output>.html --quality showcase
```

Previewはループバック上の明示的な入力を1つ監視し、安定した各ダイジェストを非公開スナップショットへ関連付け、既存の検証済み配信パイプラインに合格した場合にのみ先へ進みます。無効、書き込み途中、削除済み、または置換済みの入力があっても、以前の検証済みリビジョンを画面上とディスク上に残します。同一バイト列では再ビルドも再読み込みもしません。

プレビューランタイムは依存関係のないSkill ZIP内に同梱され、`node_modules` なしで動作しなければなりません。

既定では決して起動しないでください。CI、無人エージェント、リモート共有、モバイル用途には使用しません。`--no-open` は、表示されたローカルURLをユーザー自身が開く場合、またはループテストの場合にのみ使用します。引き渡し前にCtrl-Cで停止します。サーバー状態、ポート、ソースパス、診断、エラーテキスト、再読み込みトークンを、生成成果物やエクスポートへ決して含めてはいけません。

## 知覚的な配信ゲート

自動検証では視覚的な洗練を証明できません。決定論的な配信後、実際のHTMLを対応ブラウザーで検査するか、画像リーダーでスクリーンショットをレンダリングします。変更した場合は両テーマ、既定のREADビュー、線の交差／経路、ラベルマスク、ノード／カードの収まり、フォーカス／検索／passportの閉じ方、エクスポートの清潔さを確認します。

既定のスタンドアロンデスクトップViewerでは、1440×900、1600×1000、1920×1080を計測します。成果物を大型デスクトップ表示向けにする場合は、2048×1320も計測します。最初の画面に収まるためには、確認したすべてのサイズで `document.documentElement.scrollWidth <= window.innerWidth` かつ `scrollHeight <= window.innerHeight` を満たす必要があります。確認した最大ビューポートでは、レンダリング構成に目立つ空の下帯がないかを検査します。メインパネルと必要な結論カードは、浅い帯へ潰れるのではなく、利用可能な高さを均衡の取れた全体として使うべきです。デスクトップのビューポートであふれる場合は、ノード、ラベル、メインパネルを縮小する前に、本当に冗長な内容だけを除去するか、間隔を詰めて作成済み構成を修復します。計測を通すために、オーバーフローを隠したり、内容を切り抜いたり、図内部のスクローラーを導入したり、ノード／ラベルの文字を小さくしたりしてはいけません。狭幅／モバイルの収まりでは、ページの縦スクロールを残せます。

正確で誠実な状態を1つだけ報告します。

- `visual_review: passed` — レンダリング済み成果物を検査した後にのみ使用します。
- `visual_review: skipped (image reader unavailable)` — 対応する視覚表示面がない場合に使用します。
- `visual_review: failed` — 具体的に見える欠陥を併記します。

`correction_rounds: 0`、`correction_rounds: 1`、または `correction_rounds: 2` を使用し、焦点を絞った修正は最大2回を超えないでください。成果物を検査せずに `visual_review: passed` を報告してはいけません。

視覚レビューで候補を変更した場合、以前の確定仕様レシートは最新ではなくなるため、検証と配信を再実行しなければなりません。

## 引き渡しレシート

以下を返します。

```text
diagram_type: architecture|workflow|sequence|dataflow|lifecycle|class|er
output: /absolute/path/to/file.html
specification_sha256: <receipt value>
artifact_sha256: <receipt value>
validation: 9/9 showcase, 0 errors, 0 warnings
visual_review: passed|skipped (image reader unavailable)|failed
correction_rounds: 0|1|2
```

オープン状態、プレビュー状態、Share Card、その他のViewerエクスポートは検証済みという主張にはなりません。

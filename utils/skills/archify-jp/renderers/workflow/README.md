# ワークフローレンダラー

`diagram_type: "workflow"` のJSONファイルを標準Archify HTMLテンプレートへレンダリングします。

```bash
node archify/renderers/workflow/render-workflow.mjs input.workflow.json output.html
```

レンダラーは、同梱のスタンドアロンバリデーターを使用して、入力を `archify/schemas/workflow.schema.json` に照らして検証します。依存関係をインストールする必要はありません。

`output.html` を省略すると、レンダラーはJSONファイルの `meta.output` を使用します。それもなければ、現在の作業ディレクトリの `workflow.html` へフォールバックします。

レンダリング後、成果物チェッカーを実行します。

```bash
node archify/scripts/check-render-output.mjs output.html
```

これは、有限でないSVG値、意図しない2点間の斜め矢印、凡例を横切る矢印など、ブラウザーで最も発見しやすい最終SVGの問題を検出します。

## 入力

ワークフローJSONファイルには、次の値を設定する必要があります。

```json
{
  "schema_version": 2,
  "diagram_type": "workflow",
  "meta": {
    "title": "Agent Tool Call Workflow"
  },
  "lanes": [],
  "phases": [],
  "groups": [],
  "mainPath": [],
  "nodes": [],
  "edges": [],
  "cards": []
}
```

新しいワークフローには `schema_version: 2` を使用します。その可読レイアウトコンパイラーは、各 `col` を `0..5` の論理ランクとして扱い、計測済み文書からジオメトリを導出します。`schema_version: 1` は既存ソース向けの固定された旧契約として残ります。有効なv1出力はバイト単位で維持され、暗黙にv2として再解釈されることはありません。

一般的なv2の場合は `meta.viewBox` を省略し、コンパイラーが内在的な計測境界を使用できるようにします。v1で省略した場合、幅は720に固定され、高さはレーン数から導出されます。完全な実例は `archify/examples/agent-tool-call.workflow.json` にあります。その `schema_version` が適用契約を選択します。

schemaは次の場所にあります。

```text
archify/schemas/workflow.schema.json
```

## 移行とレイアウトレシート

既存のv1ソースを別のv2ファイルへ移行します。

```bash
node archify/bin/archify.mjs migrate workflow old.json new.json --to-schema 2 --json
```

schema-v2の出力を新しいソースとして同じコマンドを再実行すると、冪等性の検証になります。出力先のバイト列とジオメトリは変わりません。

既定では、コマンドがソースを上書きすることはありません。旧形式の絶対 `via[*][0]`、`labelAt[0]`、`channelX` 値を解決済みランク空間へ写像し、報告された垂直制約に作成者の入力が必要な場合を除いてy座標を維持し、曖昧さのない収まり修復の場合にのみ明示的viewBoxを拡張します。v2コンパイルと成果物検査に合格した後にだけ出力先を書き込みます。曖昧な明示ピンは、出力先を生成せずに失敗します。

安定した作成者向けv2計画は次で確認します。

```bash
node archify/bin/archify.mjs validate workflow input.workflow.json --layout-json
```

レシートは、選択した契約、計測済み `viewBox` と `requiredViewBox`、解決済みの列、ノード、エッジ、ラベル、因果診断を報告します。ソルバー反復と候補スコアは意図的に省略します。

## 凡例

既定の凡例は `nodes[].type` からコンポーネント種別を導出します。`meta.legend.entries` で対応するキーは、安定順で `frontend`、`backend`、`security`、`messagebus`、`database`、`cloud`、`external` です。ラベルと表示状態は共有凡例契約によって上書きできます。レンダリング済みノードに裏付けられた種別だけがSemantic Legend操作を受け取ります。

## レイアウト契約

### 固定v1

| 定数 | 値 |
|----------|-------|
| viewBox | 既定 `[720, auto]`。自動高さ = 52 + lanes×104 + (lanes−1)×20 + 124 |
| レーン枠 | x 40、幅640、高さ104、間隔20。最初のレーン上端はy 52 |
| レーンタイトル帯 | 各レーン上部30px。ノードボックスはその下に置く |
| 列中心（`col` 0～5） | x = 88, 220, 300, 430, 500, 625 |
| フェーズ見出し | 任意の `phases[]` は最初のレーン上にレンダリングされ、`fromCol..toCol` にまたがる |
| レーングループ | 任意の `groups[]` は1レーン内の並行処理または分岐処理を囲む |
| 例外レーン | 再試行、拒否、フォールバック、失敗経路には `lane.variant: "exception"` を設定 |
| メイン経路lint | 任意の `mainPath[]` は、正常系ステップに対応エッジがあり後退しないことを検査 |
| 既定ノード | 92×52（`tag` 設定時は高さ68） |
| ノード間隔 | 同一レーン内のノード間で8px以上 |
| エッジ長 | 直線区間は28px以上 |
| 凡例行 | y = レーン下端 + 44。viewBox高さは凡例y + 18以上 |

列中心間隔は132 / 80 / 130 / 70 / 125pxです。同一レーンでは、列1↔2（80px）と3↔4（70px）の両方に既定幅92pxのノードを配置できません。このような無効なv1ソースは、因果的な `workflow/column-capacity` 診断を1つ受け取り、検証済みのv2移行修復を提示されます。v1が適応レイアウトへフォールスルーすることはありません。

### 可読v2

| 不変条件 | 契約 |
|----------|----------|
| 論理列 | `col` は `0..5` の整数。ピクセル中心は計測済み出力 |
| 隣接ランク基準 | 文書固有制約を適用する前の中心間距離120px |
| 同一レーンのノード間隔 | 垂直ノード区間が重なる場合は8px以上 |
| 対向する直接エッジ | 空き幅 ≥`max(28px, measured label mask width + 8px)` |
| 自動経路リズム | 直接区間28px以上、端点スタブ8px以上、内部折れ区間16px以上 |
| 暗黙viewBox | 内在的な内容境界に契約余白を加算 |
| 明示viewBox | 収容容量。小さすぎる入力は正確な `requiredViewBox` と要因を報告 |

コンパイラーは実際に関係する、または重なる同一レーンのノードだけに制約を適用します。そのため、無関係なレーンの幅広いノードによって全ランクが拡張されることはありません。旧中心位置は正しさの制約を満たした後の弱い優先値であり、ジオメトリ保証ではありません。フェーズ枠とグループ枠は解決済みランク帯から導出されます。自動経路は一度正規化され、同じ最終sceneが検証とSVG直列化を駆動します。長い自動ラベルは、全下流ランクを広げる代わりに、直接余白の拡張と正当なチャネルを比較します。計測済みの複数行凡例は、内在高さと明示viewBox容量に含まれます。

作成済みの `via`、`labelAt`、`channelX`、`channelY` はv2の絶対的な固定ピンです。実現不能なピンは、暗黙に移動するのではなく `workflow/explicit-pin-conflict` を返します。`fromSide` と `toSide` は方向制約のままです。経路プリセットは自動候補群を制限しますが、それ自体は絶対座標ピンではありません。いずれかの端点辺を省略するとv2コンパイラーが実現可能な辺を選び、指定した辺はその端点を名前付きポートへ制限します。

## 設計規則

- 所有権またはランタイム境界にレーンを使用します。
- Intake、Plan、Execute、Reportのような高レベルのストーリー区切りにフェーズ見出しを使用します。
- レーン内の並行検査、分岐処理、限定処理にグループを使用します。各グループには1つ以上のノードが必要です。
- 人の待機、拒否、再試行、フォールバック、失敗のレーンには、正常系経路へ混在させず `lane.variant: "exception"` を使用します。
- 図に明確な正常系経路がある場合は `mainPath` を設定します。レンダラーは連続IDに対応エッジがあり、左から右へ進むことを検証します。
- 生SVG座標ではなく、レーンIDと `0..5` の `col` 索引でノードを配置します。
- セマンティックなエッジラベルを維持します。Readable v2は計測済みラベル余白を割り当てます。ラベルが収まらない場合、意味を削除せず、報告された容量または経路制約を修復します。
- 決定、承認、プロトコル、非同期トレース、復帰経路など、端点だけでは完全に示されない関係の意味にラベルを使用します。
- 生の `via` 点より先に、`drop`（レーン間で折れ、`bias` 0～1で位置を選択）、`outside-right`、`return-left`、`bottom-channel`、`up-channel` の経路プリセットを優先します。残りは `straight` と既定の `auto` で対応します。
- 狭いチャット／ブラウザープレビューでも適切にレンダリングできるよう、ワークフローexampleをコンパクトに保ちます。

### 任意のセマンティック検査

レイアウト検証は、ラベルやカードからドメイン上の真実を推測できません。ソース証拠によって起点、終端、必須の直接関係、必須の有向到達可能性が確定している場合は、その事実を `semanticChecks` にエンコードします。

```json
"semanticChecks": {
  "allowedRoots": ["request", "resource_catalog"],
  "allowedTerminals": ["reply", "audit_log"],
  "requiredEdges": [
    { "from": "dispatch", "to": "dispatch_ledger" }
  ],
  "requiredPaths": [
    { "from": "event_ledger", "to": "runtime_host" }
  ]
}
```

`allowedRoots` または `allowedTerminals` が存在する場合、それぞれ入次数0または出次数0のノードに対する完全な許可リストです。`requiredEdges` は作成済みの正確な1方向を要求し、`requiredPaths` は中間ノードを許可しますが作成済みエッジの方向に従います。これらの検査はレイアウト前に実行され、SVGやレシートのバイト列を変更しません。経路または構成診断を解決するためだけに弱めてはいけません。ドメイン事実が不明なフィールドは省略します。

schema違反は、要素のidまたはlabelを注記したパス接頭辞付きメッセージを出力して0以外で終了します。レンダラーはさらに、ノードの重なり、レーン外のノード、無効なフェーズ／グループ列範囲、空のグループ、壊れた `mainPath` ステップ、不明なエッジ終点、ラベルとノードまたは他ラベルとの衝突、ノードより幅広いラベル、viewBox外の凡例、短すぎて読みにくい直線矢印など、検出可能なレイアウト問題でも失敗します。共有Clean Flow Gateも、2pxのクリアランスで無関係なノードを横切るエッジを拒否します。レーン、フェーズ、グループは意図的な通過コンテナーのままです。テキスト幅はCJKを考慮して推定し、全角グリフを2単位として数えます。

診断は因果的です。ランク容量の失敗は、派生する短いエッジ、端点方向、ラベル重なりの検出を抑制します。各 `supportedFixes[]` エントリは、提案された編集を再計画して検証されます。ラベルの存在が不変条件違反の原因ではない場合、診断がセマンティックラベルの削除を提案することはありません。

洗練された配信には、`meta.quality_profile` を `showcase` に設定します。その場合、無関係な正規X交差は `composition/proper-crossing` で失敗します。既定の `standard` では成果物レシートの警告に留めます。同一直線上のレーン経路は正規X規則の対象外ですが、別のゲートが、無関係なエッジが8px以上重なると `standard` では警告し、`showcase` では失敗します。共有セマンティック端点、点での接触、それより短い重なりは有効なままです。Showcaseはさらに、8px未満の経路区間と16px未満の内部折れ区間を拒否します。固定レーン間隔における通常の8～15px端点スタブは有効なままです。

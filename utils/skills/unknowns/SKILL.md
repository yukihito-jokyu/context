# unknowns

AI開発における未知管理の入口として使う。作業前・作業中・作業後に残っている未知を分類し、AIが推測で空白を埋める前に、使うべき子スキルと成果物を決める。

## Purpose

- ユーザーの期待とAIの推測がズレる原因を先に見つける。
- 既知の既知、既知の未知、無自覚の既知、無自覚の未知を分ける。
- 作業リスクに応じて、必要な子スキルだけを選ぶ。

## When to Use

- AIに開発作業、設計、調査、レビューを依頼する前。
- 要件、仕様、制約、判断基準、例外条件に曖昧さがあるとき。
- 既存コード、既存仕様、既存デザインへの影響がありそうなとき。
- 実装中に計画外の判断が出てきたとき。
- 実装後に説明資料や理解確認が必要なとき。

## Inputs

- 作業の目的。
- 現在分かっている仕様。
- まだ決まっていないこと。
- 見れば判断できるが、言葉にできていない基準。
- そもそも考慮できていない可能性がある領域。
- 参照できるコード、仕様、画面、過去成果物。
- 出力してほしい成果物。
- 人間が判断したいポイント。

## Child Skills

- `blindspot`: 無自覚の未知を洗い出す。
- `prototype`: 見れば判断できる基準をプロトタイプで引き出す。
- `interview`: 曖昧な点や既知の未知を質問で明確にする。
- `reference`: 既存物から仕様、好み、設計意図を抽出する。
- `plan`: 実装前の重要判断をレビュー可能な計画にする。
- `notes`: 実装中の判断、逸脱、エッジケースを記録する。
- `pitch`: 実装後に他者へ説明できる資料を作る。
- `quiz`: 変更内容の理解漏れを確認する。

## Process

1. 作業内容を確認する。
2. 未知を4象限に分類する。
3. 作業リスクを低・中・高に分類する。
4. 使う子スキルを選ぶ。
5. 子スキルの実行順序を決める。
6. 最低限作る成果物を定義する。
7. 人間が判断すべき論点とAIが探索してよい論点を分ける。

## Selection Rules

| 状況 | 使うスキル |
| --- | --- |
| 何を考慮すべきか分からない | `blindspot` |
| 曖昧な点が多い | `interview` |
| UI、画面、レポート、体験の判断がある | `prototype` |
| 既存仕様や既存コードに合わせる必要がある | `reference` |
| 実装前に計画をレビューしたい | `plan` |
| 実装中にAIが判断する余地がある | `notes` |
| 実装後に他者へ説明する必要がある | `pitch` |
| 実装後に自分の理解を確認したい | `quiz` |

## Standard Flow

大きな作業や曖昧さの高い作業では、以下の順序を標準とする。

```text
unknowns
-> blindspot
-> reference
-> interview
-> prototype
-> plan
-> notes
-> pitch
-> quiz
```

すべての作業で全スキルを使う必要はない。作業のリスクと未知の種類に応じて省略する。

## Risk Patterns

### 低リスク作業

例: 小さな修正、既存仕様の明確な追従、影響範囲が限定的な変更。

```text
reference
-> notes
```

### 中リスク作業

例: 仕様に曖昧さがある、既存コードへの影響がある、判断が必要な実装。

```text
blindspot
-> reference
-> interview
-> plan
-> notes
```

### 高リスク作業

例: 大きな設計変更、UIや体験に関わる変更、既存システムへの影響が大きい変更、AIが多くの判断を行う作業。

```text
blindspot
-> reference
-> interview
-> prototype
-> plan
-> notes
-> pitch
-> quiz
```

## Outputs

- Unknowns Management。
- 未知の分類。
- 作業リスクの分類。
- 使用する子スキル。
- 子スキルの実行順序。
- 最低限の成果物。
- 人間が判断すべき論点。
- AIが探索してよい論点。

## Rules

- すべての子スキルを毎回使わない。
- 不明点をAIの推測で埋める前に、確認・参照・プロトタイプへ逃がす。
- 作業前、作業中、作業後で未知が増える前提で扱う。
- 重要判断は先に出す。
- 参照対象がある場合は、一般論より現物を優先する。

## Anti-patterns

- 「たぶん大丈夫」として曖昧さを放置する。
- 記事要約や思想説明だけで終わる。
- 質問を大量に並べて、回答の質を落とす。
- 実装後のdiffだけで判断理由を残したつもりになる。

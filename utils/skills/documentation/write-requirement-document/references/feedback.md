# 利用中の指摘を収集して改善へつなぐ

生成したスキルには、指摘・修正前の成果物・修正後の成果物・ユーザーの承認を保存する hooks を必ず付ける。仕組みは共通の `scripts/feedback.py`、形式は `assets/feedback.schema.json`（schema_version: 1）にする。スキルごとに別の収集形式を作らない。

収集は hooks が提供する追加機能である。生成した SKILL.md、ルール表、チェックリストへ収集の指示を足さない。入力保存・指摘分類・承認画面の案内は、有効な hooks の additionalContext からだけ伝える。共通のスクリプトと資料は必ず同梱して既定で hooks を登録するが、`install.py --no-hooks` または製品側で無効化できる。無効時は収集も指示の注入も行わない。収集の失敗で本来の生成・検査・完了を拒否しない。

## 1. 利用中に保存する

1. `run.py start` が通常の実行 ID を作り、有効な hooks が追加機能の案内を注入する。再現に必要な入力ファイルを読むときは、変更する前に `python3 <skill>/scripts/feedback.py context --file <入力ファイル>` で保存する。指定した実ファイルの内容をその時点で写す。画像等の出力には契約の `outputs[].binary: true` を指定し、検査・整形は `command` にする。外部サービスの情報は、利用許可のあるローカルの入力へ保存して指定する。
2. Stop の hook が、完了・質問待ち等で提示する成果物と使ったスキルのファイル・契約を内容ごとに保存する。完了後に直して見せた版も保存する。`run.py start/check/finish` は収集プログラムを呼ばず、hooks 無効時も本来の処理を行う。
3. 成果物を提示した後の UserPromptSubmit は、発言の原文と、その発言の時点で提示済みの成果物の版を記録する。指摘かどうかの判断は AI が行う。指摘なら、編集の前に `python3 <skill>/scripts/feedback.py feedback --event <message-ID> [--summary <指摘の要点>]` を実行する。要点で原文を置き換えない。無関係なら `ignore --event <message-ID> --reason <理由>` を実行する。どちらに分類しても原文は残る。
4. 指摘を直し、成果物を再提示する。別の実行を始めた場合も、同じセッションで対応中の指摘に版を結び付ける。`python3 <skill>/scripts/feedback.py review --port 0` を継続するターミナルで起動し、出力された localhost URL をユーザーへ渡す。画面で指摘と修正前後の実ファイル・差分を見てもらう。承認を待つためだけに成果物の作成を未完了にはしない。
5. ユーザーが画面の「この修正版を承認する」を押すと、その承認操作・コメントと、表示した修正版を結び付ける。古い画面、表示後のファイル変更、別の版への承認は拒否する。会話の「OK」等・無回答・AI の判断では承認済みにしない。AI は承認ボタンを操作せず、承認 API へ送信しない。承認操作を行うテストには合成データだけを使い、実ユーザーの承認と区別する。

出力の検査は実行中に働く。指摘と承認の収集は `done` の後にも働く。スキル自身を編集したことを理由に止めない。PreToolUse は、実行記録と収集記録の編集ツールによる直接変更を拒否する。追加機能の入力・分類・会話との対応情報は収集側だけで保持し、スキルの state.json へ書き込まない。

`feedback.py status` で未分類の発言・対応中の指摘を確認し、`validate` で実ファイルと参照を確かめる。記録先は作業プロジェクトの `.skill-feedback/<skill-name>/`。その配下の `.gitignore` でローカルの記録を Git から外す。記録は新しい実行や再実行で上書きしない。

確認画面は `127.0.0.1` でのみ待ち受け、版と送信元・一回限りのトークンを検査する。HTML は隔離したプレビュー、画像は画像、テキストは本文と差分、PDF 等は実ファイルで確認できる。画面を閉じても記録は残る。サーバーを終了するには起動したターミナルで Ctrl+C を押す。

## 2. 共通の構造

`feedback.json` は、次の要素を ID でつなぐ。テキスト・HTML・画像・PDF等の成果物は `objects/<sha256>` に元のバイト列で保存する。ファイル名や内容が変わっても、前の版は残る。

| 要素 | 保存する内容 |
|---|---|
| `messages` | UserPromptSubmit が受けた原文と、確認画面で送信した承認操作・コメント。時刻、製品、セッション、提示済みの版、分類 |
| `deliveries` | 提示した成果物の集合、実行 ID、元の依頼と正規化した入力、入力ファイル、スキルの版と実ファイル、契約 |
| `cases[].issue` | 指摘の原文・要点と、もとにした message ID |
| `cases[].before` | 指摘を受けた成果物の delivery ID |
| `cases[].revisions` | 指摘へ対応して提示した版の履歴 |
| `cases[].after` | ユーザーが承認した delivery ID。未承認なら null |
| `cases[].approval` | 確認画面の承認操作・コメント・時刻・message ID・承認した delivery ID。未承認なら null |

承認は記録されたイベントと保存内容の対応を検査する。利用者の厳密な認証や、shell による記録の書き換えまで防ぐ仕組みではない。hooks の入力を使うテストと、実ユーザーの承認の記録を区別する。本文だけのチャット回答は、そのままでは成果物のファイルとして保存できないため、スキルの出力契約に保存先を定める。

## 3. Eval と収束テストへ渡す

```bash
python3 <skill>/scripts/feedback.py export --out <新しいデータセットのディレクトリ>
python3 <foundation>/scripts/feedback_eval.py --dataset <データセット> --skill <改善するスキル> --out <新しい作業場所>
```

export は、承認済みの指摘だけを共通形式で取り出す。元の指摘・承認・修正前後の実ファイル・その時のスキルを保持し、参照と内容を検証する。未承認の修正版を成功例へ混ぜない。

feedback_eval.py は、スキルの作業用コピー、保存した事例、Eval の候補、元の依頼と入力を使う収束テストの候補を作る。正本や既存 Eval は変更しない。修正版への承認だけで、一般化した価値・評価基準への同意まで得たとは扱わない。候補の `questions` で、指摘をどこまで一般化するか、修正前を失敗・修正後を成功とするか、判定するファイル、入力条件の不足をユーザーと確認する。

その後は foundation の `references/eval.md` と `references/convergence-test.md` に従う。価値・振る舞い・判定方法と再現条件を確定させ、`eval_check.py` に通してから収束テストを準備する。画像・PDF等は元の実ファイルを見られる判定方法を決める。記録したバイナリを文字列として採点しない。

収束テストの生成担当へ渡すのは元の依頼と入力だけにする。指摘、修正版、正解、評価基準を生成担当のプロンプトや作業場所へ置かない。評価担当が、同じ Eval で元の版と候補版の結果を比較する。収集した事例に加え、通常・既定値・境目・holdout の課題を使い、特定の修正版だけに合わせた改善を避ける。実モデルの起動回数の確認は既存の規則に従う。

## 4. hooks の仕様の根拠

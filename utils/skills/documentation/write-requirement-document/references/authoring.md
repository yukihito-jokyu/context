# 原資料から要件定義へ

## 1. 材料と対象を確かめる（IN-01、IN-02）

会話・議事録・箇条書きから、解く課題、対象、利用者、業務の順序、条件、対象外を拾う。対象と課題がどちらも分からないときだけ、開始前にまとめて聞く。対象が分かる間は、未指定の条件を未決事項としてドラフトを作る。実装詳細だけを求める依頼は設計書へ案内する。

コードを根拠に既存仕様を復元する依頼は、このスキルの主な用途ではない。指定資料の範囲を読み、出典の場所と実際の抜粋を残す。出力用の追加スキルや外部サービスを自動導入しない。

## 2. 確定していない内容を分ける（STEP-02）

原資料の矛盾は、どの記述が食い違うかが分かる形にする。承認必須と承認不要が混在していれば、その両方を根拠として残し、未決事項へ承認の要否を書く。片方の条件で確定した状態遷移を描かず、未決の判断点として示す。

共通要件の説明にも、一方の案を排除する断定を混ぜない。たとえば、即時確定案と承認後確定案が未決のとき、「申し込み自体を予約の確定とは扱わない」と書くと即時確定案を排除してしまう。「申し込みと予約確定が同時になるかは未決」と書き、両案を残す。

本文や図で「未決」と示した条件は、open_questionsの質問と、その条件が決まるまで確定できない範囲へ結び付ける。たとえば取消から確定へ戻す要否を未決と書いたら、「戻す操作は必要か」と「決まるまで逆遷移の操作と受入条件を確定できない」を同じ未決事項へ書く。本文や図では「取消済みの予約を戻す操作の要否」のように内容を示し、未決という注記だけで終えない。

「効率化したい」という目的から、通知、権限、ログイン、監査ログ、性能値を決定済みとして足さない。追加が必要だと考える内容はproposalかopenにする。業務の制約と実装案を区別し、構成が指定された事実だけをconstraintsへ書く。

## 3. 原本の項目と根拠（OUT-08）

assets/examples/requirement-document.jsonを形の見本として使う。ドメインの名詞や条件は写さず、今回の原資料へ置き換える。rootのキーと各配列の形はcheckが検査する。

- summary：何の課題をどう解くかを示す冒頭の要点。重大な未決条件も短く示す。
- background・purpose：背景の課題と、必要な振る舞いで達成すること。
- terms・actors・scope：用語、利用者の役割、対象と対象外。
- requirements：誰が何をどの条件で行うかをstatementへ書き、reasonとacceptanceを添える。
- quality：performance、availability、security、privacy、operations、accessibilityの順。未指定ならopenとし、open_questionsへ確認内容を書く。
- sources：SRCの連番、資料名、行または発言の場所、実際の記述のquote。
- diagrams：Dの連番、種別、読む目的intro、読み取る結論takeaway、代替説明alt、要件ID、根拠ID、Mermaid原本。
- diagram_decisions：9種類の採否、理由、根拠ID。
- open_questions：Qの連番、質問、未決のままだと確定できない範囲、根拠ID。
- constraints・design_notes：指定された構成上の制約と、設計へ引き継ぐ未決定の実装案を分ける。

scopeのin・outにはそれぞれ1件以上書く。対象外が未指定なら、outを空配列にせず「対象外は未指定。『今回扱わない業務』で確認する」のように書き、同名の確認質問と、決まるまで確定できない範囲をopen_questionsへ残す。未指定の業務を対象外と断定しない。

constraintsとdesign_notesは文字列の一覧ではなく、次の形のオブジェクトの一覧にする。該当する記述がなければ空配列にする。constraintsには原資料で要件とされた構成上の制約だけを入れる。design_notesには決定前の案であることをstatementの文章で明記する。この2項目にはstatusキーを加えない。requirementsとqualityのstatusだけがstated・proposal・openを取る。

```json
{
  "constraints": [
    {"statement": "社内ネットワークからだけ利用する。", "source_ids": ["SRC-01"]}
  ],
  "design_notes": [
    {"statement": "Reactで画面を分割する案。採用は未決。", "source_ids": ["SRC-02"]}
  ]
}
```

要件はFR、利用者はACTの連番にする。ただし、IDはJSONのid・参照配列とHTMLのリンク先属性だけに使う。本文、見出し、リンクの表示名、代替説明、Mermaidのラベルには書かない。要件から図、図から要件の両方に参照配列を書き、HTMLでは要件名・図名・資料名と場所をリンクの表示名にする。図は「空き時間を確認する」など本文と同じ業務の言葉で照合できる形にする。原資料のquoteは忠実に保存し、原資料に元からある記号を改変しない。根拠が存在しない記述をstatedへ混ぜない。

受入条件は、原資料から導ける振る舞いを確かめるために書く。例を具体化するときも、採否、優先順位、先着順、同時要求の双方拒否など、未指定の業務判断を加えない。「重複予約を防ぐ」という要望から「同時要求は両方とも拒否する」とは決められない。

同時予約を例にするなら、「重複する2件をともに確定させない。どちらを受け付けるかは『同時に申し込まれた予約の採否』で確認する」と書き、その未決事項へ採否の決め方と未確定の受入条件を残す。「両方の予約を受け付けない」は、双方拒否と両立禁止の2通りに読めるため使わない。

## 4. 完了前の意味の確認（OUT-03）

書いた人の知識がなくても、課題と目的、利用者、対象外が分かるかを読む。次に、図の順序・条件・用語が本文と同じかを確認する。最後に、各段落の要点を1文で言い直せるかを試し、言い直せない段落は分けるか書き直す。

文字数だけで端的さを判定しない。短い文でも主語や条件が途切れていれば直す。例外を削って短くせず、条件と結果を結び直す。検査が通っても、この意味の確認は省かない。

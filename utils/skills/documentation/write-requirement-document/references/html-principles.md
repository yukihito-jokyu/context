# 読者が前提を補わずに読めるHTML

## 1. 文章の中心を決める（OUT-03）

要件定義書の中心は「何の課題を、誰のどの振る舞いで解決するか」である。各節の冒頭に要点を書き、続く文で前提と理由を補い、必要な振る舞いへつなぐ。書き手が知っているだけの前提を読者へ推測させない。

1段落を1つの論点にする。短い文を並べるだけで因果や条件が切れた文章は不合格とする。「効率化」「利便性の向上」だけで要件を済ませず、誰が何をどの条件でできるかを書く。価値を主張する文には、解く課題とのつながりを示す。修飾語と同義反復を削り、必要な前提・例外・未決事項は残す。

良い例：「同じ備品に重複する時間帯の予約がある場合、新しい予約を受け付けない。部署をまたぐ重複予約を防ぐため、入力した時間帯を確定済みの予約と照合する。」

悪い例：「シームレスな体験により利便性を向上し、業務効率化を推進する。」

用語は初めて使う箇所で説明する。予約・申請・受付が違う概念なら定義を分け、同じ概念の言い換えなら1語に統一する。AIが読む資料と読者が見る文書の差を、用語と前提の説明で埋める。

## 2. 全体像から詳細へ進める（OUT-02）

読み順は、概要、用語と前提、対象範囲、全体像と業務、機能要件、品質と制約、未決事項、根拠と補足に固定する。概要で目的をつかみ、用語と範囲を確認してから、図と個々の要件へ進む。目次と要件名のリンクで往復できる形にする。

読者に識別記号の意味や対応を覚えさせない。見出し、本文、リンク、図には「重複予約を防ぐ」「備品予約の打ち合わせメモ」のように内容が分かる名前を使う。内部IDは原本の参照とHTMLのリンク先属性に保持し、表示へ持ち込まない。未決事項も番号だけで指さず、確認する条件の名前で結び付ける。

冒頭に未決の重要条件があるときはsummaryにも短く示す。確定に見える主線の後ろへ重大な未決事項を隠さない。章を短くするために必要な説明を巻末へ追いやらない。

## 3. 図と説明を近くに置く（OUT-02）

各図は、見る目的、図、要点、関連要件、根拠の順に読む形にする。図の目的をintro、読み取る結論をtakeaway、画像を見られないときの説明をaltへ書く。altは「図」だけで済ませず、主体・関係・順序・分岐の意味を説明する。

図と本文で、主体、方向、状態、条件、用語をそろえる。図に描いた条件を本文へ書き、本文の例外を図から黙って消さない。要件の近くに図名のリンクを置き、図へも戻れるようにする。

## 4. 読むための操作を増やさない（OUT-02）

主要な本文と図は最初から表示する。折り畳みは原寸の画像、Mermaid原本、採否の補足だけに使う。要件、対象外、重大な未決事項をクリックしないと読めない場所へ隠さない。装飾目的のアニメーション、カルーセル、カードの乱立を加えない。

本文は検索・コピー・拡大できるHTML文字で残す。図のPNGには代替説明と原寸表示を付ける。色だけで確定・未決・対象外を区別せず、文字のラベルを併記する。狭い画面では本文を1列へ戻し、図の原寸表示の中だけで横スクロールする。

## 5. 分からないことを見える形にする（STEP-02）

入力に書かれた内容はstated、AIが補う案はproposal、未指定または矛盾する内容はopenとする。statedは承認済みを意味しない。業務の決定、品質の目標値、例外、権限を資料なしに確定しない。

未決事項には質問と、決まるまで確定できない範囲を書く。品質の6領域は入力に指定がなくても確認欄を残し、空欄や仮の数値で埋めない。実装案はdesign_notesに分け、業務上の要件の主線へ混ぜない。

## 6. このHTMLで採用する数値

本文の標準文字サイズは17px、行間は1.85、段落幅は44em以内、主領域は1040px以内にする。700px以下の画面では1列にし、16pxの文字を使う。これらはこのスキルの採用値であり、認知負荷が必ず下がることを保証する値ではない。意味のつながりは、Evalと読者の確認で評価する。

## 7. 根拠

[W3C COGA](https://www.w3.org/TR/coga-usable/)の明確な構造、短い文章、暗黙の前提の説明、要約、余白を参照した。[非テキストの代替](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html)と[Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)を踏まえ、代替説明と狭い画面での読み方を用意する。COGAは補足ガイダンスであり、このテンプレートを使っただけでWCAG適合と報告しない。

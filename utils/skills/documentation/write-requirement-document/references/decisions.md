# 前提と図がつながる要件定義書を書く のルール

## IN-01 材料がある要件定義だけを扱う

- 軸: I3
- ルール: 依頼が実装詳細の設計だけなら開始せず設計書の作成を案内する。解く課題と対象が会話・資料のどちらにも無ければ、開始前にその2点をまとめて聞く。条件が未指定または矛盾する材料は、ドラフトを作り未決事項へ残す。
- 理由: 対象不明のまま文章や要件を捏造しないため。
- 決め方: 依頼の指定
- 守らせ方: doc: SKILL.md の手順1、references/authoring.md の1章
- 機械化しない理由: 痕跡が残らない：開始しない判断は出力に残らない
- 良い例:

  ```text
  メモの承認条件の矛盾を未決事項へ残す
  ```
- 悪い例:

  ```text
  対象がないまま機能を提案して確定する
  ```

## IN-02 指定資料と会話を根拠に読む

- 軸: I4
- ルール: 会話、利用者が指定した資料、対象プロジェクトの AGENTS.md を読む。コードの逆解析を主目的にせず、資料にない決定は未決事項か提案として書く。根拠の抜粋と場所を sources に保存する。
- 理由: AIと読者の前提の差を根拠から埋めるため。
- 決め方: 依頼の指定
- 守らせ方: doc: SKILL.md の手順1、references/authoring.md の1章
- 機械化しない理由: 痕跡が残らない：読んだ資料の全範囲は出力だけでは確かめられない
- 良い例:

  ```text
  議事録の発言と場所を保存する
  ```
- 悪い例:

  ```text
  無関係なコードから業務条件を確定する
  ```

## STEP-01 材料から本文と図を順に作る

- 軸: P1
- ルール: 受付、資料の整理、構造化原本の作成、図の変換とHTML生成、検査、意味の確認、finish の順に進める。assets/examples/requirement-document.json を構造の見本にする。
- 理由: 本文と図を別々に作って食い違うことを防ぐため。
- 決め方: 機械で守らせられる答え
- 守らせ方: doc, template: SKILL.md の手順、assets/examples/requirement-document.json
- 機械化しない理由: 痕跡が残らない：作業の順序は最終出力だけでは分からない
- 良い例:

  ```text
  先に要件と根拠を整理してから図を生成する
  ```
- 悪い例:

  ```text
  図を先に作って本文の条件を合わせる
  ```

## STEP-02 未指定と矛盾を未決事項に分ける

- 軸: P2
- ルール: 業務の条件が未指定なら open_questions に質問と決まらない範囲を書く。本文・図で未決とした条件も、対応する質問と影響範囲へ結び付ける。資料が矛盾すれば各記述を sources に残して未決とし、一方を確定した図へ混ぜない。対象と目的が分かる間は作成を続ける。
- 理由: 質問待ちだけで止まらず、現在分かっている範囲を共有するため。
- 決め方: 依頼の指定
- 守らせ方: review: references/authoring.md の2章、完了前チェックリストで未決事項と図を照合する
- 機械化しない理由: 意味の判断が要る：記述の矛盾と未指定の条件を原資料と比較する
- 良い例:

  ```text
  承認要否は未決と図に示し、確認質問と確定できない予約条件を同じ未決事項へ書く
  ```
- 悪い例:

  ```text
  本文で取消から戻す要否を未決と書き、質問と影響範囲を残さない
  ```

## STEP-03 図の変換とHTML組立をスクリプトに任せる

- 軸: P3
- ルール: scripts/document.py の build が構造化原本から Mermaid原本、PNG、HTML、manifest を作る。check が原本・HTML・PNG・ハッシュ・参照を検査する。PNGを手で差し替えず、原本を直して build し直す。
- 理由: 原本と派生出力の対応を毎回同じ方法で確かめるため。
- 決め方: 機械で守らせられる答え
- 守らせ方: script, validate: scripts/document.py の build と check。出力 html の command 検査
- 良い例:

  ```text
  原本を直して全体を再生成する
  ```
- 悪い例:

  ```text
  PNGだけ差し替え原本を残す
  ```

## STEP-04 既存のローカル描画環境を使う

- 軸: P4
- ルール: Python 3.9以上、Node.js、既存の mermaid-cli 11以降を使う。doctor で実行経路を確認する。Mermaid図は flowchart、stateDiagram-v2、sequenceDiagram、classDiagram、erDiagram を使う。外部画像・リンク・初期化指令を図へ埋め込まず、追加パッケージとリモート描画サービスは自動導入しない。
- 理由: 同じ構文をローカルで変換し、環境による未検証の代替図を防ぐため。
- 決め方: 出力を使う道具や形式の公式の決まり
- 守らせ方: doc: scripts/document.py の doctor と build、references/diagrams.md の2章
- 機械化しない理由: 痕跡が残らない：コマンドの選択は最終出力から全て分からない
- 良い例:

  ```text
  既存mmdcで原本をPNGへ変換する
  ```
- 悪い例:

  ```text
  PNGの代わりにMermaid文字列だけを載せて完了する
  ```

## STEP-05 検査失敗を直して再生成する

- 軸: P5
- ルール: 描画または検査が失敗したら、示されたルールIDを引き、構造化原本を直して build と check を再実行する。描画環境が無ければ不足する実行経路を報告して待ち、PNGなしを完成扱いにしない。
- 理由: 壊れた図や未生成の図を納品しないため。
- 決め方: 機械で守らせられる答え
- 守らせ方: doc: SKILL.md の手順5と6、scripts/document.py のエラー出力
- 機械化しない理由: 痕跡が残らない：失敗後の対処の順序は出力だけでは分からない
- 良い例:

  ```text
  構文エラーを直して再描画する
  ```
- 悪い例:

  ```text
  未生成の図を空欄にしてfinishする
  ```

## OUT-01 実行記録の下へ一組で出力する

- 軸: O1
- ルール: {run}/out/ に requirement-document.json、requirement-document.html、manifest.json を各1件、diagrams/ に同名の .mmd と .png を図ごとに出力する。図は context・usecase・workflow を各1件以上持つ。
- 理由: 読者がHTMLを1件開き、原本と画像も再利用できるため。
- 決め方: 機械で守らせられる答え
- 守らせ方: validate: 出力の path・count と scripts/document.py の check
- 良い例:

  ```text
  HTMLと原本とPNGを同じ出力ディレクトリに置く
  ```
- 悪い例:

  ```text
  HTMLだけを保存する
  ```

## OUT-02 全体像から個々の要件へつながるHTMLを作る

- 軸: O2
- ルール: HTMLの章を、概要、用語と前提、対象範囲、全体像と業務、機能要件、品質と制約、未決事項、根拠と補足の順にする。目次・見出し・要件名のリンクを付ける。図の直前に読む目的、直後に要点と関連要件を置く。本文をHTML文字で残し、図のPNGを埋め込み、拡大用画像へのリンクも付ける。各図のMermaid原本を任意に開けるdetailsにも保存する。
- 理由: 前提を覚え続けずに、全体と詳細の関係をたどれるため。
- 決め方: 依頼の指定
- 守らせ方: script, validate: scripts/document.py の build と check、references/html-principles.md
- 良い例:

  ```text
  図と説明を同じfigureに置き、内容が分かる要件名でリンクする
  ```
- 悪い例:

  ```text
  図を巻末へ集め、本文から探させる
  ```

## OUT-03 要点と理由を具体的な文章でつなぐ

- 軸: O3
- ルール: 各節の冒頭で要点を示し、前提、理由、必要な振る舞いをつなぐ。1段落を1論点にし、誰が何をどの条件で行うかを書く。用語を統一し、抽象的な美辞麗句、同義反復、根拠のない価値判断を削る。短くするために前提・例外を落とさない。 否定の範囲を明示し、双方拒否と両立禁止の両方に読める文を使わない。
- 理由: 短文だけを並べても意味のつながりが無ければ理解できないため。
- 決め方: 依頼の指定
- 守らせ方: review: references/html-principles.md の1章、Evalのbehavior-1とbehavior-3、完了前チェックリスト
- 機械化しない理由: 意味の判断が要る：文章の要点と因果のつながりは原資料と比較する
- 良い例:

  ```text
  重複があれば確定せず、重複を社員へ表示する
  ```
- 悪い例:

  ```text
  効率化を推進し、利便性の向上を実現する
  ```

## OUT-04 内部IDを表示せず名前で参照する

- 軸: O4
- ルール: sources は SRC-01、actors は ACT-01、requirements は FR-01、diagrams は D-01、open_questions は Q-01 から出現順の連番にする。IDは原本のid・参照配列とHTMLのリンク先属性だけに使う。本文、見出し、リンクの表示名、代替説明、Mermaidへ書かず、要件名・図名・資料名と場所・確認する条件の名前で示す。原資料のquoteは改変しない。生成日時・乱数を加えない。
- 理由: 読者に記号の意味と対応を覚えさせず、内部では参照の対応を検査するため。
- 決め方: 依頼の指定
- 守らせ方: validate: scripts/document.py の原本検査とHTML生成、references/authoring.md の3章
- 良い例:

  ```text
  「空き時間を確認する」から同名の要件へ移動できる
  ```
- 悪い例:

  ```text
  図にFR-01を付け、対応する要件を読者に探させる
  ```

## OUT-05 一つの図と段落で一つの問いを扱う

- 軸: O5
- ルール: 本文は1段落1論点にする。図は1つの問いに絞り、Mermaid原本は図ごとに6000文字以下、PNGは幅・高さ6000px以下かつ2500万画素以下にする。上限を超えるときは、全体図と業務別の詳細図に分け、要件への参照を保つ。
- 理由: 図や文章を縮小して詰め込むと流れが読めなくなるため。
- 決め方: 機械で守らせられる答え
- 守らせ方: validate: scripts/document.py の寸法・原本長検査、references/diagrams.md の3章
- 良い例:

  ```text
  全体図から申請と取消の詳細図へ分ける
  ```
- 悪い例:

  ```text
  巨大な図を小さく縮めて一枚に収める
  ```

## OUT-06 原本と派生出力を同期する

- 軸: O7

- 理由: 古い図が本文に残ることを機械で防ぐため。
- 決め方: 機械で守らせられる答え
- 守らせ方: validate: scripts/document.py の check と together の source・html・manifest
- 良い例:

  ```text
  文だけの変更でもHTMLとmanifestを再生成する
  ```
- 悪い例:

  ```text
  Mermaidを変えて古いPNGを再利用する
  ```

## OUT-07 検査を省く入力を出力へ加えない

- 軸: O8

- 理由: 検査の省略を成果物へ埋め込ませないため。
- 決め方: 機械で守らせられる答え
- 守らせ方: validate: scripts/document.py の原本キーとmanifest検査
- 良い例:

  ```text
  未決事項を記録し、検査は実行する
  ```
- 悪い例:

  ```text
  skip_validationをtrueにする
  ```

## OUT-09 図を目的と材料から選び設計詳細を分ける

- 軸: X2
- ルール: context・usecase・workflow は作成する。state は状態と変化条件、screen は画面と操作経路、domain は業務概念の関係、sequence は外部との順序が材料にあるときに選ぶ。concept のER・classは概念整理に限定する。component は構成が要件に指定された場合だけ選ぶ。9種類すべての採否と理由を diagram_decisions に残す。DBの物理列・メソッド・未決定の実装構造は design_notes へ分ける。
- 理由: 図を増やすこと自体を目的にせず、要件と設計を混ぜないため。
- 決め方: 依頼の指定
- 守らせ方: validate: scripts/document.py の図の種別・選択記録検査、references/diagrams.md の1章
- 良い例:

  ```text

  ```
- 悪い例:

  ```text
  列型やクラスメソッドを要件の主線にする
  ```

## RPT-01 最終の返答は finish の本文をそのまま使う

- 軸: R1
- ルール: 最終の返答は、`run.py finish` が出力した本文をそのまま使い、前後に文を足さず、要約しない。中断したときは、`run.py abort` が出力した本文を同じように使う。決めきれなかったことは、finish の前に `.skill-runs/<name>/notes.md` に「- 」で始まる箇条書きで書く（10 項目まで）。finish がそれを本文の「## 補足」に入れる。
- 理由: 報告の形と中身が AI ごとに分かれない。既定値で決めた値と検証の結果を、読み手が必ず見られる。
- 決め方: 機械で守らせられる答え
- 守らせ方: runtime, validate, review: scripts/run.py の finish と abort が本文を組み立て、.skill-runs/<name>/report.md にも保存する。check と finish が notes.md の形を検査する
- 良い例:

  ```text
  決めきれなかった既定値を notes.md に「- 」で書き、finish の本文をそのまま返答する
  ```
- 悪い例:

  ```text
  finish の本文を要約し直し、最後に自由な文で補足を足して返答する
  ```

## CTL-01 実行は run.py で始めて終える

- 軸: C1
- ルール: 手順の最初に `run.py start`、出力を書いた後に `run.py check`、最後に `run.py finish` を実行する。`finish` が終了コード0で終わるまで、完了と返答しない。
- 理由: 始まりと終わりをスクリプトで区切ると、検査が必ず走り、hooks が実行中かどうかを判定できる。完了の基準が AI ごとに分かれない。
- 決め方: 機械で守らせられる答え
- 守らせ方: runtime, validate: scripts/run.py。finish は契約の検査に通らないと終了コード1で終わる
- 良い例:

  ```text
  `run.py finish` が終了コード0で終わってから、その本文で返答する
  ```
- 悪い例:

  ```text
  出力を書いた直後に「完了しました」と返答する
  ```

## CTL-02 スキル自身の変更制限

- 軸: C2
- 廃止（ID は再利用しない）: ユーザーによる微修正を妨げるため、変更制限と変更後の特別な検査手順を廃止した。

## CTL-03 質問は start の前に済ませる

- 軸: C3, I2
- ルール: ユーザーに聞くことは `run.py start` の前にまとめて聞く。start の後に聞く必要が出たときは、`run.py wait --question <質問>` を実行してから聞く。聞けない状況では既定値を使い、報告の「既定値で決めた値」に載せる。
- 理由: 実行の途中で質問するかどうかが AI ごとに分かれると、出力が揃わない。wait を挟むと、質問のために応答を終えることを hooks が止めない。
- 決め方: 機械で守らせられる答え
- 守らせ方: runtime, doc: scripts/run.py の start は、聞くべき入力が無いと終了コード3で止まり、質問を出力する。wait は hooks の強制を止める
- 良い例:

  ```text
  start の終了コード3で出た質問をユーザーに聞き、答えを `--set` で渡して start をやり直す
  ```
- 悪い例:

  ```text
  出力を半分書いたところで、形式をユーザーに尋ねる
  ```

## CTL-04 hooks は出力の検査だけに使い、入力を止めない

- 軸: C4
- ルール: hooks は、このスキルの実行中（status: active）に、編集の後と応答を終える前に出力を検査する。実行記録への直接の編集は拒否する。実行していないときは何もしない。ユーザーの発言を止めたり書き換えたりしない。
- 理由: スキルの微修正を妨げず、出力の検証結果と実行記録を揃える。
- 決め方: 機械で守らせられる答え
- 守らせ方: runtime: scripts/hook.py。install.py が Claude Code（.claude/settings.json）と Codex（.codex/hooks.json）に登録する
- 良い例:

  ```text
  Stop の hook が、検査に通るまで応答の終了を差し戻す
  ```
- 悪い例:

  ```text
  UserPromptSubmit の hook で、依頼文の書き方が違うと拒否する
  ```

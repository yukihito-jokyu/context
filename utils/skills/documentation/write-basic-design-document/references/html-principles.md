# 前提と採用理由をつなげて読めるHTML

## 1. 要点から設計と理由へ進む（OUT-03）

基本設計書では「何を解くため、どの責務・画面・データ・連携を選ぶか」を説明する。節の冒頭で要点を示し、前提、設計内容、採用理由をつなぐ。1段落を1論点にし、同じ意味を言い換えて繰り返さない。

良い例：「同じ備品の重複予約を確定させないため、重複の判定と登録を予約受付へ集める案とする。同時申込みの採否の順序は未決であり、詳細設計の前に確認する。」

悪い例：「予約受付の高度化と最適化によって、効率的な業務の効率化を実現する。」

独自の英字の略語や内部記号を覚えさせず、「予約受付」「予約の保存先」のように役割の分かる名前を使う。一般的な技術用語は必要な場面で初出の意味を説明する。文章を短くするときも、条件・例外・根拠・未決事項を残す。

## 2. 全体から観点別に読む（OUT-02）

章の順序は、概要、前提と要望、全体構成、画面と操作、データ設計、外部連携、品質と運用、未決事項と詳細設計への引継ぎ、根拠と補足である。目次から移動し、要望名・設計名・図名・質問名・資料名のリンクで往復できる形にする。

本文は検索・コピー・拡大できるHTML文字とし、主な本文と図は最初から表示する。折り畳みは原寸画像、Mermaid原本、図の採否の補足だけに使う。重大な未決事項を概要から隠さない。

## 3. 図と説明を同じ観点へ置く（OUT-02）

各図は、読む目的、図、要点、関連する設計、根拠の順に読める形にする。画面の図は画面と操作、データの図はデータ設計へ置き、すべての図を巻末へ集めない。

図と本文の主体・関係・方向・順序・状態・条件をそろえる。altは「構成図」で済ませず、図を見られなくても何と何がどのようにつながるか分かる文にする。

## 4. 読む操作と見た目

本文の標準文字サイズは17px、行間は1.85、段落幅は44em以内、主領域は1040px以内にする。700px以下では本文を16pxとし、1列にする。原寸の図の表示領域で横スクロールできる形にする。

色だけで入力の事実・設計案・未決を区別せず、文字のラベルを付ける。装飾のアニメーション、カルーセル、図を読むための画面切替を加えない。この数値だけで理解の一致を保証せず、文章と図の意味をEvalで確かめる。

## 5. 生成と検査の根拠

図とその説明を一組にする構造は[HTML Standardのfigureとfigcaption](https://html.spec.whatwg.org/multipage/grouping-content.html#the-figure-element)を参照する。文章の要点、独自略語の回避、図と本文の一致は、dev/eval/eval.jsonで利用者と確かめた価値と事例を根拠にする。

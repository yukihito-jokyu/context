# 基本設計書のMarkdown書式

利用者が示した要件定義書のMarkdownを、読み進め方と記法の参考にする。参考文書の業務・技術・章構成・版番号を基本設計へ転用しない。実行時にその個別ファイルを読めることを前提にしない。

## 冒頭と見出し

- 文書名を最初の`#`見出しにする。続けて基本設計書の目的、今回の設計の要点、読者を書く。
- 「目次」の下に、番号付きの章名と文書内リンクを並べる。
- 章は`## 1. 概要`、節は`### 3.1 予約の判定を受付へ集める`のように番号を付ける。HTMLタグのアンカーや内部IDをMarkdown本文へ挿入しない。
- 版番号は参考文書から流用せず、入力にない版・承認・更新日時を作らない。

## 表と説明文

用語は「用語・意味・根拠」、利用者は「利用者・行うこと・根拠」の表で示す。表には並列に比べられる情報を置き、設計の説明と採用理由はつながりのある段落で書く。セル内の改行と縦棒で表を壊さない。

設計の節は、状態、設計内容、必要な補足、`採用理由：`、元の要望、関連図、確認する条件、根拠の順にする。要件の受入条件だけを列挙して設計の代わりにしない。入力の要望は前提に置き、どの責務・画面・論理データ・連携で実現するかと選ぶ理由を設計の章で示す。

## 図と参照

図は設計する観点の章に置き、次の順に読む形とする。

1. 番号付きの図の見出しと、図を見る目的。
2. 意味を説明した代替テキスト付きのPNG画像。
3. `図を拡大する`と`図の定義を確認する`の相対リンク。
4. `要点：`で始まる、図から読み取る関係・条件・順序。
5. `関連設計：`と根拠への、内容が分かる名前の文書内リンク。

設計から図へ、図から設計へ戻れるようにする。内部の参照IDは表示せず、番号付き見出しから文書内リンクを作る。画像とMermaidは`diagrams/`に同梱し、Markdownを共有するときは出力ディレクトリ一式を渡す。

## 基本設計の範囲

章は概要、前提と要望、全体構成、画面と操作、データ設計、外部連携、品質と運用、未決事項と詳細設計への引継ぎ、根拠と補足の9章とする。参考文書の「機能要件」「基本設計への引き継ぎ」をそのまま採用しない。未決事項には質問と確定できない設計の範囲を残し、物理列・索引・メソッドなどは詳細設計へ引き継ぐ。

MarkdownとHTMLは同じJSON原本から生成し、同じ本文・採用理由・図・未決事項・根拠を持つ。Markdownの表や図の操作リンクと、HTMLの表示用要素は各形式に合わせる。片方を手で編集して内容をずらさない。

# 図と採用理由がつながる基本設計書を書く のルール

## IN-01 対象と課題がある基本設計を扱う

- 軸: I3
- ルール: 要件定義だけ、または実装コード・物理列・メソッドの定義だけを求める依頼では開始せず、対応する作業を案内する。解く課題または対象が会話と資料のどちらにも無ければ、開始前に不足する点をまとめて聞く。対象と課題が分かり、条件だけが未指定か矛盾しているときは、未決事項を残して基本設計のドラフトを作る。
- 理由: 対象不明のまま文章や要件を捏造しないため。
- 決め方: 依頼の指定
- 守らせ方: doc: SKILL.md の手順1、references/authoring.md の1章
- 機械化しない理由: 痕跡が残らない：開始しない判断は出力に残らない
- 良い例:

  ```text
  メモの承認条件の矛盾を未決事項へ残す
  ```
- 悪い例:

  ```text
  対象がないまま機能を提案して確定する
  ```

## IN-02 会話と指定資料から根拠を読む

- 軸: I4
- ルール: 会話、利用者が指定した資料、対象プロジェクトのAGENTS.mdを読む。既存コードは利用者が既存構成の確認を指定したときだけ読む。資料の抜粋と場所をsourcesへ保存し、要望の事実と新しく提案する設計を分ける。
- 理由: AIと読者の前提の差を根拠から埋めるため。
- 決め方: 依頼の指定
- 守らせ方: doc: SKILL.md の手順1、references/authoring.md の1章
- 機械化しない理由: 痕跡が残らない：読んだ資料の全範囲は出力だけでは確かめられない
- 良い例:

  ```text
  議事録の発言と場所を保存する
  ```
- 悪い例:

  ```text
  無関係なコードから業務条件を確定する
  ```

## STEP-01 要望から設計と図を順に作る

- 軸: P1
- ルール: 受付、要望と根拠の整理、4観点の設計と理由の作成、構造化原本、図とHTMLの生成、検査、意味の確認、finishの順に進める。assets/examples/basic-design-document.jsonを構造の見本にする。原本作成用の補助スクリプトは作成手順内で使い終えて削除し、納品物へ残さない。
- 理由: 本文と図を別々に作って食い違うことを防ぐため。
- 決め方: 機械で守らせられる答え
- 守らせ方: doc, template: SKILL.md の手順、assets/examples/basic-design-document.json
- 機械化しない理由: 痕跡が残らない：作業の順序は最終出力だけでは分からない
- 良い例:

  ```text
  先に要件と根拠を整理してから図を生成する
  ```
- 悪い例:

  ```text
  図を先に作って本文の条件を合わせる
  ```

## STEP-02 未指定と矛盾を質問と影響へ結び付ける

- 軸: P2
- ルール: 業務条件や技術が未指定ならopen_questionsへ確認する条件と、決まるまで確定できない設計の範囲を書く。資料が矛盾するときは両方をsourcesへ残し、片方を合意済みとして採用しない。本文と図にある未決の条件を質問と影響範囲へ結び付ける。提案はproposal、入力の事実はstated、未決の設計はopenにし、承認を捏造しない。
- 理由: 質問待ちだけで止まらず、現在分かっている範囲を共有するため。
- 決め方: 依頼の指定
- 守らせ方: review: references/authoring.md の2章、完了前チェックリストで未決事項と図を照合する
- 機械化しない理由: 意味の判断が要る：記述の矛盾と未指定の条件を原資料と比較する
- 良い例:

  ```text
  承認要否は未決と図に示し、確認質問と確定できない予約条件を同じ未決事項へ書く
  ```
- 悪い例:

  ```text
  本文で取消から戻す要否を未決と書き、質問と影響範囲を残さない
  ```

## STEP-03 原本から図とHTMLを一組で生成する

- 軸: P3
- ルール: scripts/document.pyのbuildで構造化原本からMermaid原本・PNG・HTML・manifestを作る。checkで原本の形、参照、画像の実体と同期を確かめる。派生出力を手で差し替えず、原本を直してbuildを実行する。
- 理由: 原本と派生出力の対応を毎回同じ方法で確かめるため。
- 決め方: 機械で守らせられる答え
- 守らせ方: script, validate: scripts/document.py の build と check。出力 html の command 検査
- 良い例:

  ```text
  原本を直して全体を再生成する
  ```
- 悪い例:

  ```text
  PNGだけ差し替え原本を残す
  ```

## STEP-04 既存のローカル描画環境を使う

- 軸: P4
- ルール: Python 3.9以上、Node.js、既存のmermaid-cli 11以降を使い、doctorで経路と版を確認する。Mermaidはflowchart・stateDiagram-v2・sequenceDiagram・classDiagram・erDiagramを使う。外部画像、クリック、初期化指令を図へ埋め込まず、新規パッケージとリモート描画サービスを自動導入しない。
- 理由: 同じ構文をローカルで変換し、環境による未検証の代替図を防ぐため。
- 決め方: 出力を使う道具や形式の公式の決まり
- 守らせ方: doc: scripts/document.py の doctor と build、references/diagrams.md の2章
- 機械化しない理由: 痕跡が残らない：コマンドの選択は最終出力から全て分からない
- 良い例:

  ```text
  既存mmdcで原本をPNGへ変換する
  ```
- 悪い例:

  ```text
  PNGの代わりにMermaid文字列だけを載せて完了する
  ```

## STEP-05 失敗の原因を直して検査し直す

- 軸: P5
- ルール: buildまたはcheckが失敗したら、示されたルールIDに従って原本を直し、buildとcheckを実行し直す。描画の実行経路か起動権限が無ければ、環境が用意する承認手順を使う。使えないときは不足する経路を報告して質問待ちにし、PNGが無い状態を完成としない。
- 理由: 壊れた図や未生成の図を納品しないため。
- 決め方: 機械で守らせられる答え
- 守らせ方: doc: SKILL.md の手順5と6、scripts/document.py のエラー出力
- 機械化しない理由: 痕跡が残らない：失敗後の対処の順序は出力だけでは分からない
- 良い例:

  ```text
  構文エラーを直して再描画する
  ```
- 悪い例:

  ```text
  未生成の図を空欄にしてfinishする
  ```

## OUT-01 原本と派生出力を同じ場所へ出す

- 軸: O1
- ルール: {run}/out/へbasic-design-document.json・basic-design-document.html・manifest.jsonを各1件、diagrams/へ同名の.mmdと.pngを図ごとに出力する。context・component・workflow・dataの図を各1件以上作る。
- 理由: 読者がHTMLを1件開き、原本と画像も再利用できるため。
- 決め方: 機械で守らせられる答え
- 守らせ方: validate: 出力の path・count と scripts/document.py の check
- 良い例:

  ```text
  HTMLと原本とPNGを同じ出力ディレクトリに置く
  ```
- 悪い例:

  ```text
  HTMLだけを保存する
  ```

## OUT-02 全体から観点別に読める構造を作る

- 軸: O2
- ルール: HTMLの章は、概要、前提と要望、全体構成、画面と操作、データ設計、外部連携、品質と運用、未決事項と詳細設計への引継ぎ、根拠と補足の順にする。設計ごとに観点、設計内容、採用理由、状態、要望・図・質問・根拠への参照を持つ。図は各観点の章へ置き、直前に読む目的、直後に要点を示す。検索できる本文、PNGの埋め込み、代替説明、原寸表示、Mermaid原本のdetails、目次と名前のリンクを付ける。
- 理由: 前提を覚え続けずに、全体と詳細の関係をたどれるため。
- 決め方: 依頼の指定
- 守らせ方: script, validate: scripts/document.py の build と check、references/html-principles.md
- 良い例:

  ```text
  図と説明を同じfigureに置き、内容が分かる要件名でリンクする
  ```
- 悪い例:

  ```text
  図を巻末へ集め、本文から探させる
  ```

## OUT-03 短い文章と分かる名前で説明する

- 軸: O3
- ルール: 各節の要点を先に示し、前提から設計と採用理由へ説明をつなぐ。1段落を1論点にし、主体・条件・結果を具体的に書く。同義反復、抽象的な美辞麗句、独自に作った英字の略語を本文・見出し・図・リンクの表示名へ出さない。一般的な技術用語は使うときに初出で意味を説明する。必要な前提・例外・未決事項を短縮のために落とさない。
- 理由: 短文だけを並べても意味のつながりが無ければ理解できないため。
- 決め方: 依頼の指定
- 守らせ方: review: references/html-principles.mdの1章、Evalのbehavior-3とbehavior-4、完了前チェックリスト
- 機械化しない理由: 意味の判断が要る：文章のつながりと、略語が文書独自のものかは原資料と文脈で判断する
- 良い例:

  ```text
  重複を確定させないため、予約受付で日時を照合する案を示す
  ```
- 悪い例:

  ```text
  独自のRCPで最適化を高度化し、効率的な価値を実現する
  ```

## OUT-04 連番の内部IDを表示へ出さない

- 軸: O4
- ルール: sourcesはSRC-01、actorsはACT-01、requirementsはREQ-01、designsはDES-01、diagramsはD-01、open_questionsはQ-01から出現順の連番にする。IDは原本のid・参照配列とHTMLのリンク先属性だけに使い、本文・見出し・リンクの表示名・代替説明・Mermaidの表示ラベルへ出さない。原資料のquoteは改変しない。生成日時と乱数を加えない。
- 理由: 読者に記号の意味と対応を覚えさせず、内部では参照の対応を検査するため。
- 決め方: 依頼の指定
- 守らせ方: validate: scripts/document.py の原本検査とHTML生成、references/authoring.md の3章
- 良い例:

  ```text
  「空き時間を確認する」から同名の設計へ移動できる
  ```
- 悪い例:

  ```text
  図にFR-01を付け、対応する要件を読者に探させる
  ```

## OUT-05 問いごとに図と段落を分ける

- 軸: O5
- ルール: 本文は1段落1論点とし、図は1つの問いを扱う。Mermaid原本は図ごとに6000文字以下、PNGは幅と高さ6000px以下かつ2500万画素以下にする。上限を超えるときは、全体図と処理別の詳細図へ分け、設計への参照を保つ。
- 理由: 図や文章を縮小して詰め込むと流れが読めなくなるため。
- 決め方: 機械で守らせられる答え
- 守らせ方: validate: scripts/document.py の寸法・原本長検査、references/diagrams.md の3章
- 良い例:

  ```text
  全体図から申請と取消の詳細図へ分ける
  ```
- 悪い例:

  ```text
  巨大な図を小さく縮めて一枚に収める
  ```

## OUT-06 原本とHTMLと画像を同期する

- 軸: O7

- 理由: 古い図が本文に残ることを機械で防ぐため。
- 決め方: 機械で守らせられる答え
- 守らせ方: validate: scripts/document.py の check と together の source・html・manifest
- 良い例:

  ```text

  ```
- 悪い例:

  ```text
  Mermaidを変えて古いPNGを再利用する
  ```

## OUT-07 検査を省く項目を原本へ加えない

- 軸: O8
- ルール: 原本とmanifestは定義したキーだけを持つ。skip_validation、ignore_errors、自己申告の検証済みを受け付けず、検査は原本と派生出力の実体で行う。
- 理由: 検査の省略を成果物へ埋め込ませないため。
- 決め方: 機械で守らせられる答え
- 守らせ方: validate: scripts/document.py の原本キーとmanifest検査
- 良い例:

  ```text
  未決事項を記録し、検査は実行する
  ```
- 悪い例:

  ```text
  skip_validationをtrueにする
  ```

## OUT-08 要望から設計と根拠をたどれるようにする

- 軸: X1
- ルール: sourcesへ資料名・場所・実際の記述の抜粋を保存する。各要望から設計、設計から図と根拠、図から設計と根拠をたどれる参照を持つ。未決の設計は対応する質問を参照し、HTMLでは内容が分かる名前をリンクの表示名にする。入力に無い条件を合意済みの事実として書かない。
- 理由: AIが見た根拠を読者も確認できるため。
- 決め方: 依頼の指定
- 守らせ方: validate: scripts/document.py の参照・抜粋検査、references/authoring.md の3章
- 良い例:

  ```text
  設計から議事録の発言の抜粋へ移動できる
  ```
- 悪い例:

  ```text
  出典名だけを書き該当記述を示さない
  ```

## OUT-09 設計の観点に合わせて図を選ぶ

- 軸: X2
- ルール: coverageはarchitecture・screen・data・integrationの順に採否と理由を持つ。architectureとdataは採用し、全体構成と責務、処理、データ関係の図を作る。screenを採用したときはscreen、integrationを採用したときはsequenceの図を作る。図の8種類context・component・workflow・screen・data・sequence・state・deploymentの採否と理由をdiagram_decisionsへ残す。画面や外部連携が無いときは理由を示し、未指定のときは未決事項を残す。物理列、索引、メソッドの定義はhandoffへ分ける。
- 理由: 図を増やすこと自体を目的にせず、要件と設計を混ぜないため。
- 決め方: 依頼の指定
- 守らせ方: validate: scripts/document.py の図の種別・選択記録検査、references/diagrams.md の1章
- 良い例:

  ```text
  画面のない夜間処理ではscreenを省き、構成・処理・データ・外部連携の図を作る
  ```
- 悪い例:

  ```text
  図を増やすため、要望のない操作画面を確定した構成へ足す
  ```

## RPT-01 最終の返答は finish の本文をそのまま使う

- 軸: R1
- ルール: 最終の返答は、`run.py finish` が出力した本文をそのまま使い、前後に文を足さず、要約しない。中断したときは、`run.py abort` が出力した本文を同じように使う。決めきれなかったことは、finish の前に `.skill-runs/<name>/notes.md` に「- 」で始まる箇条書きで書く（10 項目まで）。finish がそれを本文の「## 補足」に入れる。
- 理由: 報告の形と中身が AI ごとに分かれない。既定値で決めた値と検証の結果を、読み手が必ず見られる。
- 決め方: 機械で守らせられる答え
- 守らせ方: runtime, validate, review: scripts/run.py の finish と abort が本文を組み立て、.skill-runs/<name>/report.md にも保存する。check と finish が notes.md の形を検査する
- 良い例:

  ```text
  決めきれなかった既定値を notes.md に「- 」で書き、finish の本文をそのまま返答する
  ```
- 悪い例:

  ```text
  finish の本文を要約し直し、最後に自由な文で補足を足して返答する
  ```

## CTL-01 実行は run.py で始めて終える

- 軸: C1
- ルール: 手順の最初に `run.py start`、出力を書いた後に `run.py check`、最後に `run.py finish` を実行する。`finish` が終了コード0で終わるまで、完了と返答しない。
- 理由: 始まりと終わりをスクリプトで区切ると、検査が必ず走り、hooks が実行中かどうかを判定できる。完了の基準が AI ごとに分かれない。
- 決め方: 機械で守らせられる答え
- 守らせ方: runtime, validate: scripts/run.py。finish は契約の検査に通らないと終了コード1で終わる
- 良い例:

  ```text
  `run.py finish` が終了コード0で終わってから、その本文で返答する
  ```
- 悪い例:

  ```text
  出力を書いた直後に「完了しました」と返答する
  ```

## CTL-02 スキル自身の変更制限

- 軸: C2
- 廃止（ID は再利用しない）: ユーザーによる微修正を妨げるため、変更制限と変更後の特別な検査手順を廃止した。

## CTL-03 質問は start の前に済ませる

- 軸: C3, I2
- ルール: ユーザーに聞くことは `run.py start` の前にまとめて聞く。start の後に聞く必要が出たときは、`run.py wait --question <質問>` を実行してから聞く。聞けない状況では既定値を使い、報告の「既定値で決めた値」に載せる。
- 理由: 実行の途中で質問するかどうかが AI ごとに分かれると、出力が揃わない。wait を挟むと、質問のために応答を終えることを hooks が止めない。
- 決め方: 機械で守らせられる答え
- 守らせ方: runtime, doc: scripts/run.py の start は、聞くべき入力が無いと終了コード3で止まり、質問を出力する。wait は hooks の強制を止める
- 良い例:

  ```text
  start の終了コード3で出た質問をユーザーに聞き、答えを `--set` で渡して start をやり直す
  ```
- 悪い例:

  ```text
  出力を半分書いたところで、形式をユーザーに尋ねる
  ```

## CTL-04 hooks で出力を検査する

- 軸: C4
- ルール: hooks は実行中（status: active）に、編集の後と応答を終える前に出力を検査する。実行記録への直接の編集は拒否する。ユーザーの発言を止めたり書き換えたりしない。hooks が無くても run.py check と finish で同じ出力の検査を行う。
- 理由: スキルの微修正を妨げず、出力の検証結果と実行記録を揃える。
- 決め方: 機械で守らせられる答え
- 守らせ方: runtime: scripts/hook.py。install.py が Claude Code（.claude/settings.json）と Codex（.codex/hooks.json）に登録する
- 良い例:

  ```text
  Stop の hook が、検査に通るまで応答の終了を差し戻す
  ```
- 悪い例:

  ```text
  UserPromptSubmit の hook で、依頼文の書き方が違うと拒否する
  ```

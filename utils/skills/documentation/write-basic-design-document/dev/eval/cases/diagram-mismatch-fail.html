図と説明が食い違う例

何を設計するか

紙台帳による予約の重複を防ぐため、社員の申込みを予約受付で検査し、保存する構成を提案する。画面・データ・メール連携の役割をそろえ、詳細設計へ渡す。

会話で確認した要望を根拠とし、以下の構成・画面・データ・連携は設計案として示す。使用する製品と取消期限は未決である。

設計案と選んだ理由

観点設計案理由
構成画面からの申込みを予約受付へ集め、受付判定と登録を一つの単位として扱う。同じ備品への同時申込みでも重複を確定させないため。
画面備品一覧・予約入力・結果確認・自分の予約一覧を分ける。申込みと本人の確認・取消の操作目的を区別するため。
データ予約を社員・備品へ関連付け、開始・終了日時と状態を持たせる。重複の判定と、貸出・返却を含む履歴の確認に必要なため。
外部連携予約の登録完了後に、既存メール基盤へ送信を依頼する。確定した予約の内容を通知するため。

詳細設計へ渡す未決事項

取消をいつまで受け付けるか確認する。決まるまで、取消画面の受付条件を確定できない。

メール送信に失敗した場合の再送方法と予約結果への影響を確認する。決まるまで、連携の失敗時処理と確認画面の表示を確定できない。

利用技術は未指定のため、既存環境と整合する候補を比較して確定する。今回の設計案で採用済みの製品はない。

会話の根拠

紙台帳で重複予約が起きる。社員は備品と開始・終了日時を指定して申し込み、本人が取り消せる。管理担当は貸出と返却を記録する。予約確定メールは既存の社内メール基盤から送る。重複する予約を確定させない。

場所：今回の会話メモ。取消期限、メール送信失敗時の扱い、利用技術の指定はない。

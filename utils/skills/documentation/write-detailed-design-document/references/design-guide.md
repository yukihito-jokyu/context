# 詳細設計の作成と確認

詳細設計は、要件と基本設計にある振る舞いを、実装担当者と試験担当者が同じ条件として扱えるまで具体化する文書である。機能ごとの説明を始める前に、資料の状態と共通の用語を揃える。

## 1. 対象資料と設計の状態

IN-01・IN-02・STEP-04: 指定された要件と基本設計を読み、対象機能、対象外、制約、数値、設計案、判断の記録、未決を抽出する。指定がなければ`design.py inspect --root .`で`docs`直下の一組を列挙する。候補が決まらなければ利用者に対象を聞く。既存の実装を読むのは、利用者が既存実装の反映を求めた場合、または資料がその実装を根拠として指定する場合である。

基本設計は採用済みとは限らない。資料の記載、設計者の提案、採用判断、試験で観測した結果は別の情報として残す。実際に実行していない試験には、期待する結果だけを書く。外部の仕様を使う場合は対象版と公式資料を確認し、確認できない条件を未決へ残す。

`design.py cite --root . --path <資料> --line <開始行> --end-line <終了行> --kind <種類> --id S001`は引用と資料全体のSHA-256を返す。引用の種類は`requirement`、`basic_design`、`decision`、`verification`から選ぶ。要件や基本設計の記載を、種類の指定だけで判断の記録や実施結果へ変えない。

## 2. 共通仕様と文書のつながり

STEP-01・OUT-03・OUT-04: `assets/examples/design.json`を形の見本とし、対象資料から台帳を書く。見本の通知先名、サイズ、状態、DB型を対象システムの仕様としてコピーしない。入力資料にない方式・数値を追加する場合は`decisions`に`proposed`として採用理由を書く。

台帳の`scope`には対象機能を文章で書き、`scope_exclusions`には対象外を列挙する。対象資料の各要件を`requirements`へ登録する。今回の対象外は`out_of_scope`と理由、未決で具体化できない要件は`blocked`と未決・確認条件、設計した要件は`designed`と機能・確認条件を付ける。

共通の責務を`modules`、用語を`terms`、状態と意味を`state_sets`、時刻の単位・基準・判定責任を`time_policy`に置く。画面だけの状態と保存する業務状態、判断の確定と返却の成否、セッションとプロセスの寿命を混同しない。状態名を境界や画面で使うときは共通の状態IDを参照する。

説明は前提、決める条件、その条件による結果の順で書く。節の導入で読者が知っているべき背景を補う。同じ概念を文書ごとに言い換えず、画面の表示名が違うときは対応を明記する。

`review.html`は同じ台帳の値を分野別に閲覧するための窓であり、AIが作った採点結果ではない。責務と機能、境界、物理データ、画面、要件と確認条件、状態と遷移、並行制御、回復、判断、未決と変更を別の節で読める。根拠の引用全文は`evidence.md`で辿る。採用・検証の証拠に分類された原文はHTMLにも載せる。

## 3. 機能を実装と試験へ渡す

OUT-02・OUT-10: `features`の各行を次の六つの節へ展開する。担当者が接続部分と重要な振る舞いを一致させられることを目安にし、全補助関数やコードの各行は先に固定しない。

| 読む順 | 記録する条件 |
| --- | --- |
| 目的と根拠 | 機能が実現する要件、元の記述、担当する責務 |
| 開始条件と入力 | 呼出し元、開始できる状態、境界の入力と制約 |
| 処理の流れ | 検査、権限判定、状態更新、保存、外部呼出しの順序と確定点 |
| 結果 | 呼出し元と画面へ返す値、受付成功と実行成功の違い |
| 異常・競合・中断 | 失敗した場所ごとの確定状態、回復と再試行の条件 |
| 確認方法 | 開始条件・操作・観測結果が揃った確認条件への参照 |

境界の契約は`interfaces`へ置く。両側の担当、項目と型、欠落・null・未知の項目、文字数とバイト数、検査順、版、最大サイズ、出力、エラーと終了値、再送照合、切断後照会を定義する。該当しない項目には理由を書く。HTTPでない入口にHTTPの状態値を強制しない。

OUT-14: 内部・外部の全境界で`request_fields`と`response_variants`に項目を定義する。項目の`path`は入れ子を含む位置、`type`は型、`required`は必須、`nullable`はnull可否、`constraint`は値域と意味である。任意項目には欠落時の意味も記す。応答は成功・失敗・未確認等の`name`ごとに`description`と`fields`を持つ。入力のない操作は空配列と`request_policy`の理由を記し、未知キー・重複キー・欠落の扱いもここに置く。型を本文へ重複して定義せず、`input`と`response`には処理の意味を書く。実アダプターへの写像が未検証でも、提案する契約自体の項目は具体化する。

同じ通信先でも、処理開始・状態照会・結果取得・中止など、許可する状態や副作用が異なる操作は別の境界IDへ分ける。各境界の入力と検査順に、呼出し可能な共通状態、必要な権利、状態更新の有無を書く。機能と回復手順から呼び出す各箇所について、その時点の状態が境界の許可条件を満たすかを照合する。処理開始に必要な実行権を、完了済みの結果の読取りへ無条件に流用しない。

たとえば、開始操作が実行中の権利を確認する設計でも、結果照会は完了済み、回復照会は結果不明の状態から必要になる場合がある。それぞれを許可するか、別経路を用意するかを明示する。これは区別の例であり、この状態名や許可範囲を対象資料へ無条件に持ち込まない。

OUT-15: `state_policy`に許可状態・権利・副作用を書き、`state_effects`に状態定義ID、現在状態、応答のnameに対応する`outcome`、次状態、`transition_id`、理由を書く。状態を変える結果は遷移IDを必須とし、同じ状態を保つ結果は同じfrom・toとnullの遷移IDを使う。状態のない境界は空配列と理由を記す。機械検査は参照の一致を確かめる。許可した全経路の十分性は意味の照合で確かめる。照会をstartingから許可するなら、完了結果でどの遷移へ進むか、またはその結果では状態を保つ理由まで辿る。画面の再取得から再編集・再保存へ戻る経路も省かない。

物理データは`tables`へ置く。列名、型、NULL可否、既定値、主キー・一意制約・参照関係、索引と採用理由、更新と削除の単位、移行と移行失敗時の扱いを記す。設定、呼出しの追跡、実行基盤の会話を同じ寿命と仮定しない。会話本文を保存しない制約があれば、復元の便宜のために保存へ変えない。

OUT-13: 主キーは`primary_key`の列名配列、一意キーは`unique_keys`の列名配列の配列に一度だけ定義する。`key_policy`に構成の理由を記す。列のconstraint、表のconstraints・indexesにはPRIMARY KEY・UNIQUE・主キー・一意の再宣言を書かない。列のキーへの所属は生成側が導出する。複合キーの一つの列を単独一意と扱わない。キーを持たない非関係形式は空配列と理由で示す。値域のCHECKと参照制約は従来の制約へ記す。

画面は`screens`へ置く。項目、入力検査、読込中・保存中・成功・失敗・競合・結果未確認の表示、操作可否、保存結果、フォーカスとキーボード操作、更新通知を定義する。現在値の再取得と、直前の操作の成否を区別する。

図は`diagrams`に置き、順序は`sequence`、状態は`state`、関係は`er`を使う。`mermaid`にはフェンスを含めない。`diagram_notes`に採った図と省いた図の理由、`condition_ids`に図だけでは表せない厳密な条件の参照を記す。図の構文検査と実際の描画確認は別であり、このスキルの字面の検査だけで描画確認済みとは報告しない。

## 4. 競合と途中失敗を確認する

OUT-11: `transitions`に現在状態、イベント、遷移条件、次状態、保存の原子性、通知を記す。`concurrency`には保護するデータ、排他範囲、取得順、確保・解放の時点、上限更新、時刻の境界、勝敗を記す。対象外の枠や期限は、ない理由を書く。

| 観点 | 答えが決まるまで具体化する問い |
| --- | --- |
| 受付と同時再送 | 同じ内容に含める項目は何か。同じ識別子・違う内容をどう返すか。同時到着をどの一意制約か条件付き更新で決めるか。 |
| 同じ会話の順序 | 受付順をいつ採番するか。保存失敗時に番号と受付結果はどうなるか。実行権は誰が持ち、異常終了でどう回収するか。 |
| 追加処理と上限 | 親子の寿命、回数を消費する確定点、拒否と失敗時の返却、循環待ち、実行枠の解放はどうなるか。 |
| 承認と期限 | 画面と保存側のどちらの時刻で判定するか。期限と等しければどうするか。判断と期限監視の勝敗をどこで決めるか。 |
| 確定と通知 | コミット前後、外部送信前後、応答前後で停止したとき、何を確定済みとするか。結果の再送と作業の再実行を区別しているか。 |
| 削除と再起動 | 削除対象、順序、部分失敗、再試行、途中からの再開、停止した子プロセス群の扱いは決まっているか。 |

`recovery`に停止位置、確定済み、残る情報、再開、再試行、呼出し元と画面の結果を記す。外部作用の重複を防げる証拠がないときは、作業の自動再実行で回復したことにしない。

`checks`は正常、異常、境界、競合、再起動の条件を選び、`given`・`when`・`then`で書く。期限の直前・等号・直後、同時更新、保存失敗、切断、再送、停止注入の前提と、観測する値・状態・回数を明記する。実施していない試験は検証成功へ数えない。

## 5. 未決・変更・検査の扱い

STEP-02・STEP-05・OUT-12: `decisions.kind`は`inherited`・`proposed`・`observed`、採用判断は`adoption`、検証状態は`verification`に分ける。採用済みには`decision`の根拠、検証結果には`verification`の根拠を参照させる。根拠の種類だけを変えて条件を満たしたことにしない。

外部検証に依存する未検証の判断は`external_dependency: true`として`issues`へつなぐ。未決には問題、影響する設計、検証する内容、採用できる結果、担当、独立して進める範囲を書く。利用方針が既に選択されている場合は、その方針を何度も問い直さず、開発側が検証の証拠と制約を提示する。

資料間の不一致と変更は`changes`に対象、変更前後、理由、影響、判断の出典と採用状態を記す。変更判断の記録を読めない場合は、承認済みと断定しない。要件本文、用語、図、受入条件が更新済みかも分けて扱う。

OUT-06・OUT-07: 文書は`design.json`から生成し、生成したMarkdownを直接直さない。手書き文書と衝突した場合は元の文書を保持し、利用者に保存先を確認する。台帳を変えたら再生成して、要件・設計・確認条件、状態・保存・画面・返却の対応を読み直す。

OUT-05・OUT-08・OUT-09: 検査のエラーは引用、台帳、生成結果を直して解消する。分量の上限を超えたときは条件を削らず対象の分割を相談する。空欄や仮置きを完成扱いにせず、分からない内容を影響付きの未決へ変える。スキルや検査を緩めて通さない。


## 6. 保存先、項目の図、参照先の引用

保存先は、利用者の明示指定、会話で合意した先、既存設計の先の順に選ぶ。指定と既存文書がなければdocs/detailed-designを使い、選んだ値を報告する。成果物の保存先と.skill-runsの内部記録は別に扱う。

各項目の構造から、その直下のMermaid、同じソースの.mmdと.pngを生成する。横断する図を追加する場合はdiagramsに記し、condition_idsで説明する項目を指定する。図は概要であり、文字を省いたラベルの全文、時刻の等号、保存と競合の条件は同じ項目の表へ残す。PNGを実際に開き、切れ・重なり・読めない文字を確認する。

根拠と関連仕様には、参照先の実際の条件・判断・観測結果を引用する。リンクに資料名やIDしかない状態を避ける。引用は>、要約は要約と明示して原文を変えずに書く。目次、戻る、ファイルのダウンロードは情報の参照とは分ける。

PNG生成には既存のMermaid CLIを使う。DETAILED_DESIGN_MMDCでmmdcまたはcli.js、DETAILED_DESIGN_BROWSERでブラウザーを指定できる。不足や構文エラーの場合は止めて報告し、PNGを作ったことにしない。新たなパッケージを自動取得しない。


## 7. 最後の照合と確認の記録

同じ操作の要求項目・応答・状態・保存・確認条件は、別の記述でも同じ条件にする。

- 条件付き必須は、required=falseだけで終えず、constraintに「outcome=failureでは必須、successでは省略」のように条件を書く。物理列の必須条件と、欠落時に返すエラーにも一致させる。
- errors一覧とresponse_variantsのcode等で返せる値を比較する。停止済みの証拠を要求するなら、どの項目かどの保存済み情報で照合するかも定義する。
- 期限到達時の遷移を追加・変更したら、既存のguard・validation_order・state_policy・state_effects・回復と確認条件も検索し、古い遷移への参照を残さない。
- 状態名は描画の都合で改名しない。必要な改名をする場合は、構造化された状態だけでなく、state_policy・自由記述・手書き図の旧名も検索する。
- 保存失敗は、ロールバックが確定した場合とコミット結果が不明な場合を分ける。後者に「元状態を保つ」というDB状態の断定を付けず、結果を照会するまで未確定として扱う。呼出し元が最後に確認した状態と、保存側の確定状態は別に説明する。

readは台帳の値を省略せず6,000文字以下へ分ける。listで全ページ数を得て、overview・sourcesと10分野の全ページを読み、読んだ範囲を記録する。一度に大量のページを出力して省略された場合は未読に戻す。意味の照合には同じ値をMarkdownとHTMLの両方で繰り返し読む必要はない。項目直下の図と引用の位置は生成したMarkdownで確認する。

sheetsはqa配下へ4図ずつの一覧と、元PNGの対応・ハッシュを作る。確認結果の合格を自動生成する機能ではない。全シートを開き、小さな文字や長い図は元PNGで拡大する。確認後に台帳を変えた場合はrender、sheets、変更したPNGの再確認の順に進め、古い一覧を最後の成果物の確認に使わない。描画用ブラウザーが権限管理で起動できない場合は、環境が提供する正規の権限要求でローカル描画を再試行する。新しいパッケージを取得して迂回しない。

# 領域特化型マルチエージェント連携基盤 基本設計書

本書は、開発者が構成・画面・データ・外部連携の実現方式と採用理由を確認し、未決条件を整理して詳細設計へ進めるための基本設計書である。記載する設計案は、採用承認を示すものではない。

macOS用デスクトップアプリを構築するWailsで画面と仲介を一つのアプリ本体に置き、専用コマンドから専門エージェントへ依頼する。同じ会話は順次処理し、独立した依頼と追加質問は別の実行枠を使う。設計レビューに従い、会話ごとの休止と接続全体の終了を分け、会話全文とSkillの適用は実行基盤・アダプターに委ねる。Wailsは呼び出し関係と状態を表示する。実行期限30分、承認待ち2分、会話休止5分などは選択済みの初期値であり、実装と結合検証は未実施である。

### 3.2 受付から実行までの責務とローカル通信

状態：設計案

仲介サービスの中を、設定管理、依頼受付、実行順序管理、プロセス管理、通信規約の接続、承認管理、保存管理に分ける。外部コマンドは同一ユーザーのローカルソケットから依頼受付へ接続する案とする。

- ローカルソケットにはUnixドメインソケットを使う。これは同じ端末のプロセス間で通信する仕組みであり、依頼と応答は構造化テキストのJSONを1行1件として送る。
- ソケットはユーザーだけが読書きできる一時ディレクトリに置き、親ディレクトリを所有者だけが利用できる権限とする。接続元のOSユーザーを確認する。同じユーザーの任意プログラムからの利用は信頼境界内とする。
- 画面はWailsが提供する画面と本体の連携経路で同じ設定・承認・追跡の責務を呼ぶ。画面から専門エージェントへ直接依頼する入口は設けない。
- 依頼受付で宛先・会話・権限・上限を検査し、受付順と追跡情報を保存してから受付結果を返す。依頼本文と返却結果は受け渡しに必要な間だけメモリに保持し、永続保存しない。実行順序管理は処理枠が空いた依頼だけを接続・会話管理へ渡す。
- 仲介からアダプターへの接続は標準入力・標準出力を使う。通信規約の処理と標準エラーの記録を分離し、通信の読み取りを画面の承認待ちで止めない。
- 通信形式に版番号を持たせ、異なる版では処理を始めず不一致を返す。接続確立は5秒、受付応答は5秒を初期の期限とする。

### 3.3 同じ会話は順次処理し独立した会話を並列に進める

状態：設計案

セッションごとの待機列と1件の実行権を持たせる。別のセッションは並列に実行し、追加質問が回答を待つ間も親セッションの実行権は保持する案とする。

- 到着順は仲介が依頼の保存を確定した順とする。セッション内に単調増加の受付順を付け、同時到着でも一意の順序にする。
- 同じセッションは実行、承認待ち、追加質問の回答待ちを通じて1件だけを処理する。成功・失敗が保存された後、次の依頼を開始する。
- ルート依頼は同時2件を初期値とする。ルート依頼とは、他の依頼に属さない最初の依頼である。追加質問の実行枠は別に6件確保し、親が枠を占めても子を開始できるようにする。
- 各親から同時に動かす追加質問は1件とし、複数届けば受付順に待機させる。深さ3、ルート2件のとき、追加質問用の6枠で各経路を進められる。ルート同時数または最大深さを増やす場合、追加質問枠を両者の積以上とする。
- 同じセッションの待機は32件、全体の待機は100件を上限案とし、超過時は受け付けず容量超過を返す。待機期限は受付から5分、処理期限は実行開始から30分とし、親の残り期限を子も超えない。

### 4.3 承認を対象依頼と期限に結び付ける

状態：設計案

承認待ち一覧と承認詳細を設け、専門エージェント、対象操作、対象ファイルまたはコマンド、関連する依頼、期限を示す。許可と拒否は1回だけ確定する案とする。

- 承認要求を保存した時点から120秒を初期の待ち時間とし、画面が非表示でも計測を始める。アプリ本体から画面を表示して該当する承認詳細へ移動する。
- 人間は提示された単発の許可または拒否を選ぶ。実行基盤が示す選択肢へ対応付け、継続的な許可へ勝手に置き換えない。操作内容が欠けて判断できない要求は許可しない。
- 判断時点で未回答かつ期限前かを保存側で確認し、最初の有効な判断だけを確定する。期限に達した場合は拒否を確定し、遅れて届く許可は適用せず結果を表示する。
- 期限内拒否、期限後拒否、アプリ停止による拒否を追跡記録で区別する。複数の承認がある場合も一括許可は設けず、対象を確認して1件ずつ判断する。
- 画面を閉じる操作は承認の許可にしない。画面表示に失敗しても仲介の期限監視で拒否を返す。承認結果を返せない接続障害は対象依頼の失敗として記録する。
- キーボードのTabで内容とボタンへ移動し、EnterまたはSpaceで選ぶ。初期フォーカスは操作説明へ置き、画面表示直後のEnterだけで許可されないようにする。

### 5.1 管理データと識別子を一つの保存先で扱う

状態：設計案

設定、依頼の追跡記録、実行基盤の会話との対応表を、ローカルファイル型のデータベースであるSQLiteへ保存する案とする。プロジェクト、領域、専門エージェント、Skillを別の概念として管理し、会話全文は保存しない。

- プロジェクト1件に領域が複数、領域1件に専門エージェントが複数所属する。プロジェクトにディレクトリは持たせず、領域に正規化した絶対パスと権限方針を保持する。
- 専門エージェントは役割の説明、実行基盤、アダプター設定、選択したSkill1つ、有効状態、起動設定の版を持つ。同じSkillを複数の専門エージェントから参照できる。Skill本文の独自の版固定は持たない。
- 識別子は種類を示す接頭辞と無作為な128ビット値の小文字16進32桁とする。接頭辞はproject、area、agent、skill、session、request、approvalを使い、後ろをアンダースコアでつなぐ。表示名やパスを識別子にしない。
- プロジェクト間許可は呼び出し元プロジェクトと宛先プロジェクトの組を方向付きで持つ。許可の不存在は拒否、同一プロジェクト内は領域権限を前提に利用可能とする。
- アプリ専用の設定と追跡記録はユーザーのApplication Support配下へ保存し、ユーザーだけが読み書きできる権限とする。実行基盤の会話保存先はその既存機能へ委ねる。ソケットは短いパスを使える一時ディレクトリへ分ける。
- ディレクトリ重複は警告し、存在するディレクトリの正規化とシンボリックリンクの解決結果を表示して保存する。重複を許すことは同じファイルへの並行書き込みを防ぐことを意味しない。
- 設定と追跡記録の更新は仲介からのみ行い、コマンドや画面が保存ファイルを直接編集しない。物理的な列、索引、移行手順、耐障害性の設定は詳細設計へ引き継ぐ。

### 6.1 共通Skillとコマンドの操作を統一する

状態：設計案

専用コマンド名をagent2agentとし、宛先の検索、依頼の送信、状態と結果の取得を分ける。共通Skillはこの操作手順と失敗の読み方を両方の呼び出し元AIへ提供する案とする。

- agent2agent service startはWailsアプリ本体を起動して仲介の準備を待ち、service statusは接続状態を返す。本体の停止は画面の「アプリを終了」から行う。
- agent2agent agents list --source-project &lt;呼び出し元&gt; --project &lt;宛先&gt;は利用可能な領域、専門エージェント、役割、実行基盤、検証状態を返す。projects list --source-project &lt;呼び出し元&gt;で利用可能なプロジェクトの識別子を先に取得できる。許可のない他プロジェクトの詳細は返さない。追加質問では呼び出し元を資格から確定する。
- 最初の依頼例はagent2agent request submit --source-project &lt;呼び出し元&gt; --project &lt;宛先&gt; --area &lt;領域&gt; --agent &lt;専門エージェント&gt; --new-session --kind question --input-file &lt;本文ファイル&gt;とする。監査などは--kind workを使う。
- 継続は--new-sessionの代わりに--session &lt;セッション識別子&gt;を必須とする。両方の指定、両方の省略、指定したプロジェクト・領域・専門エージェントの不整合は受け付けない。本文を標準入力で渡す場合は--input-file -とする。
- submitは受付後に依頼とセッションの識別子を返す。agent2agent request wait --request &lt;識別子&gt;で最終結果を待ち、request show --request &lt;識別子&gt;で現在の状態を取得する。状態と呼び出し関係は追跡記録から確認する。
- コマンドは送信前に受付用識別子を生成し、再照会に使えるよう標準エラーへ出す。--request-keyで同じ識別子を明示でき、同じ内容の再送では新しい実行を始めない。接続切断そのものを再実行の理由にしない。
- 標準出力はコマンド形式の版、状態、依頼、セッション、取得できた結果と失敗を持つJSONに統一する。受付成功・参照成功・実行成功は終了値0、依頼の失敗は1、入力不正は2、接続不可は3とする。submitの成功は作業完了を意味しない。
- 共通Skillは、一覧で役割を確認し、宛先と会話の新規・継続を選び、送信後に待機して結果を読む手順を示す。失敗時の再依頼は呼び出し元が判断し、waitやshowの再実行では作業を再送しない。
- Wailsの利用準備画面から、両実行基盤向けの共通Skill導入先と差分を表示して導入する。既存ファイルを無断で上書きせず、専門エージェント用Skillとは別に版を管理する。専門エージェントにも追加質問用として共通Skillを適用する。
- ルート依頼では呼び出し元プロジェクトを明示し、同一ユーザーのローカル利用として扱う。追加質問では呼び出し資格から呼び出し元を確定し、引数による偽装を認めない。資格の受渡しと実行基盤ごとの導入は結合検証する。
- 最終回答は実行中の通信から受け取り、waitへ渡す間だけメモリに保持する。接続切断後や再起動後の回答再取得は、実行基盤の保存済み会話から対象依頼の回答を識別して取得できるかを検証する。取得できない場合は状態と取得不可の理由を返し、回答を得るために作業を自動再実行しない。

### 8.1 採用版における休止・復元・Skillと権限の結合検証

公開済みのCodex用とClaude用アダプターの終了経路はソースで確認した。採用する実行基盤とアダプターの固定版、認証、休止と接続終了、他会話への影響、Skillの受け渡しと更新反映、領域権限、子コマンドの資格引継ぎを実機で検証する。選択済みの利用方針を再びユーザーに委ねる項目ではなく、開発側が検証結果と制約を提示する作業である。未検証のため採用版と接続共有の実装を確定できない。


### 8.2 会話識別子と結果参照を実行基盤へ委ねる経路

会話全文を独自保存しない前提で、明示した会話の復元と、切断後に対象依頼の回答を実行基盤から再取得できる経路を確認する。仲介の追跡記録が期限切れでも、保存中の会話の継続を妨げない対応表の扱いを具体化する。会話が実行基盤側で削除された場合の検出と表示も確認する。経路が決まるまで回答再取得と対応表の整理方法を確定できない。


### 8.3 macOS上で画面を閉じた後に承認画面を再表示できるか

採用するWails、画面用のライブラリ、実装言語のGo、対応macOSの版を固定し、画面を閉じても本体が動き、承認要求から再表示できることを確認する。現時点では未実施。採用版と配布時の署名方式が決まるまで、終了イベントと画面再表示の実装および配布条件を確定できない。

### 8.5 詳細設計へ引き継ぐ作業

- 実行基盤とアダプターの採用版を固定し、会話ごとの休止、接続全体の終了、他会話への影響、保存済み会話の復元、Skillの読み込みと更新反映、領域権限、子コマンドの資格引継ぎを結合検証して対応表を埋める。
- コマンドとローカル通信の要求・応答、入力サイズ、終了値、再送照合、切断後の状態照会と実行基盤からの回答再取得、取得できない場合の説明を定義する。依頼本文と回答を仲介に永続保存しない条件を守る。
- 論理データから物理列・制約・索引と移行手順を定義する。設定、会話の対応表、呼び出し追跡記録を分け、受付順・上限消費・成否の更新と30日の記録削除、保存失敗時の扱いを具体化する。
- 会話待機列、ルートと追加質問の実行枠、循環待ち、依頼の中止期限、会話休止の判定、接続共有と終了を排他制御へ落とし込む。権限変更や終了との競合、バックグラウンド処理の検出と停止を確認する。
- 画面の入力検査、1つのSkillの編集と割り当て、呼び出し関係と状態の追跡、承認の初期フォーカスと期限競合を具体化する。WailsとmacOSの採用版を固定し、非表示中の仲介・承認再表示・単一起動・配布を検証する。
- 標準端末と実行基盤の測定条件を固定し、選択済みの同時2件と追加質問の深さ3・総回数16を検証する。実際のプロセス数・メモリ・終了時間から接続数や資源上限の実装案を具体化する。

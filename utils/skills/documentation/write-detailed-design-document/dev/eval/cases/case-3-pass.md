# 承認回答と期限処理（追加提案）

対象は承認回答の競合と保存・返却である。以下の状態名と制御は設計案であり、実装・結合検証済みとは扱わない。

[basic-design.mdの引用 27行目](../inputs/agent2agent/basic-design-excerpts.md#L27)

> 判断時点で未回答かつ期限前かを保存側で確認し、最初の有効な判断だけを確定する。

## 状態と共通値

判断状態はpending、allowed、denied。拒否理由はuser、expired、shutdownを別項目にする。返却状態はnot_sent、delivered、failedとし、判断と送達を同じ状態列に押し込めない。DB・状態表・API・画面はこの値を共通定義から参照する。画面の「期限切れ」はdeniedかつ理由expiredの表示名であり、第4の判断状態ではない。

approval_idを主キー、decisionとdeliveryを上記の列挙値制約付きNOT NULL、deadlineとdecided_atをUTCミリ秒とする。pendingではdecided_atはnull、確定済みでは非nullとする。request_idは対応依頼への参照であり、別依頼の承認へ回答できない。返却失敗は依頼の失敗理由としても保存する。

## 更新の責任と勝敗

保存リポジトリが短い書込みトランザクションで判断を確定する。外部通信中は書込みロックを持たない。書込み権を取った後、保存側で時刻tを1回取得する。画面で押した時刻は採用しない。判断時刻と更新の間には外部呼出しを挟まない。

| 現在状態と条件 | 次状態と保存する内容 |
|---|---|
| pendingかつt < deadlineで許可 | allowed、decided_at=t、delivery=not_sent |
| pendingかつt < deadlineで拒否 | denied、理由user、decided_at=t、delivery=not_sent |
| pendingかつt >= deadline | denied、理由expired、decided_at=t、delivery=not_sent |
| allowedまたはdeniedへ再回答 | 更新せず、確定済みの判断を返す |

期限監視と人間の回答は同じ保存処理を通す。pendingを条件にした更新と判断結果の記録を同じトランザクションに含め、1件だけが確定できる。複数の行を扱う処理はrequest_id、approval_idの順に対象を確定し、別の処理でもこの順を使う。期限前に監視処理が起動してもpendingを維持し、期限へ再登録する。

## 確定前後の失敗

コミット失敗では判断未成立としてエラーを返し、許可を外部へ送らない。コミット成功後に送達を試みる。返却失敗では判断を覆さずdelivery=failedを保存し、対応依頼を返却失敗として終える。追跡への失敗記録も保存できなければ永続化未確認の障害として運用へ通知し、成功を返さない。

画面からの同じ回答の再送は保存済みの判断と送達状態を返す。アダプターへ許可を再送してよいかは、その接続の承認要求が同じものとして有効かの検証に依存するため、本案で自動再送しない。外部作用が既に実行された可能性がある場合、作業自体を自動再実行しない。

再起動後は確定済みの判断を保持する。旧接続に残ったpendingはshutdownの拒否へ確定し、旧実行は中断として扱う案とする。復元接続の新しい承認要求は別の識別子で受け付け、旧許可を流用しない。これらのアダプター適用可否は結合検証が必要である。

## 確認条件

- 同時に許可・拒否を送ると1件だけが確定し、後続には同じ確定結果を返す。
- 保存側のtがdeadlineの1ミリ秒前なら許可可能、等しい時刻と1ミリ秒後ならexpiredの拒否になる。
- コミット前、直後、返却直後で停止し、DB判断と送達状態・画面・呼出し元の結果を照合する。返却済みか不明な停止を送達成功と断定しない。
- UIの状態名とAPI・DBの値が対応表と一致し、送達失敗によってallowedがpendingへ戻らない。

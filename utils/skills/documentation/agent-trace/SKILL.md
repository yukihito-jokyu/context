# agent-trace

エージェントの動作を後から追跡できるように記録し、必要なときだけ再現用の簡易手順書へ変換する。ログは事実の保存を目的とし、手順書は目的達成に必要な最短経路の共有を目的とする。

## 保存場所とファイル名

作業対象リポジトリを `<repo-root>` とし、次のディレクトリを作成する。

```text
<repo-root>/.agent-trace/<yyyymmdd-HHmmss>/
├── <task-slug>.md
└── <task-slug>-guide.md
```

- ディレクトリ名はタスク開始時刻を `yyyymmdd-HHmmss` 形式にした値にする。例: `20260914-153045`。
- 時刻はローカル時刻で記録し、同じ時刻に開始したタスクが衝突しないよう、既存ディレクトリがある場合は秒が変わるまで待つか、同一タスクの継続として扱う。
- 秘密情報をディレクトリ名やファイル名に含めない。
- `task-slug` はタスクの目的を短く表す小文字の kebab-case とする。
- `.agent-trace` とセッションディレクトリがなければ作成する。
- 同じセッションで別タスクを扱う場合は、タスクごとに別の `task-slug` を割り当てる。既存ファイルを無関係なタスクで上書きしない。
- 生成物は Markdown のみとする。JSON、HTML、独自形式の補助ファイルは作らない。

## 開始時の処理

Skill が呼び出されたら、ユーザーのタスクに着手する前に次を行う。

1. 作業対象リポジトリ、セッション ID、タスク名、ログパスを確定する。
2. `.agent-trace/<yyyymmdd-HHmmss>/<task-slug>.md` を作成する。既存なら内容を確認し、同じタスクの継続時だけ追記する。
3. 次の初期内容を記録する。

```markdown
# Agent Trace: <task-slug>

## Task

- 目的: <ユーザーの依頼を要約>
- 開始日時: <ISO 8601>
- セッションディレクトリ: <yyyymmdd-HHmmss>
- 作業対象: <repo-root>

## Trace

### 1. 作業開始

- 内容: <開始した理由と最初に確認すること>
```

初期ログを保存した後、通常のタスク実行へ進む。

## 記録する内容

タスクが完了するまで、意味のある作業単位ごとにログへ追記する。記録順は実際の実行順に合わせる。

- 調査: 読んだファイル、確認した仕様、参照した外部リソース。
- 判断: 採用した方針と、その理由。
- 操作: 実行したコマンド、編集したファイル、利用したツール。
- 結果: コマンドや検証の結果、変更の要点。
- 失敗・逸脱: 失敗した操作、計画からの変更、再試行した理由。
- 完了: ユーザーの目的を満たしたこと、確認した検証結果、残課題。

各エントリは次の形式を基本とする。

```markdown
### N. <作業単位>

- 時刻: <ISO 8601>
- 種別: 調査 | 判断 | 操作 | 結果 | 失敗 | 完了
- 内容: <何をしたか>
- 根拠・結果: <確認できた事実>
- 次: <次に行うこと>
```

コマンドを実行した場合は、ログにそのまま記録する。ただし、シェル展開後の秘密情報、アクセストークン、パスワード、Cookie、個人情報などは伏せる。コマンドに秘密情報が含まれる場合は、目的が分かる安全な表現へ置き換える。

ファイルを変更した場合は、相対パスと変更内容を記録する。ユーザーが根拠を確認できるよう、可能ならファイルへの絶対パスと行番号も残す。外部リソースは URL を Markdown リンクとして記録する。

ログは失敗を隠さず時系列の事実として残す。成功した作業だけを残すのは手順書の責務であり、ログでは行わない。

## タスク完了時

ユーザーのタスクが完了したら、ログの末尾に `完了` エントリを追加する。まだユーザーの確認が必要な場合は完了扱いにせず、確認待ちであることを記録する。ユーザーが追加作業を依頼した場合は、同じログへ追記して証跡を継続する。

## 「ログをまとめて」への対応

ユーザーが「ログをまとめて」「手順書にして」「再現手順を出して」など、ログを手順書へ変換する意図を示したら、タスクの到達目的を確認したうえで `.agent-trace/<yyyymmdd-HHmmss>/<task-slug>-guide.md` を作成または更新する。

手順書には、目的達成までの最短の成功経路だけを残す。失敗したコマンド、不要な試行錯誤、迂回経路、採用しなかった案、内部的な迷いは省く。ただし、成功経路の再現に必要な前提条件や注意点は残す。

手順の各項目は必ず連番にし、動詞で始める。コマンドがある項目では、実際に成功したコマンドをコードブロックへ記載する。外部リソースを参照する項目では、リンク形式で記載する。

手順書は次の形式にする。

`markdown

# <目的>の手順書

## 前提

- <必要な環境・権限・入力>

## 手順

1. <最初に行うこと>

   ```sh
   <成功したコマンド>
   ```

2. [<参照先の名称>](URL)を参照する。

3. <次に行うこと>

## 完了条件

- <目的を達成したと判断する条件>

`

手順書の内容はログから確認できる事実だけで構成する。コマンドを短く書き換えて再現性を損なわない。相対パスは手順の実行場所が明確な場合だけ使い、必要なら実行場所を前提に記載する。

## 制約

- ログの追記をタスク後にまとめて行わず、作業と同時に記録する。
- ログと手順書を混ぜない。ログは時系列の証跡、手順書は成功経路の手順とする。
- ユーザーの依頼にない外部送信、公開、削除をログ作成のために行わない。
- 秘密情報を保存しない。
- 手順書を作成したら、対象パスと、ログから失敗経路を除外して最短経路に整理したことをユーザーへ伝える。

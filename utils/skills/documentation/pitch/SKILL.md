# pitch

実装後に、他者やレビュアーが理解しやすい説明資料を作る。

## Purpose

- レビュアー側の未知を減らす。
- 実装内容だけでなく、なぜその変更をしたのかを伝える。
- 確認してほしい点、注意点、未解決事項を明確にする。

## When to Use

- 実装後。
- レビュー前。
- 他者に変更内容を説明する前。
- 合意形成や承認が必要なとき。
- プロトタイプ、仕様、実装ノートをまとめる必要があるとき。

## Inputs

- Prototype。
- Implementation Plan。
- Implementation Notes。
- 実装結果。
- 既知の未解決事項。
- レビューしてほしい点。
- デモやスクリーンショットなどの補助資料。

## Process

1. 変更の背景をまとめる。
2. 実装内容を説明する。
3. 主要な判断理由を説明する。
4. レビュー観点を整理する。
5. 注意点と未解決事項を明示する。
6. 共有しやすい文章にまとめる。

## Outputs

- Pitch / Explainer。
- 背景。
- 変更内容。
- 主要な判断。
- 確認してほしい点。
- 注意点と未解決事項。

## Output Format

```markdown
# Pitch / Explainer

## 1. 背景

- ...

## 2. 変更内容

- ...

## 3. 主要な判断

- ...

## 4. 確認してほしい点

- ...

## 5. 注意点

- ...

## 6. 未解決事項

- ...
```

## Rules

- 実装内容の羅列だけにしない。
- 判断理由を含める。
- レビュー観点を明確にする。
- 他者の未知を埋める資料として作る。

## Anti-patterns

- diffの要約だけを書く。
- 何を確認してほしいかを書かない。
- 未解決事項やリスクを隠す。

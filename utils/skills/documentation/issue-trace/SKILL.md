# issue-trace

Issueを読めば、何を解決し、なぜその対応になり、どこまで確認できたかを他の人が判断できるようにする。情報の必要性を選んでから、記録フォーマットを使う。

## Issueに残す情報

- 問題・背景・影響：なぜ取り組む必要があるか。
- 期待する結果・対象範囲・完了条件：何ができれば終わるか。不具合では再現手順、期待と実際の動作も含む。
- 判断に影響する調査結果・未確定事項：何が分かり、何の確認や判断が必要か。
- 採用した方針・重要な変更・理由：なぜその対応になったか。
- 対応結果・確認根拠・残課題：どこまで解消し、何が残るか。
- 終了・中断の理由と次の対応：なぜ終了するか、この後に何をするか。

これらはIssue全体で理解できるようにし、毎回すべてを再掲しない。読者の理解・判断・再現・引き継ぎに役立つ情報を選び、今回分かったことや変わったことを中心に書く。

## 情報の基準

- 目的・要件・合意事項は、Issue本文とコメントに記録された有効な合意を正とする。本文とコメントが矛盾するときは、後の明示的な合意を確認し、合意を特定できなければ未解決として残す。
- 実装内容と達成状況は、実際のコード、差分、検証結果、実行状態で裏付ける。Issueに完了と書かれていても、現在の実態を確認せず完了と断定しない。
- Issueと実態の食い違いは「Issueとの相違」に記録する。コードに合わせて要件を決め直したり、未合意の案を合意済みにしたりしない。
- 会話で新たに合意された内容を記録するときは、その決定内容と合意の根拠を残す。共有可能な会話リンクがなければ、ユーザーの実際の発言と会話での合意であることを記載する。

## 開始時

1. 対象リポジトリとIssueを特定する。指定番号と現在のリポジトリの組み合わせが曖昧なら、対象だけ確認する。
2. Issue本文、コメント、関連するPR・コミットを読む。GitHubでは、たとえば `gh issue view <number> --repo <owner/repo> --json number,title,body,comments,url,state` で取得する。
3. 適用されるAGENTS.md、Issueテンプレート、プロジェクトの記録ルールを確認する。既存コメントは参考にできるが、それだけで必須項目を増やさない。
4. 依頼範囲を確認する。Issueを進める依頼では次節の手順を使う。記録だけの依頼では作業を開始せず、記録対象の要件と実施済みの作業を対応付ける。後から記録する場合は、残っている根拠で確認できる作業だけを扱い、時刻や経緯を補作しない。
5. [記録フォーマット](references/record-formats.md)を読み、種別と追加項目を選ぶ。

## Issueの進め方

途中から再開する場合は、既存の合意と実態から現在の段階を確認し、未完了の作業から進める。有効な承認を取り直したり、完了済みの段階を形式のために繰り返したりしない。

### 1. 調査

Issueの目的・要件に対して、現状、原因、制約、影響範囲を調べる。事実と仮説を分け、コードや実行結果で確認できることは先に確認する。調査の結論と、計画を決めるために必要な未確定事項を調査記録として保存する。

### 2. 計画

調査結果から、対応する要件、進め方と採用理由、変更・実行の範囲、作業順序、検証方法、完了条件を提示する。人間の判断が必要な点を先に示し、回答を反映して計画をまとめる。

計画の承認が得られるまでは、会話内で検討し、計画記録を投稿しない。承認された最終計画と承認の根拠を一つの計画記録にまとめて保存する。回答ごとの案や修正過程をコメントにしない。既に承認済みの計画がある場合はそれを使う。

### 3. 実装・実行

承認済みの計画とユーザーが許可した操作の範囲で、実装または実行を行い、計画した検証で結果を確認する。変更を伴わない実行も、実施した操作と観測結果を根拠にする。未実施の検証や失敗を成功として扱わない。

実装・実行記録を保存し、人間が確認できる成果物と検証結果を提示する。計画の範囲や完了条件を変える必要が生じたら、理由と影響を会話で示し、変更計画の承認後に計画記録を残してから進める。

### 4. 人間のフィードバックと修正

人間の確認結果を受け、指摘をIssueの要件・合意事項と対応付ける。修正が必要なら、期待と実態の差、原因の確認状況、対応方針を整理し、許可された範囲で修正・再検証して結果を提示する。要件や計画が変わる場合は、計画の段階へ戻って合意する。

修正記録は、修正結果について人間の承認を得た後に、指摘、対応内容、判断理由、検証結果、承認の根拠をまとめて保存する。個々の回答や未承認の修正結果を都度投稿しない。承認を待っている間は会話内で確認を続け、返答がないことを承認とみなさない。

修正不要の確認結果も、確認対象と根拠を残す。実装・実行記録とまとめられる場合は一つの記録に含め、同じ確認結果を独立コメントで繰り返さない。追加の指摘があればこの段階を繰り返す。

### 5. 完了・中断

要件への対応、検証、人間の確認結果、既存記録を照合し、[記録フォーマット](references/record-formats.md)の「到達点・終了・中断」に従って現在の到達点と終了理由をまとめる。残課題は別Issueへの移管先、対象外とした合意、確認待ちなど扱いを区別する。検証成功やPRのマージだけで人間の確認まで完了したとみなさず、未確認の解消や終了理由を推測しない。

中断・引き継ぎでは、確認済みの事実、現在の段階、残事項を記録する。未承認の計画や修正の詳細を、この記録で代わりに投稿しない。必要なら「計画の承認待ち」「修正結果の確認待ち」と状態だけを示す。

## 記録単位

調査、計画、実装・実行、フィードバック、修正は、情報を整理するための種別とする。Issueを進める依頼や継続記録では、重要な発見、合意、結果、残課題や状態の変化があったときに保存する。工程を通過したことだけを投稿理由にしない。単発の記録依頼は、依頼された範囲をまとめる。

計画と修正は、後から記録する場合も承認の根拠を確認してから投稿する。未承認なら会話内の草案に留める。計画や修正に含まれる方針は、その記録へまとめる。独立した方針案の記録依頼では、案・未合意であることを明示する。複数種別をまとめる場合も、承認対象と確認範囲を混同しない。

### 記録を簡潔にする

- 結論を冒頭に置き、後続には判断に必要な根拠・条件だけを加える。既出の要件・計画・検証はリンクし、今回の変更を示す。
- Issueには問題、重要な判断、到達点を残す。差分、変更ファイル、レビュー、CIの詳細はPRや実行結果へリンクし、結論と必要な注意点を要約する。PR提出時もリンク・到達点・新たな残課題で足りれば、それだけを書く。
- 投稿内容の再取得、通常の起動・再試行、コマンド履歴は内部の確認手順とし、原則として独立投稿しない。失敗が再現性、成果物の信頼性、引き継ぎへ影響する場合や、その操作自体が検証対象の場合は残す。
- 重要な合意は内容・対象範囲・根拠を一度示す。同じ承認発言や権限の説明を繰り返さない。
- 文字数を一律に制限しない。重要な判断、失敗、再現条件を削って短くしない。

## 必須・任意項目の選択

次の順で項目を決める。

1. 共通必須情報と、種別ごとの必須情報を満たす。必要なのは情報であり、独立した見出しや段落ではない。短い記録は一段落にまとめてよい。
2. プロジェクトの明示的な記録ルールで指定された項目を追加する。それらは、そのプロジェクトでは必須として扱う。共通必須項目の意味を保てるなら、プロジェクトの見出しや書式に対応付けてよい。
3. 任意項目の選択条件に今回の記録が該当するか確認し、該当するものを追加する。
4. Issueと実態に食い違いがあれば「Issueとの相違」を追加する。
5. 選択しなかった任意項目の見出しは省略する。内容が必須項目に含まれている場合は、同じ説明を繰り返さない。

必要な情報が分からない場合は「未特定」「未確認」「未実施」などと理由を記載する。今回の要件や判断に無関係な未実施事項は列挙しない。残事項がなければ「なし」と示す。要件との関係を特定できない場合も、その事実を残す。

## 根拠の書き方

- 結論を先に述べ、それを支える実際の記述や観測結果を示し、参照先をリンクする。リンク先の何が根拠なのかを短く説明する。
- コードは可能ならコミットSHA固定のファイル・行リンクにする。未コミットの変更は、相対パスと対象箇所、変更の要点、未コミットであることを記載する。GitHubの読者が利用できないローカル絶対パスを唯一の根拠にしない。
- コミットやPRが作成されたら、そのリンクを以後の到達点の記録に含め、一時的な根拠から辿れるようにする。成果物の削除・非公開により再確認できない範囲を明示し、ハッシュだけで品質を再確認できると扱わない。
- 実行結果は、実行した検証と結果を記載する。再現に環境やコマンドが必要なら任意項目を追加する。合格・失敗・未実施を区別し、確認した範囲だけを成功とする。
- 原因や影響が仮説なら、その旨と未確認部分を明示する。ログの全文を貼る代わりに、判断に必要な抜粋と参照先を残す。
- 秘密情報や個人情報を投稿しない。必要な証拠が公開できない場合は、安全な要約と参照制約を残す。

## Issueへの保存

作業の証跡はコメントへ時系列で追記する。Issue本文は最新の要件・合意事項・状況を示す場所とし、本文の更新が依頼やプロジェクトルールに含まれる場合に限り更新する。既存の証跡を現在の状況で上書きしない。過去の誤りを訂正するときは、元のコメントへのリンクと訂正内容を新しい記録に残す。

本文更新が許可されている場合は、重要な変更時に最新の要件・合意・状態を本文へ反映し、経緯はコメントから辿れるようにする。許可されていない場合は、重要な変更時や終了・中断時のコメントへ現在の対象範囲、到達点、残課題と扱い、関連記録へのリンクをまとめる。全コメントを読み返さなくても最新状態が分かる入口にし、既存コメントと別に同じ要約を重複投稿しない。

1. 投稿前にIssueを再取得し、新しい合意と重複記録がないか確認する。
2. 記録内容をMarkdownの一時ファイルへ保存する。本文をシェル文字列へ直接埋め込まず、改行や記号を保つ。
3. Issueへの記録を依頼されている場合は、その範囲で投稿する。草案だけを求められた場合は、草案を提示する。
4. GitHubでは `gh issue comment <number> --repo <owner/repo> --body-file <markdown-path>` で投稿する。他のIssue管理サービスでは、同じ書式と確認手順を対応するAPIやツールで実施する。
5. 投稿されたコメントのURLと本文を再取得し、対象Issue、内容、リンク、改行を確認する。投稿結果が不明な場合は既存コメントを調べてから再試行し、二重投稿を避ける。
6. 投稿に失敗した場合は草案を保持し、未投稿であることと失敗理由を報告する。保存成功と扱わない。

記録の依頼だけでコードの修正や実行を行わない。Issueを進める依頼でも、Issueのクローズ、ラベル変更、Issue本文の更新は、その操作が依頼やプロジェクトルールに含まれる場合に限る。

## 完了報告

要件に対する到達点、判断理由、検証と人間の確認状況、記録した種別とコメントリンクを短く報告する。未投稿の場合は草案の保存先と未投稿理由を示す。タスク自体の完了と、証跡の投稿完了を区別する。

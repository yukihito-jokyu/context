# 記録フォーマット

共通必須項目と種別必須項目は常に残す。任意項目は末尾の選択ルールで追加する。テンプレート中の説明文を実際の内容へ置き換え、任意項目の空見出しは作らない。

## 共通必須項目

| 項目 | 内容 |
|---|---|
| 種別・対象 | 調査／計画／実装・実行／フィードバック／修正／方針決定と、何についての記録か。タイトルで示す。 |
| 要点 | 分かったこと、変更したこと、決めたことと、現在の到達点。冒頭で示す。 |
| 根拠 | 要点を裏付ける実際の記述・観測結果と参照先。種別の各欄に含めてもよい。 |
| 残事項 | 未解決・未対応・未確認の内容と、次に必要な作業。なければ「なし」。 |

## 調査

追加必須項目は「調査した問いと範囲」「確定事項と未確定事項の区別」。

```markdown
## 調査記録：<調べたこと>

### 要点
<調査の結論。確定できていなければ未確定と記載する。>

### 調査した問いと範囲
<何を明らかにするために、どこまで確認したか。>

### 確定事項と根拠
<確認できた事実、実際の記述・観測結果とリンク。確定事項がなければ明記する。>

### 未確定事項と残事項
<仮説や未確認の内容と、それを確認する次の作業。なければ「なし」。>
```

## 計画

人間が承認した最終計画だけを記録する。追加必須項目は「対応する要件と完了条件」「進め方と判断理由」「作業順序と検証方法」「承認の根拠」。

```markdown
## 計画記録：<取り組むこと>

### 要点
<承認された計画の要点と、これから行う範囲。>

### 対応する要件と完了条件
<Issueの要件と該当箇所へのリンク、何をもって対応済みとするか。>

### 進め方と判断理由
<変更・実行の範囲、採用した方針とその理由。>

### 作業順序と検証方法
<依存関係に沿った作業順序と、完了条件の確認方法。>

### 承認の根拠
<最終計画に対する人間の承認発言と参照先。>

### 残事項
<実施予定の作業と未解決事項。なければ「なし」。>
```

## 実装・実行

追加必須項目は「対応したIssueの要件」「変更後の動作または実行結果」「検証状況」。実行のみの場合は、実施した操作と観測結果を記載する。

```markdown
## 実装・実行記録：<行ったこと>

### 要点
<何を実装・実行し、どこまで対応したか。>

### 対応した要件
<Issueの要件の引用または要約と該当箇所のリンク。>

### 実施内容と根拠
<変更後の動作または実行結果、実施した内容、コード・差分・実行結果などのリンク。>

### 検証状況
<確認した条件、実施した検証、結果。未実施なら理由。>

### 残事項
<未対応の要件や未確認事項と、次の作業。なければ「なし」。>
```

## フィードバック

修正を要しない人間の確認結果を記録する。修正がある場合は、次の修正記録へ指摘と確認結果をまとめ、重複投稿しない。追加必須項目は「確認対象と人間の確認結果」「フィードバックの根拠」。

```markdown
## フィードバック記録：<確認したこと>

### 要点
<人間の確認結果と、修正不要と判断した理由。>

### 確認対象と人間の確認結果
<確認した成果物・動作、対応する要件、受け取ったフィードバック。>

### フィードバックの根拠
<実際の確認発言と参照先。返答がない場合は確認済みにしない。>

### 残事項
<未確認の範囲や次の対応。なければ「なし」。>
```

## 修正

修正結果について人間の承認を得てから記録する。追加必須項目は「指摘と期待・実際の動作」「原因の確認状況」「修正内容と判断理由」「検証状況」「承認の根拠」。

```markdown
## 修正記録：<修正した問題>

### 要点
<何を修正し、問題がどこまで解消したか。>

### 指摘と期待・実際の動作
<受け取った指摘、Issueを基準にした期待と観測した問題。その根拠とリンク。>

### 原因の確認状況
<確認できた原因と根拠。仮説なら仮説、分からなければ未特定と記載する。>

### 修正内容と判断理由
<変更した内容、対応方針を選んだ理由と、コード・差分などのリンク。>

### 検証状況
<問題の解消を確認した条件と結果、関連動作の確認状況。未実施なら理由。>

### 承認の根拠
<修正結果に対する人間の承認発言と参照先。>

### 残事項
<未解消・未確認の内容と、次の対応。なければ「なし」。>
```

## 方針決定

追加必須項目は「決定内容」「判断理由」「合意の根拠」。計画や修正に含まれる方針は、それらの承認後の記録へまとめる。独立した方針案の記録を依頼された場合は、案・未合意であることを明示して記録する。

```markdown
## 方針決定記録：<決めたこと>

### 決定内容
<決定内容。案・合意済みなどの状態も示す。>

### 判断理由
<目的・要件との関係と、その方針を採用する理由。>

### 合意の根拠
<決定を裏付けるIssueコメントや実際の合意発言と参照先。未合意ならその旨。>

### 残事項
<未決定の内容や、決定を反映するための次の作業。なければ「なし」。>
```

## 任意項目と選択条件

| 任意項目 | 追加する条件 | 記載する内容 |
|---|---|---|
| 背景・経緯 | Issueや過去の記録だけでは今回の作業理由が分からない。 | 作業に至った事情と関連する過去の記録。 |
| 再現手順・実行環境 | 条件によって結果が変わる、または他者による再確認が必要。 | 手順、コマンド、環境、対象バージョンなど、再確認に必要な条件。 |
| 比較した案・不採用理由 | 複数の有力な案があり、後から判断を見直す可能性がある。 | 比較した案、採否、判断に使った条件。 |
| 影響範囲・互換性 | 他の機能、利用者、API、保存データなどに影響する。 | 影響する対象と内容、確認済み・未確認の区別。 |
| 性能測定 | 性能が要件に含まれる、または性能への影響を判断する必要がある。 | 測定条件、結果、比較対象、測定の限界。未測定ならその旨。 |
| 移行・リリース・切り戻し | 変更を利用可能にするために追加の操作が必要。 | 必要な操作と実施状況、問題発生時の対応。 |
| 画面・図・ログ抜粋 | 文章やコードへのリンクだけでは結果を確認しにくい。 | 結論を支える画像・図・ログの必要な部分と説明。 |
| 次の担当者・期限 | 引き継ぎや期限について合意がある。 | 合意済みの担当者・期限と合意の参照先。推測で割り当てない。 |
| プロジェクト固有項目 | プロジェクトの明示的な記録ルールで指定されている。 | 指定された情報。そのプロジェクトでは必須として扱う。 |

共通・種別必須項目を選んだ後、プロジェクトルールによる必須化、今回の選択条件への該当、の順で確認する。どちらにも当てはまらない任意項目は省略する。選択条件に当てはまるが情報を得られていない場合は、未確認であることと理由を記載する。

## 条件付き必須項目：Issueとの相違

Issueの要件・合意事項と、コード・実際の状態が食い違う場合は、どの種別でも次を追加する。

```markdown
### Issueとの相違
- Issueの要件・合意事項: <実際の記述と該当箇所へのリンク>
- 確認した実態: <コード・観測結果と根拠へのリンク>
- 未解決の判断と次の対応: <何を判断・確認する必要があるか>
```

食い違いを記録しただけで要件変更が合意されたことにはしない。

# remote-tts

文章を音声ファイルにする。まずLAN上の別PCのAPIで生成し、使えなければこのPCのlocal-ttsへ切り替える。
`<remote-tts>`をこのSKILL.mdのあるフォルダ、`<local-tts>`を隣のlocal-ttsスキルのフォルダとして、同梱のクライアントを使う。

```console
python3 "<remote-tts>/scripts/rtts.py" <command> ...
```

直接`curl`で呼ぶより同梱のクライアントを優先する。下の「APIの落とし穴」と切り替えを吸収してあるためで、手で呼ぶと声の取り違えや壊れたヘッダーをそのまま受け取ることになる。

## リモートとローカルの切り替え

`speak`は次の順に動く。

1. リモートのAPIに接続できるか確かめる（最大3回、完全に止まっていれば約21秒で判定）。
2. リモートで生成する。接続の切断と503は間隔を空けて最大3回試す。
3. リモートが使えないと分かったら、**全文を**このPCのlocal-ttsで生成し直す。1本のファイルに2台の音声を混ぜないためで、途中まで生成した分は使わない。

| 状況 | 動き |
|---|---|
| つながらない、途中で切れ続ける、503が続く、401、404、設定がない | ローカルへ切り替える |
| 入力の誤り（400）、`known_voices`にない声、SSML | 切り替えずにエラーで止める。どちらの環境でも直らないため |
| リモートもローカルも失敗 | 両方の理由を出して止まる。リモートの完了分は残るので、後で同じコマンドを実行すれば続きから再開する |

- 結果のJSONの`backend`が`remote`か`local`かを必ず見る。`local`なら**切り替わったことと`fallback_reason`をユーザーに伝える**。
- リモートでの生成を確実にしたいとき（声を揃えたい本番の音声など）は`--no-fallback`を付ける。ローカルへ切り替えず、エラーで止まる。
- ローカルでは次の点が変わる。

| 項目 | ローカルでの違い |
|---|---|
| エンジン | `--engine`（なければ設定の`engine`、それもなければlocal-ttsの既定のVoxCPM2）。結果のJSONの`engine`に出る |
| 時間 | このMac（M4）で1文字あたりOmniVoice約0.3秒、VoxCPM2約0.33秒、S2約1.7秒。どれもモデルの読み込みに別に20〜30秒 |
| 声 | 同じ`myvoice`でも、リモートと同じ声とは限らない（エンジンが違えばなおさら）。S2同士でも基本周波数の中央値がリモート約320 Hz、ローカル約236 Hzだった（1回の比較）。**切り替わった音声は声の違いに注意するようユーザーに伝える** |
| `--speed` | 0.5〜2.0のみ |
| `[laugh]`などの角括弧の表記 | エラーになるので、取り除いてからやり直す |
| 中断からの再開 | できない。最初から生成する |
| サーバー | 切り替えで起動したローカルのエンジンのサーバーは、終了時に自動で止める（メモリを4〜14 GB使うため）。続けて何本も作るなら`--keep-local-server`を付け、最後に下のコマンドで止める |

```console
uv run --project "<local-tts>/tools" local-tts server stop
```

ローカルのエンジンが未セットアップのときは、エラーになる。ソフトの導入（S2はライセンスへの同意も）の承認が必要なので、勝手に進めず[ローカルのセットアップ](references/local-setup.md)に従う。

## 手順

### 1. つながるか確かめる

```console
python3 "<remote-tts>/scripts/rtts.py" check
```

- `backend`が`remote`ならAPIとキーは有効。`local`ならリモートは使えず（`remote_error`に理由）、このPCでは生成できる。どちらも使えなければ終了コード1。
- リモートの合成まで確かめたいときは`--synth`を付ける（約10秒）。
- 設定は`~/.config/remote-tts/config.json`（`base_url`、`api_key`、`voice`、`known_voices`、任意で`engine`）にある。環境変数`RTTS_BASE_URL`・`RTTS_API_KEY`で上書きできる。
- `--engine`を付けると、そのエンジンでの確認になる。
- **リモートのPCがまだ旧版（presenter-tts）なら、APIは`model`を無視してS2で返す。** 結果の`engine_requested`は頼んだエンジンで、実際に使われたエンジンではない。あちらのPCを更新するまでは、`--engine`を付けても声はS2になると伝える。

### 2. 時間を見積もる

```console
python3 "<remote-tts>/scripts/rtts.py" speak --file 原稿.txt --dry-run
```

サーバーを使わず、分割の結果と所要時間の目安を出す。目安はリモートで**1文字あたり約0.85秒**（273文字で233秒）、`estimated_if_local`がローカルへ切り替わった場合の目安。

**見積もりが1分を超えるなら、目安の時間をユーザーに伝えてからBashの`run_in_background`で実行する。** 千字でリモート約14分、4096字では約1時間になる（千字以上は比例で見積もった値で、実測ではない）。

### 3. 音声にする

```console
python3 "<remote-tts>/scripts/rtts.py" speak "こんにちは。" -o out.wav
python3 "<remote-tts>/scripts/rtts.py" speak --file 原稿.txt -o narration.mp3 --gap 0.6
```

| オプション | 意味 |
|---|---|
| `-o` | 出力先。拡張子で形式が決まる（`.wav` `.mp3` `.m4a` `.ogg` `.opus` `.flac`） |
| `--voice` | 登録済みの声。省略時は設定の`voice`（`myvoice`） |
| `--engine` | `omnivoice`・`voxcpm2`・`s2`。リモートにはAPIの`model`として、ローカルには`--engine`として渡す。省略時は設定の`engine`、なければそれぞれの既定 |
| `--speed` | 0.25〜4.0。生成後の音声を伸縮するだけなので、生成時間は変わらない |
| `--gap` | 段落（空行区切り）の間に入れる無音の秒数。間を空けたいときの唯一の手段 |
| `--max-chars` | 1リクエストの文字数（既定300）。通常は変えない |
| `--force` | 既存の出力を置き換える。作り直すと確かめたときだけ付ける |
| `--play` | 完成後に再生する。その場で聞きたいと言われたら付ける |
| `--no-fallback` | ローカルへ切り替えず、エラーで止める |
| `--keep-local-server` | 切り替えで起動したローカルのサーバーを止めずに残す |

- 文字列の代わりに`-`を渡すと標準入力から読む。
- 文の切れ目で分割して順に生成し、1本のファイルに結合する。サーバーも文ごとに生成しているので、分割で読み方は変わらない。
- リモートの生成が途中で止まったら、**同じコマンドをもう一度実行する**。完了した部分は`<出力>.parts/`から再利用される。声と速度と文章が同じなら再生成しない。
- 生成しながら聞く用途には向かない。実時間より遅く、文の単位でまとめて届くため、ファイルを作ってから再生する。

### 4. 渡す

ファイルの場所、音声の長さ、使った声、**生成した環境（リモートかローカルか）**、**聞いて確かめた範囲とまだ聞いていない範囲**を伝える。
こちらには音声が聞こえないので、長さや音量の確認を「聞いて確かめた」ことの代わりにしない。ユーザーに試聴してほしい箇所（数字、英字、固有名詞、長い文）を具体的に挙げる。

## 読み間違いを減らす

モデルは表記から読みを推測するので、原稿を読ませたい形に直してから送る。

| 元の表記 | 書き換え |
|---|---|
| `API`、`goroutine`などの英字 | `エーピーアイ`、`ゴルーチン` |
| `1,280円`、`48ms` | `千二百八十円`、`四十八ミリ秒` |
| `A/B`、`→`などの記号 | 読みを書くか、言葉に置き換える |

SSMLは受け付けない。APIがタグを解釈せず（タグが文章としてモデルに渡り、`<break>`の無音も入らない）、クライアントはタグを含む入力を拒否する。間は`--gap`で入れる。

## APIの落とし穴

クライアントが対処済みのものを含む。自分でコードを書いて直接呼ぶときは、すべて自分で考慮する。

1. **未登録の声でもエラーにならず、別の声で返る。** `voice`の省略、`alloy`などのOpenAI名、打ち間違いはすべてサーバーの既定の声になる（実測で`myvoice`の基本周波数は約320 Hz、既定の声は約123 Hz）。声の一覧を取るAPIもない。必ず`voice`を明示する。クライアントは`known_voices`にない名前を拒否する。
2. **同じ入力でも毎回音声が変わる。** 同じ文の再生成で長さが4%ほど違った。良かった音声は保存し、作り直しに注意する。
3. **同時に送っても順番待ちになるだけで、エラーにならない。** 3件同時で8秒、17秒、27秒に完了した。並列化しても速くならず、長い生成は他の利用者を待たせる。タイムアウトは長くする。
4. **ストリーミングの途中で失敗すると、HTTP 200のまま接続が切れる。** ステータスだけで成功と判断しない（`curl`なら終了コード18、Pythonなら`IncompleteRead`）。
5. **WAVのヘッダーのサイズ欄が`0xFFFFFFFF`になっている。** 読めないツールがあるので、ヘッダーを書き直すか、クライアントを通す。
6. **句読点だけの入力は503になる**（`No speech generated`）。

詳細な測定値、エラーの一覧、OpenAI SDKの例は[api-notes.md](references/api-notes.md)にある。アプリに組み込むコードを書くとき、または挙動の詳細が必要なときに読む。

## うまくいかないとき

ローカルへ切り替わった場合も、次回リモートを使えるように原因を確かめて伝える。

| 症状（`fallback_reason`など） | 対処 |
|---|---|
| `Cannot reach` | APIが止まっている可能性が高い。起動はあちらのPCのセッションでしかできないので、ユーザーに起動を頼む。IPの変更なら設定の`base_url`を直す |
| `HTTP 401` | キーの誤り。あちらのPCで`%LOCALAPPDATA%\local-tts\api-key.txt`（旧版なら`%LOCALAPPDATA%\presenter-tts\api-key.txt`）を確かめてもらい、設定を更新する |
| `HTTP 503` が続く | 合成エンジン側の問題。あちらのPCでの確認を頼む |
| 反応がなく長時間待つ | 他のリクエストの順番待ちの可能性がある |
| 声が違う | `backend`と`--voice`の名前を確かめる。新しく登録した声は設定の`known_voices`に追加する |
| ローカルの生成に失敗 | エラーの1行目と`~/.local/share/local-tts/cache/<エンジン>-server.log`（S2は`s2-server.log`）の末尾を読む。原因が分からないまま再試行を繰り返さない |

## 気をつけること

- **APIキーを報告やファイル、コードに書き写さない。** 設定ファイルか環境変数から読む。知っている人は、この声で何でも話させられる。
- リモートのサーバーは起動中VRAMを約2.4 GB使う。使い終わったら、あちらのセッションで止めるようユーザーに伝える。こちらからは止められない。
- S2 Proは**Fish Audio Research License**で、商用利用には別途契約が必要。業務や収益化に使うと分かったら伝える。OmniVoiceとVoxCPM2はApache-2.0（なりすましや詐欺への使用は禁止）。
- クローンした声で、本人が言っていないことを本人の発言として公開しない。公開・配布するなら、合成音声と示すかどうかをユーザーに確かめる。

## リモートのPCを新しいlocal-ttsにするとき

あちらのPCでlocal-ttsスキルを更新し、`local-tts home migrate --dry-run`で移すものを確かめてから`local-tts home migrate`を実行してもらう（声・設定・APIキーはコピーされ、キャッシュは移動する）。そのあと`local-tts api`で起動し直すと、`--engine`の指定が効くようになる。APIキーは移し替えでそのまま引き継がれる。

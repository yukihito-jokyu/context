# ばらつきの軸とルールの書き方（フェーズ3）

同じ依頼を受けても、AI によって出力が変わる。変わる箇所は、どのスキルでもおおむね同じ種類に分かれる。この種類を「ばらつきの軸」と呼ぶ。フェーズ3では、軸ごとに答えを1つに決め、`dev/spec.json` の `decisions` に書く。決めた答えが「ルール」であり、ルールには ID を振る。

この章は次の順に読む。1章で軸の一覧を見て、2章で軸ごとの答えの選び方を確かめる。3章でルールの書き方と分け方を、4章で ID の振り方を、5章で使ってはいけない語を確かめる。

## 1. 軸の一覧

「覆い方」の列は、その軸に答える場所を示す。

- `spec:<節>`：spec のその節に書く。ルールは書かない
- `decision`：ルールを書く。決めることが無い軸は、`excluded_axes` に軸と理由を書く
- `standard`：`init_skill.py` が標準のルールを足す。書き換えない

| 軸 | 接頭辞 | 名前 | 覆い方 | 決めることの例 |
|---|---|---|---|---|
| T1 | TRG | 起動する依頼 | `spec:triggers.use_when` | どの言い方で起動するか |
| T2 | TRG | 起動しない依頼と代わり | `spec:triggers.not_for` | 紛らわしい依頼と、その代わり |
| T3 | TRG | 自動で起動するか | `spec:triggers.implicit` | 明示したときだけ起動するか |
| I1 | IN | 入力の項目と受け付ける書き方 | `spec:inputs` | キー、型、別名、大文字と小文字 |
| I2 | IN | 聞くか既定値で補うか | `spec:inputs` | `ask` と `default` |
| I3 | IN | 対象外の依頼の扱い | `decision` | 材料が無いとき、範囲外の依頼のとき |
| I4 | IN | 作業の前に読む範囲 | `decision` | 読むファイル、読まないファイル |
| P1 | STEP | 手順の順序 | `decision` | どの順で何をするか |
| P2 | STEP | 分岐の条件 | `decision` | 数や種類で分かれる処理の境目 |
| P3 | STEP | スクリプトに任せる処理 | `decision` | 数える、集める、並べる処理 |
| P4 | STEP | 使う道具とコマンド | `decision` | 使うコマンド、使わないコマンド |
| P5 | STEP | 失敗したときの扱い | `decision` | 中断するか、続けるか |
| O1 | OUT | 出力の置き場と名前 | `decision` | パス、ファイル名、件数 |
| O2 | OUT | 出力の構造 | `decision` | 見出し、行の形、JSON のキー |
| O3 | OUT | 文体と用語 | `decision` | 言語、文末、用語の統一 |
| O4 | OUT | 値の決め方（日付・ID・順序・数値） | `decision` | 日付の形式、並べ順、端数 |
| O5 | OUT | 出力の量 | `decision` | 行数、項目数、文字数 |
| O6 | OUT | 既にあるものの扱い | `decision` | 上書き、追記、別名で保存 |
| O7 | OUT | 一緒に変えるファイルの組 | `decision` | 片方を変えたら必ず変えるファイル（例：変更履歴と版の番号）。契約の `together`（[control-ladder.md](control-ladder.md) の4章） |
| O8 | OUT | 検査を止める記法 | `decision` | lint の無効化コメント、テストの skip、CI を止める記法を出力に書くか |
| R1 | RPT | 最終の返答の形 | `standard` | RPT-01 |
| C1 | CTL | 実行の始まりと終わり | `standard` | CTL-01 |
| C2 | CTL | スキル自身の保護 | `standard` | CTL-02 |
| C3 | CTL | 質問の時機 | `standard` | CTL-03 |
| C4 | CTL | 自動実行（hooks） | `standard` | CTL-04 |
| C5 | CTL | 契約の外の変更 | `standard` | CTL-05 |

作るスキルの種類（`kind`）ごとに、軸の読み替え、追加の軸、重点軸が [skill-profiles.md](skill-profiles.md) に決めてある。追加の軸は `init_skill.py` が `extra_axes` の先頭に入れる。重点軸は `excluded_axes` にできない（`skill_lint.py`）。

一覧にも種類の追加の軸にも無いばらつきを見つけたら、`extra_axes` の最後に `{"axis": "X<続きの番号>", "prefix": "OUT", "name": "<名前>"}` の形で足し、ルールを書く。

ばらつかない軸にはルールを書かない。たとえば、出力を既存のファイルに書かないスキルの O6 は、`excluded_axes` に軸と理由を書く。

## 2. 決めた根拠（basis）の選び方

1つの軸に候補が2つ以上あるときは、次の表を上から順に当てはめ、最初に当たった行の答えを選ぶ。当たった行の `basis` を、ルールの `basis` に書く。同じ依頼から別の AI が作っても、軸ごとに同じ答えを選ぶようにするためである。

| 順 | 当てはめる条件 | 選ぶ答え | `basis` |
|---|---|---|---|
| 1 | 依頼に答えがある | 依頼のとおり | `user` |
| 2 | 後付け（`mode: retrofit`）で、既存のスキルに答えがある | 既存のスキルの書き方 | `existing` |
| 3 | 作業するプロジェクトに決まりがある（設定ファイル、既存の出力、git の履歴） | その決まり。決まりが文書や設定に書かれていなければ、既存の出力の書き方を数え、多数派を決まりとする（同数なら次の行へ）。実行のたびに読み取れるなら、読み取るスクリプトを作る | `project` |
| 4 | 出力を使う道具や形式に公式の決まりがある | 公式の決まり。`dev/research.md` の「使ったルール」にこの ID を書き、出典を示す | `official` |
| 5 | 候補のうち、機械（スクリプト、契約の検査）で守らせられるものがある | 機械で守らせられる答え | `machine` |
| 6 | 候補のうち、道具・スクリプト・入力の項目を増やさないものがある | 増やさない答え | `fewer-tools` |
| 7 | 候補のうち、AI の判断と覚える概念が少ないものがある | 少ない答え | `fewer-concepts` |
| 上のどれでもない | — | 最も普及している答え。`reason` に「好みで決めた」と書く | `common` |

公式の今の決まりと、広く知られた古い書き方が食い違うときは、公式の今の決まりに従う。そのうえで、古い書き方を `bad` に書き、validate で止める（違反例を作る）。AI は古い書き方に引き戻されやすく、文書だけではばらつきが残るからである。

3の「数える」は、目で見て済ませず、grep や `git log` のコマンドで数える。数えた結果は `dev/research.md` の項目に「- 分布：<書き方 A> <件数>、<書き方 B> <件数>（数えたコマンド：`<コマンド>`）」の形で書く。決まりが書かれているときは、数えずに「- 決まり：<書いてあるファイルと場所>」を書く（[research.md](research.md) の3章）。

`skill_lint.py` は、`basis` が表の値であること、`project` なら `dev/research.md` の項目の「使ったルール」にその ID があり、同じ項目に「決まり：」か件数のある「分布：」があること、`existing` は後付けだけで使い、`dev/research.md` の「## 既存のスキル」の「使ったルール」にその ID があること、`official` なら `dev/research.md` の「使ったルール」にその ID があること、`common` なら `reason` に「好みで決めた」があることを確かめる。

## 3. ルールの書き方

ルールは次の項目を持つ。すべての項目を書く。空にしてよいのは `table`（省略可）、`why_not_machine`（機械が確かめる段を含むとき）、`probes`（validate も format も含まないとき）、`split_reason` と `retired`（当てはまらないとき）だけである。

| 項目 | 書くこと |
|---|---|
| `id` | 4章の規則で振った ID |
| `axes` | 答える軸の記号の配列。1つ以上 |
| `title` | ルールの要約。「〜する」「〜しない」で終える1文 |
| `decision` | 決めた答え。読んだ AI が迷わない具体的な値、パス、コマンド、数で書く |
| `table` | 条件で答えが分かれるときの場合分けの表。1行目は見出し、最後の行の1列目は「上のどれでもない」にする |
| `reason` | その答えにした理由。ばらつくと何が困るかを書く |
| `basis` | 決めた根拠。2章の表の `basis` の値 |
| `split_reason` | 同じ最初の軸に、守らせ方も同じルールが既にあるときだけ書く。分けた理由（下の「ルールの数」） |
| `retired` | ルールをやめたときだけ書く。やめた理由（4章） |
| `control` | 守らせ方の段の配列（[control-ladder.md](control-ladder.md) の1章の問いの順で選ぶ） |
| `how` | 守らせ方の具体。スクリプトのパス、契約の検査、レビューで見ること |
| `why_not_machine` | `control` に runtime・format・validate のどれも無いとき、「<種類>：<理由>」の形で書く。種類は `痕跡が残らない`・`意味の判断が要る`・`費用が見合わない` のどれか（[control-ladder.md](control-ladder.md) の1章） |
| `probes` | validate か format を含むとき、違反例の ID の配列（[control-ladder.md](control-ladder.md) の7章） |
| `good` | ルールに従った出力の例 |
| `bad` | ルールに反する出力の例。実際に AI が書きそうなものにする |

場合分けの表は、条件を上から順に当てはめ、最初に当たった行を使う形にする。条件は数、種類、有無のように判定が割れないもので書く。

```json
"table": [
  ["ステージされたファイルの数", "本文"],
  ["1", "書かない（1行目だけ）"],
  ["2〜5", "ファイルごとに1行"],
  ["6以上", "ディレクトリごとに1行"],
  ["上のどれでもない（0）", "IN-01 に従い、書かずに中断する"]
]
```

ルールの数は次の規則で決める。ルールの数が作る AI ごとに変わると、ID がずれ、違反例と指摘が別のルールを指すようになるからである。

- 1つの軸に1つのルールを既定にする
- 同じ軸のルールを分けるのは、(a) 守らせ方の段（`control`）が違う部分がある、(b) 片方だけ破られうる独立した部分がある、のどちらかのときだけにする。(b) で分けたときは、後のルールの `split_reason` に理由を書く（同じ最初の軸で `control` も同じルールが2つあると、`skill_lint.py` が `split_reason` を求める）
- 1つのルールが複数の軸に答えるときは、`axes` に軸を全部書き、ルールは1つにする

## 4. ID の振り方

- 形は `<接頭辞>-<2桁の番号>` である（例：`OUT-03`）
- 接頭辞は、ルールが答える軸の1つ目の接頭辞にする（1章の表）
- 番号は接頭辞ごとに `01` から振る。1章の表の軸の順に並べ、同じ軸の中は書いた順にする
- spec の `status` を一度 `ready` にした後は、番号を振り直さない。新しいルールは、その接頭辞の最後の番号の次にする。違反例や記録が ID を指しているため、振り直すと辿れなくなる。`skill_lint.py` は、`ready` のスキルでは軸の順を確かめない
- 標準のルール（CTL-01〜05、RPT-01）は `init_skill.py` が足す。中身を書き換えない
- 違反例の ID は `<ルールID>-<英小文字>` にする（例：`OUT-03-a`）
- ルールをやめるときは、ルールを消さずに `retired` にやめた理由を書いて残す。ID は再利用しない。違反例、指摘、記録が古い ID を指していても辿れるようにするためである。やめたルールは、軸の網羅と契約から外れ、SKILL.md の「4. ルール」にも出ない（`references/decisions.md` には残る）。番号に欠けがあると `skill_lint.py` がエラーにする

`skill_lint.py --phase 3` が、接頭辞と軸の一致、番号の連続と順序（廃止したルールは順序から外す）、軸の網羅を確かめる。

## 5. 使ってはいけない語

読む AI ごとに解釈が分かれる語は、ルールと SKILL.md に書かない。`skill_lint.py` が検出する。

- 日本語：なるべく、できるだけ、できる限り、可能な限り、可能であれば、極力、適切、適宜、必要に応じ、基本的に、原則として、推奨、望ましい、場合による、場合によって、ケースバイケース、状況に応じ、柔軟に、など、等々、その他、いい感じ、うまく、よしなに
- 英語：should、prefer、preferably、preferred、recommended、appropriate、appropriately、as needed、if possible、generally、usually、etc、where sensible、as appropriate

言い換えの例：

| 使ってはいけない書き方 | 言い換え |
|---|---|
| 必要に応じてテストを足す | 公開関数を変えたときはテストを足す。それ以外は足さない |
| 適切な粒度で書く | 1ファイルにつき1行で書く |
| 日付など | 日付と ID |

「を含む」「ほか」（英語では including、such as）は、列挙が閉じていない可能性があるので `skill_lint.py` が警告を出す。全部を列挙しているなら、そのままでよい。列挙が閉じていないなら、残りを全部書くか、場合分けの「上のどれでもない」の行で扱う。

# Eval 作成（手順3）

手順3では、作るスキルが実現すべき価値をユーザーと確かめ、その価値を満たしたかを判定できる形（Eval）にする。受付から先で決めるルールと手順は、ここで確かめた価値を実現するためのものである。価値を確かめずにルールを決めると、誰が使っても同じ出力になるスキルはできても、その出力がユーザーの役に立つとは限らない。

Eval は、収束テストの課題（`dev/evals.json`）とは別のものである。収束テストは、別の AI が同じ依頼から同じ出力を作るか（ばらつき）を測る。Eval は、出力がユーザーの確かめた価値を満たすか（正しさ）を判定する。

この章は次の順に読む。1章で Eval を作るかを決め、2章でユーザーへの聞き方を確かめて材料を聞き、3章で価値仮説を立てて確定させ、4章で確定した価値を振る舞い・事例・正解の根拠・判定方法に落とし、5章で記録の形を確かめ、6章で Eval 自体を検証する。7章は、Eval を収束テスト（フェーズ6）の採点に使う方法で、フェーズ4とフェーズ6で読む。8章は、Eval を確かめた後に、収束テストの題材をユーザーと決める方法で、手順3の終わりに読む。

## 1. 作るか（入力 `eval`）

Eval を書く前に、`<base>/<name>/` の状態を SKILL.md の OUT-06 の場合分けで確かめ、`mode` を決める。後付けにするかを聞く前に、既にあるスキルの置き場へ書き込まないためである。そのうえで、STEP-06 の表に従って作るかを決める。

| 状況 | 扱い |
|---|---|
| `eval` が `make` で、ユーザーに質問できる | 作る。2章から進める |
| `eval` が `skip` | 作らない。`dev/eval/eval.json` に `skip_reason` だけを書き、「利用者が Eval を省くと指定した」とする |
| ユーザーに質問できない（依頼文だけで動く独立エージェントとして実行している） | 作らない。`skip_reason` に「利用者に価値を確かめられない」と書く。価値はユーザーが確かめるまで確定しないので、AI だけで書いた Eval は残さない |
| 上のどれでもない | `make` と同じにする |

作らないときも、6章の `eval_check.py` を実行する。

## 2. 材料を聞く

### 聞き方

手順3では、ユーザーに聞くことをチャットに書かず、`eval.json` の `questions` に書いて、カタログの「Eval 作成」タブで答えてもらう。タブは、答える前の質問を削る前のスクラッチのカードで隠し、今の質問のカードだけを削って開けるようにする。ユーザーは今の質問だけに集中でき、答えた質問は答えだけを残して畳まれる。材料、仮説の確定、事例の判定への同意、収束テストの題材（8章）など、手順3で聞くことはすべてこの聞き方で聞く。

1. 聞くことを `questions` に書く（形は下の表）。1回に聞くことを、1つの `talk` にまとめる
2. `python3 <skill>/scripts/eval_check.py <base>/<name>` と `python3 <skill>/scripts/catalog.py --project .` を実行する。答えを待っている質問があるあいだ、`eval_check.py` はそのことだけを指摘する
3. `run.py wait --question "<質問の要点>"` を実行してから（CTL-03）、カタログのページ（`.skill-runs/catalog/<name>.html`）の「Eval 作成」タブで答え、「回答をコピー」で写した文をチャット欄に貼るよう、ユーザーに伝える
4. 貼られた文を言い換えずに、`python3 <skill>/scripts/eval_check.py <base>/<name> --answer -` の標準入力に渡す。`eval_check.py` が、質問と貼られた文を `dialog` に `questions.talk` の ID で足し、`questions` を消す
5. 回答を Eval に反映する。カタログは、回答した時の版と比べて、足した項目に「新規」、直した項目に「更新」、変えていない項目に「既存」のラベルを付ける。まだ聞くことがあれば 1 に戻る

| キー | 書くこと |
|---|---|
| `questions.talk` | 回答を記録する対話の ID。まだ `dialog` に無い `talk-<番号>` |
| `questions.items[].title` | 質問の短い名前。回答の文の「Q<番号> <title>:」になる |
| `questions.items[].ask` | 質問の文 |
| `questions.items[].why` | 聞く理由（任意） |
| `questions.items[].refs` | 関係する Eval の項目か、収束テストの題材の ID（任意）。カタログで、その項目へのリンクになる |
| `questions.items[].options` | 選べる答え（任意）。`key`（A、B、C の順）と `text` を書き、選ぶと書き足す答えには `free: true` を付ける。無ければ、書いて答える質問になる |

回答の文で「（まだ答えていない）」となっている質問は、次の `questions` で聞き直す。ユーザーがカタログを開けないときや、チャットに直接答えたときは、質問と答えを言い換えずに `dialog` に書き、`questions` を消す。

### 材料

価値は、抽象的な目的から直接は決めない。次の4種類の具体的な材料から見つける。

| 材料 | `materials` のキー | ID | 聞くこと |
|---|---|---|---|
| 利用場面 | `scenes` | `scene-<番号>` | いつ、何を手元に持って、このスキルを使うか |
| 今の不満や失敗 | `pains` | `pain-<番号>` | 今のやり方（スキル無しで AI に頼む、手で作る）で困っていること、起きた失敗 |
| 望む結果 | `wants` | `want-<番号>` | 出力を受け取った後に、何ができるようになっていればよいか |
| 許容できない結果 | `unacceptable` | `ng-<番号>` | これが起きたら使えない、という出力や動き |

- 4種類は、1つの `questions` にまとめて聞く。ひな形には4種類の質問を書いてあるので、作るスキルに合わせて質問の文を直す
- 依頼文に既に書かれている材料は聞き直さずに材料へ書き、その種類の質問を `questions` から消す
- 材料は、ユーザーの言葉を残して1項目1文で書く。AI の解釈は3章の仮説に書く
- 後付け（`mode` が `retrofit`）なら、元の `<base>/<name>/SKILL.md` を読み、そのスキルで起きた不満や失敗も聞く

## 3. 価値仮説を立てて確定する

1. 材料から価値仮説を `hypotheses` に `hyp-<番号>` の ID で書き、もとにした材料の ID を `from` に書く。利用場面・不満・望む結果の材料は、どれも1つ以上の仮説の `from` に入れる。どの仮説にも入らない材料は、材料から外す
2. 仮説が合っているか、直すところはあるかを、2章の聞き方で聞く。質問の `refs` に仮説の ID を書くと、ユーザーがカタログで仮説を開ける
3. ユーザーが合っていると答えた仮説を、確定した価値として `values` に `value-<番号>` の ID で書く。`from` に仮説の ID、`confirmed_in` にユーザーが確かめた対話の ID を書く。直すと答えたら、仮説を直して聞き直す。退けられた仮説は `hypotheses` に残し、`values` には書かない
4. 価値は、出力を受け取ったユーザーにとっての結果で書く。スキルの作り（使うスクリプト、手順の数）は価値に書かない

## 4. 価値を Eval に落とす

確定した価値ごとに、次の表の順に書く。

| 順 | 書くもの | キー | 決まり |
|---|---|---|---|
| 1 | 外から確かめられる振る舞い | `behaviors[].text` | 出力のファイル・返答・終了の状態を見れば、満たしたかが決まる文にする。AI の考えや、道具を使った順序は書かない。判定するのは結果で、道筋ではない |
| 2 | 判定方法 | `behaviors[].judge` | 下の表で選ぶ |
| 3 | 成功と失敗の事例 | `cases[]` | 振る舞いごとに、成功（`expect: pass`）と失敗（`expect: fail`）を1つ以上ずつ書く。成功の事例だけでは、何でも通す判定方法を見逃す |
| 4 | 正解の根拠 | `cases[].reason` | その事例を成功・失敗とする理由を、振る舞いの文と出力の見本の箇所で、1〜2文で書く。2人が別々に読んでも同じ判定になる文にする。材料を指すときは、ID に中身を添える（例: `pain-1` の「層の境界がわからない」） |

判定方法は、次の表の上から順に当てはめ、最初に当たった行を使う。

| 振る舞いの決まり方 | `judge.type` | 書くこと |
|---|---|---|
| 出力の文字・行・見出し・JSON の形で決まる | `code` | `checks` に、契約の `checks` と同じ書き方の検査（`require`、`forbid`、`headings`、`max_lines`、`min_lines`、`line_length`、`json_schema`、`front_matter`）を書く。`command` は使わない（手順3では、作るスキルのスクリプトがまだ無い）。入力の値は `{in:<キー>}` で書き、事例の `inputs` に値を書く。検査ごとに、`message` に、その検査が確かめることを、正規表現を読まない人にも分かる1文で書く（カタログと判定の結果に出る） |
| 文の意味で決まり、基準の文を読めば AI が判定できる | `model` | `rubric` に、成功と失敗を分ける基準の文を「成功: …。失敗: …。」の形で書く（カタログは、成功と失敗を2行に分けて見せる） |
| 上のどれでもない（ユーザーの好みや業務の知識で決まる） | `human` | `rubric` に、人が判定するときの基準の文を「成功: …。失敗: …。」の形で書く |

`model` と `human` の事例は、判定（成功か失敗か）への同意を2章の聞き方で得て、同意した対話の ID を `agreed_in` に書く。code の判定は6章で機械が見本に当てて確かめ、model と human の判定はユーザーの同意で確かめる。

事例は次の決まりで書く。

- 出力の見本は `dev/eval/cases/` にファイルで置き、`output` に `dev/eval/` からの相対パスを書く。同じ見本を複数の事例で使ってよい
- `situation` に、その出力を作った依頼と入力を書く。状況が同じ事例は、一字一句同じ文にする（カタログは、同じ状況をまとめて1回だけ見せる）
- 許容できない結果（`ng-<番号>`）は、どれも1つ以上の失敗の事例の `covers` に書く。許容できない結果を確かめない Eval は、最も避けたい出力を見逃す

## 5. 記録の形（`dev/eval/eval.json`）

ひな形は `assets/templates/eval.example.json` にある。`<base>/<name>/dev/eval/eval.json` に写して埋める。キーは次の順に並べ、後のキーは前のキーの ID だけを指す。

| キー | 書くこと |
|---|---|
| `skip_reason` | 作らないときの理由（1章）。作るときは空にする |
| `materials` | 2章の4種類の材料 |
| `dialog` | ユーザーへの質問（`asked`）と答え（`answer`） |
| `questions` | 答えを待っている質問（2章の聞き方）。回答を記録すると消える |
| `hypotheses` | 価値仮説（`text`）と、もとにした材料（`from`） |
| `values` | 確定した価値（`text`）、もとにした仮説（`from`）、確かめた対話（`confirmed_in`） |
| `behaviors` | 振る舞い（`text`）、確かめる価値（`value`）、判定するファイルの場所（`target`。フェーズ4で書く。7章）、判定方法（`judge`） |
| `cases` | 事例。振る舞い（`behavior`）、成功か失敗か（`expect`）、状況（`situation`）、入力の値（`inputs`）、出力の見本（`output`）、正解の根拠（`reason`）、確かめる許容できない結果（`covers`）、同意した対話（`agreed_in`） |

## 6. Eval 自体の検証（`eval_check.py`）

`python3 <skill>/scripts/eval_check.py <base>/<name>` を実行し、エラーを0件にしてから受付（手順4）に進む。`eval_check.py` は次を確かめ、結果を `dev/results/eval-check.json` に書く。

| 確かめること | 満たさないと起きること |
|---|---|
| 4種類の材料が、それぞれ1つ以上ある | 価値が具体的な場面から離れる |
| 利用場面・不満・望む結果が、どれも仮説に使われている | ユーザーが話した材料が価値に反映されない |
| 確定した価値が、もとにした仮説と、ユーザーが確かめた対話を持つ | AI の思い込みが価値として残る |
| 価値ごとに振る舞いがあり、振る舞いごとに成功と失敗の事例が両方ある | 判定できない価値や、何でも通す判定方法が残る |
| 許容できない結果が、どれも失敗の事例で確かめられている | 最も避けたい出力を見逃す |
| code の判定が、成功の事例を通し、失敗の事例を落とす | 判定方法そのものが壊れていても気づかない |
| model・human の判定の事例に、ユーザーが同意した対話がある | 判定の基準がユーザーの判断とずれる |
| 答えを待っている質問（`questions`）が無い | ユーザーが確かめていない Eval のまま受付に進む |

`eval_check.py` が失敗したら、Eval（`dev/eval/`）の側を直す。code の判定が成功の事例で落ちるなら、検査が厳しすぎるか、見本が振る舞いを満たしていない。失敗の事例で通るなら、検査が緩いか、見本が振る舞いを破っていない。どちらを直すかは、振る舞いの文と正解の根拠に合わせて決める。

Eval を変えたら、`eval_check.py` を実行し直す。`skill_lint.py --final` は、今の Eval の結果か `skip_reason` を求める（STEP-06）。受付（手順4）では、確定した価値から spec の `purpose` を、利用場面から `triggers.use_when` の依頼の言い方を書く。

## 7. 収束テストでの採点（フェーズ4・6）

Eval は手順3で作って終わりではない。収束テスト（フェーズ6）の各ラウンドで、独立エージェントの出力を Eval で採点する。実際の出力に当てると、手順3では見えなかった Eval 自体の問題（判定のずれや、確かめていない価値）も見つかる。流れは次のとおりで、Eval の問題が見つかる間は 2〜5 を繰り返す。

1. フェーズ4で、振る舞いに判定するファイルの場所（`target`）を書く
2. 各ラウンドの `diff` と `analysis-collect` が、各エージェントの出力を採点する
3. 締め込みで、落ちた判定と、Eval で確かめていない動きの指摘を分類する
4. Eval の疑いか抜けがあれば、次のラウンドに進む前に、ユーザーとすり合わせて Eval を直す。そのラウンドで収束テストを終えるなら、直さずに「結論」に残す（下の「収束テストを終えるとき」）
5. 次のラウンドに進む

### 判定するファイルの場所（`target`）

code と model の振る舞いには、`target` に判定するファイルの場所を、プロジェクトのルートからの相対パスで書く。書き方は出力の契約の置き場（`outputs[].path`）と同じで、`{run}`（実行記録の置き場）、`{in:<キー>}`（入力の値）、`*` を使える。複数のファイルに当たるときは、名前の順で最後のもの（`round-10` は `round-9` の後）を判定する。HTML の一部だけを判定するときは、`#<要素の id>` を付ける。human の振る舞いには書かない（収束テストで採点しない）。

| 例 | 判定するもの |
|---|---|
| `{run}/out/commit-message.txt` | 出力の契約の置き場にある出力 |
| `{in:base}/{in:name}/dev/results/convergence/round-*/report.json` | 最後のラウンドの report.json |
| `.skill-runs/catalog/{in:name}.html#skill-{in:name}-eval` | カタログのページのうち、id がその値の要素 |

`skill_lint.py --phase 4` と `convergence.py prepare` は、`target` の無い code・model の振る舞いがあると止まる（STEP-07）。

### 採点

| 判定方法 | 判定するもの | 結果 |
|---|---|---|
| code | `convergence.py diff` が、`judge.checks` を判定するファイルに当てる | 通過・落ちた |
| model | `analysis-prepare` が、分析役の `record.md` の「Eval の判定」に、振る舞い・基準の文・判定するファイルの中身を入れる。分析役が判定し、`analysis-collect` が取り込む | 通過・落ちた・対象なし |
| human | 判定しない。カタログに「人が確かめる」と並べる | — |

- 判定するファイルが無い出力は「対象なし」にし、落ちたとは数えない。依頼がその出力を求めていない課題があるからである。ただし、ラウンドの全員で対象なしだった振る舞いは確かめられていないので、`skill_lint.py --final` が警告する。そのときは `target` か課題を見直す
- `expect_status` が `unused` の課題（スキルを使わないのが正解のもの）は採点しない
- Eval に落ちた出力がある課題は、ばらつきの基準を満たしていても基準を満たさない（convergence-test.md の4章）。model の判定待ちが残っている間も満たさない
- 結果は `report.json` の課題ごとの `eval`（エージェント → 振る舞い → 結果）と、ラウンドの `eval`（採点に使った Eval のハッシュと対話の数）に入る。カタログの「収束テスト」タブがラウンドごとの採点を、「Eval 作成」タブが最後のラウンドの採点を価値ごとに出す。「Eval 作成」タブに出るのは、最後のラウンドを今の Eval で採点したときだけである

### 分類とすり合わせ

`analysis-collect` が書く `analysis.md` の末尾に、Eval に落ちた判定が並ぶ。締め込みでは、落ちた判定ごとに判定したファイルを開き、STEP-07 の表で分類する。Eval に落ちていなくても、`analysis.md` の動きの指摘の問題を Eval のどの振る舞いも確かめていなければ、Eval の抜けにする。全員が通過しても、抜けがあれば Eval の問題である。

| 分類 | 当てはまるとき | 対処 |
|---|---|---|
| 出力の誤り | 落ちた出力が、確定した価値を満たしていない | 作るスキルの側を直す（ばらつきと同じ締め込み） |
| Eval の疑い | 落ちた出力が確定した価値を満たしている。または判定が課題の状況に合わない | ユーザーとすり合わせて、振る舞い・判定方法・事例を直す |
| Eval の抜け | 動きの指摘の問題を、Eval のどの振る舞いも確かめていない | ユーザーとすり合わせて、振る舞いと事例を足す |

分類は `dev/convergence-report.md` の「## Eval の採点」の節に、全ラウンド分を1つの表で書く。「ラウンド」の列には数字だけを、「課題/エージェント」の列には `report.json` の課題の ID とエージェントを書く。

| ラウンド | 課題/エージェント | 振る舞い | 分類 | 対処 |
|---|---|---|---|---|
| 1 | T1-typical/claude-1 | behavior-2 | 出力の誤り | 手順5に、本文をファイルごとの箇条書きにすると足した |

Eval の疑いか抜けがあれば、落ちた出力と判定の理由を `why` に書いた質問で、Eval をどう直すかを2章の聞き方で確かめる（回答は `dialog` に足される）。4章の順に振る舞い・事例・判定方法を直して、6章の `eval_check.py` のエラーを0件にしてから次のラウンドに進む。AI だけで判定を緩めない。

### 収束テストを終えるとき

そのラウンドで収束テストを終えるとき（convergence-test.md の6章で、ユーザーが続けないと答えたとき、または最終ラウンドで全課題が基準を満たしたとき）は、Eval を直さない。直しても、直した Eval で採点するラウンドが無く、確かめられないまま残るだけだからである。代わりに、疑いと抜けの振る舞いの ID（抜けで振る舞いが無いなら価値の ID）、分類、残した理由を、`dev/convergence-report.md` の「結論」に1件1行で書く。

```markdown
- behavior-3: Eval の疑い。Eval を省くのが正しい課題でも落ちる。最後のラウンドなので直さず、ラウンドを足すときに直す
```

後でラウンドを足すときは、次のラウンドの `convergence.py prepare` が、すり合わせて Eval を直すまで止まる。

次のラウンドの `convergence.py prepare` と `skill_lint.py --final` は、次を確かめる（STEP-07）。

- model の判定待ちが残っていない
- 落ちた判定がすべて表にあり、分類と対処が埋まっている
- 疑いか抜けを書いたラウンドの後に、Eval が変わり、対話が増え、`eval_check.py` に通っている（`skill_lint.py --final` は、最後のラウンドなら、疑いと抜けの ID が「結論」にあることでもよい）
- 最後のラウンドを今の Eval で採点した（`skill_lint.py --final` だけが確かめる。続けないときは、採点していない理由を「結論」に書く）

## 8. 収束テストの題材を決める（手順3の終わり）

収束テスト（フェーズ6）は、作成に関わっていない AI に `dev/evals.json` の題材を解かせ、出力が揃うかを測る。題材がユーザーの使い方から外れていると、揃っても、ユーザーが使う場面で揃うとは言えない。そこで、Eval を確かめた後に、題材の案をユーザーと確かめる。Eval を作らなかったときと、入力 `measure` が `skip` のときは聞かない（題材は手順10で書く）。

1. `<skill>/assets/templates/evals.example.json` を `<base>/<name>/dev/evals.json` に写し、[convergence-test.md](convergence-test.md) の1章の形と規則、[skill-profiles.md](skill-profiles.md) の種類の節の「課題の例」に従って題材を書く。依頼文は、2章で聞いた利用場面と、4章の事例の状況から作る。fixture（`dev/fixtures/basic`）の中身は手順10で作るので、ここでは題材に要るもの（どんなプロジェクトで、何を準備しておくか）を `setup` と依頼文で決める。題材ごとに、その題材で確かめること（`aim`）を1文で書く。カタログの題材の表に出て、ユーザーが題材を確かめるときの手掛かりになる
2. 2章の聞き方で聞く。1つの `talk` に題材ごとの質問を1つずつ書き、`refs` に題材の ID（`T1-typical` など）を書く。質問では、何を試す題材か（よくある依頼、入力を書かない依頼、場合分けの境目の依頼、最後のラウンドだけで使う依頼）を示し、その依頼文と準備でよいか、足りない場面が無いかを聞く
3. 回答を `dev/evals.json` に反映する。カタログの「Eval 作成」タブは、題材を「収束テストの題材」の表に、最後の回答の時の版との違い（新規・更新・既存）のラベルを付けて載せる

合意した後に題材を変えても、検査は止めない。変えた題材には、タブで「更新」のラベルが付く。題材の依頼文を変えたときは、次にユーザーに聞くときに、変えた題材の ID と理由を伝える。

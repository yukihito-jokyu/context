# スキル作成者

新しいスキルを作成し、反復的に改善するためのスキルです。

ユーザーと構成、実物モック、決定論設計、スクリプト生成物、配置、検証方法を段階的に合意し、実装承認後に草案、テスト、評価、独立検証、改善を進めます。既存の草案があれば評価・反復から始め、ユーザーが軽い検討だけを望む場合はそれに合わせます。完成後は、必要に応じてスキル説明の最適化を提案できます。

## ユーザーとのコミュニケーション

コーディング用語への親しみは利用者ごとに異なるため、文脈に合わせて説明します。目安として次のとおりです。

- 「評価」と「ベンチマーク」は境界的ですが、そのまま使って構いません
- 「JSON」と「アサーション」は、説明なしで使う前に、ユーザーがそれらを理解しているという明確な手掛かりを確認してください

理解できるか不確かな用語には短い定義を添えます。「修正案」を提示する場合は、対象ファイル、現在の行番号、置換前の文言、置換後の文言を示します。動作や出力の例だけを修正案とは呼びません。

## スキルを作成する

### 意図を把握する

まずユーザーの意図を理解します。現在の会話には、ユーザーがスキルとして取り込みたいワークフローがすでに含まれていることがあります（例: 「これをスキルにして」と言う場合）。その場合は、使用したツール、手順の順序、ユーザーが行った修正、確認できた入力・出力形式について、まず会話履歴から答えを抽出します。「作りたい」「改善したい」は相談・設計の依頼として扱い、明示的な実装承認とはみなしません。

1. このスキルによってClaudeは何ができるようになるべきか。
2. このスキルはいつトリガーされるべきか（ユーザーのどの表現・文脈か）。
3. 想定する出力形式は何か。
4. スキルが動作することを検証するテストケースを用意すべきか。客観的に検証できる出力（ファイル変換、データ抽出、コード生成、固定されたワークフロー手順）を持つスキルは、テストケースの恩恵を受けます。主観的な出力（文体、アート）を持つスキルには、不要であることが多いです。スキルの種類に応じて適切なデフォルトを提案しますが、決定はユーザーに委ねてください。

### ヒアリングと調査

エッジケース、入力・出力形式、例のファイル、成功基準、依存関係について、会話から確定できない重要事項だけを質問します。この部分を詰め終えるまで、草案やテストプロンプトは書かないでください。

利用可能なMCPを確認します。ドキュメントの検索、類似スキルの発見、ベストプラクティスの確認といった調査に役立つ場合は、可能ならサブエージェントで並行して調査し、そうでなければインラインで行います。ユーザーの負担を減らせるよう、文脈を用意して臨んでください。

### 構成、実物モック、決定論設計、スクリプト生成物、実装の承認

新規作成または変更では、初回回答を目的の短い要約、スキル本体の構成、生成成果物の構成、重要な未確定事項に絞ります。ファイルとディレクトリは箇条書きで列挙せず、スキル本体と生成成果物を分けたtree形式で示します。すり合わせ・検証用ワークスペースの保存先も構成確認で合意し、ユーザーが指定しない場合はGitプロジェクトのルート、Gitプロジェクトでなければ現在の作業ディレクトリに `<skill-name>-workspace/` を配置します。その中では、変更前の固定版を `skill-snapshot/`、反復ごとの修正候補を `candidate-skill/iteration-N/`、実物モックを `mock/`、試作用資材と生成物を `prototype/`、評価定義を `evals/`、反復ごとの評価結果を `iteration-N/` に分離します。ユーザー未指定のCLI引数、依存関係、機能は確定せず提案として扱い、テストや対象外事項など後で確認できる詳細を初回回答へ詰め込みません。

承認対象を曖昧にしないため、次の順で進めます。

1. **構成確認**: 目的、tree、保存先、未確定事項に加え、実物モック、プロトタイプ用スクリプト、入力、各実行の生成物、描画・検証結果、成果物対応表のファイルと保存先を確認する。この了承は列挙したすり合わせ用ファイルの作成だけを許可し、本実装は許可しない。
2. **実物モック確認**: 最終成果物と同じ形式・描画方法で実ファイルを作り、構造、内容、見た目、操作性をユーザーと合意する。合意したモックは比較基準として専用の場所に固定し、後続のスクリプト生成物と混在・上書きしない。
3. **決定論設計確認**: 合意済みの実物モックを基準に、スクリプトで作る範囲と作らない範囲を決める。入力、出力、実行コマンド、処理順序、失敗・上書き時の挙動、再現性の判定方法を示し、スクリプト、AI、ユーザーの責務、固定規則、可変部分、入出力対応を簡潔な表で合意する。未確定事項を勝手に固定しない。この段階では完成版の実装承認を求めず、承認は次段階のプロトタイプ作成・実行だけを許可する。
4. **スクリプト生成物確認**: 決定論設計の承認後、完成版へ進まず、合意済みの専用領域に最小スクリプト、fixture、テンプレートを実際に作って実行する。報告の冒頭で、コードやテンプレートの構造によって保証される部分、同一入力による実行一致で再現性だけを確認した部分、入力やAIに依存する可変部分、未検証・未保証の部分を要約する。続けて「成果物の性質、実際の結果、担保するもの、固定／可変、根拠、未保証部分」を対応づけた保証範囲表を示し、実行結果が一致しただけの性質を仕組みによる保証として扱わない。スクリプトと未加工生成物は実物モックと別のtreeで示し、実行コマンド、入力、処理順序、生成物のtree、描画結果、検証結果、各スクリプトと成果物の対応、mockを生成経路で参照していないこと、生成後に直接編集していないことを報告する。各実行は別のrunディレクトリへ保存し、AIは生成物を直接編集しない。問題があればスクリプト、テンプレート、設定、入力を修正して新しいrunへ再生成し、以前の生成物を残す。同じ入力で2回実行し、明示した可変値を除いてファイル数・名前・配置・順序・必須構造・内容またはチェックサムを比較する。実物モックとスクリプト生成物を別々に提示し、この実物をユーザーが承認するまで次段階へ進まない。
5. **実装承認**: スクリプト生成物の承認後に限り、合意済みの実物モック、責務境界、決定論・可変部分、入出力、実行順序、スクリプトと生成物の対応、再現性結果、実物モックとの差分、完成版で追加する範囲を短く再掲し、`candidate-skill/iteration-N/<skill-name>/` へ候補版を作成・変更する承認を得る。正本への反映承認とは区別する。

構成確認で列挙・承認された実物モック、プロトタイプのスクリプト・入力、run別の未加工生成物、描画・検証・対応表ファイルを除き、実装承認前に候補版や完成版ファイルを作成・変更しません。実装承認後も正本を直接変更せず、変更前のスキルを `skill-snapshot/<skill-name>/` に固定して、候補版を `candidate-skill/iteration-N/<skill-name>/` に作成します。実物モックとスクリプト生成物は別の場所と名称で管理し、生成物を手作業やAIで直接修正しません。承認範囲外の案は、利点、コスト、影響するファイルを添えた追加提案にとどめ、合意内容の変更が必要なら再承認を得ます。相談、レビュー、修正案だけを求められた場合は会話内の提案にとどめます。

### SKILL.mdを書く

構成、実物モック、決定論設計、スクリプト生成物を合意し、実装承認を得た後、ユーザーへのヒアリングに基づき、候補版のSKILL.mdへ次の要素を記入します。

- **name**: スキル識別子
- **description**: トリガーすべき時と、行うことです。これが主要なトリガー機構であり、スキルの機能と、使用すべき具体的な文脈の両方を含めます。「いつ使うか」に関する情報はすべて本文ではなくここに置きます。注: 現在のClaudeには、有用な場面でもスキルを使わない「トリガー不足」の傾向があります。これに対処するため、スキルの説明は少し「積極的」にしてください。たとえば「社内のAnthropicデータを表示する、シンプルで高速なダッシュボードの作り方」ではなく、「社内のAnthropicデータを表示する、シンプルで高速なダッシュボードの作り方。ユーザーがダッシュボード、データ可視化、社内指標に言及する場合、または『ダッシュボード』を明示的に求めていなくても、あらゆる種類の会社データを表示したい場合は必ずこのスキルを使用する」と書けます。
- **compatibility**: 必要なツール、依存関係（任意。必要になることはまれ）
- **スキルのその他の部分 :)**

### スキル執筆ガイド

#### スキルの構成

```
skill-name/
├── SKILL.md（必須）
│   ├── YAMLフロントマター（name、descriptionは必須）
│   └── Markdownの指示
└── 同梱リソース（任意）
    ├── scripts/    - 決定的・反復的なタスク用の実行可能コード
    ├── references/ - 必要に応じてコンテキストへ読み込むドキュメント
    └── assets/     - 出力で使うファイル（テンプレート、アイコン、フォント）
```

#### 段階的な情報開示

スキルは3段階の読み込みシステムを使用します。

1. **メタデータ**（name + description）- 常にコンテキストにある（約100語）
2. **SKILL.md本文** - スキルがトリガーされるたびにコンテキストにある（理想は500行未満）
3. **同梱リソース** - 必要に応じて読み込む（無制限。スクリプトは読み込まずに実行できる）

これらの語数は目安であり、必要なら長くして構いません。

**重要なパターン:**

- SKILL.mdは500行未満に保つ。この上限に近づく場合は、スキルを利用するモデルが次に何を参照すべきか明確に示したうえで、階層を追加する。
- SKILL.mdから参照ファイルを明確にリンクし、いつ読むべきかを案内する。
- 大きな参照ファイル（300行超）には目次を含める。

**ドメイン別の構成**: スキルが複数のドメイン・フレームワークをサポートする場合は、バリエーションごとに整理します。

```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

Claudeは関連する参照ファイルだけを読みます。

#### 驚き最小の原則

言うまでもありませんが、スキルにはマルウェア、エクスプロイトコード、またはシステムセキュリティを損なう可能性のある内容を含めてはいけません。スキルの内容は、説明されている意図の範囲でユーザーを驚かせるものであってはなりません。誤解を招くスキル、無許可アクセス、データ流出、その他の悪意ある活動を促進するよう設計されたスキルの作成依頼には従わないでください。ただし、「XYZとしてロールプレイする」のようなものは問題ありません。

#### 執筆パターン

指示では命令形を優先します。

**出力形式の定義** - 次のように定義できます。

```markdown
## レポート構造

常にこの正確なテンプレートを使用する:

# [タイトル]

## エグゼクティブサマリー

## 主な発見

## 推奨事項
```

**例のパターン** - 例を含めると役立ちます。次のように整形できます（ただし、例に「入力」と「出力」が含まれる場合は、多少形式を変えた方がよいこともあります）。

```markdown
## コミットメッセージの形式

**例 1:**
入力: JWTトークンによるユーザー認証を追加した
出力: feat(auth): JWTベースの認証を実装
```

### 執筆スタイル

新規作成・既存改善とも、目的達成に必要な最小限の指示とリソースで構成します。重複する指示を積み増さず、置換・統合・削除を優先します。既存改善では現在の目的、核となるワークフロー、互換性を先に特定し、構造的な書き直しやファイル削除・置換などの破壊的変更が必要でもそれらを維持します。正しさを差分の小ささより優先しますが、効果が同等なら変更量の少ない案を選びます。指示の理由を説明し、特定の例へ過剰適合しない汎用的な草案にします。

### テストケース

スキルの草案を書いたら、実際のユーザーが言いそうな現実的なテストプロンプトを2〜3件作成します。ユーザーと共有してください（この表現をそのまま使う必要はありません）。「試したいテストケースをいくつか用意しました。これでよいですか、それとも追加しますか？」承認後に実行します。

テストケースは `evals/evals.json` に保存します。まだアサーションは書かず、プロンプトだけを記載してください。実行中に、次の手順でアサーションの草案を作成します。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "ユーザーのタスクプロンプト",
      "expected_output": "期待される結果の説明",
      "files": []
    }
  ]
}
```

完全なスキーマは `references/schemas.md` を参照してください（後で追加する `assertions` フィールドを含みます）。

## テストケースの実行と評価

この節は一続きの手順です。途中で止めないでください。`/skill-test` や他のテスト用スキルは使用してはいけません。

評価ワークスペースの保存先と内部構造は実装承認前に合意します。ユーザーから保存先の指定がなければ、プロジェクトルートの `<skill-name>-workspace/` を使用し、反復ごと（`iteration-1/`、`iteration-2/` など）、テストケースごとに整理しますが、構成確認で合意する前に作成しません。

### 手順 1: すべての実行（スキルありとベースライン）を同じターンで起動する

各テストケースについて、同じターンにサブエージェントを2つ起動します。一方はスキルあり、もう一方はスキルなしです。これは重要です。スキルありの実行を先に起動し、後からベースラインに戻ることはしないでください。すべて同時に起動し、ほぼ同時に完了するようにします。

**スキルありの実行:**

```
このタスクを実行する:
- スキルパス: <path-to-skill>
- タスク: <eval prompt>
- 入力ファイル: <eval files if any, or "なし">
- 出力の保存先: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 保存する出力: <ユーザーが重視するもの — 例: 「.docxファイル」「最終CSV」>
```

**ベースライン実行**（プロンプトは同じですが、ベースラインは文脈に応じて異なります）:

- **新しいスキルを作成する場合**: スキルを一切使いません。同じプロンプトで、スキルパスなしとし、`without_skill/outputs/` に保存します。
- **既存スキルを改善する場合**: 旧バージョンを使います。編集前にスキルをスナップショット（`cp -r <skill-path> <workspace>/skill-snapshot/`）し、ベースラインのサブエージェントにそのスナップショットを指定します。`old_skill/outputs/` に保存します。

各テストケースについて `eval_metadata.json` を書きます（現時点ではアサーションを空にして構いません）。各評価には、単なる「eval-0」ではなく、何を検証するかに基づく説明的な名前を付けます。その名前をディレクトリ名にも使用します。この反復で新規または変更済みの評価プロンプトを使う場合は、新しい評価ディレクトリごとにこれらのファイルを作成してください。前回の反復から引き継がれると仮定してはいけません。

```json
{
  "eval_id": 0,
  "eval_name": "ここに説明的な名前",
  "prompt": "ユーザーのタスクプロンプト",
  "assertions": []
}
```

### 手順 2: 実行中にアサーションの草案を作る

実行の完了をただ待つのではなく、この時間を有効に使えます。各テストケースの定量的なアサーションを草案にし、ユーザーへ説明します。`evals/evals.json` にすでにアサーションがある場合は、見直して何を確認するものか説明します。

優れたアサーションは客観的に検証可能で、説明的な名前を持ちます。ベンチマークビューアで明確に読めるため、結果を一見した人が各アサーションの確認内容をすぐ理解できます。主観的なスキル（文体、デザイン品質など）は定性的に評価する方が適しています。人間の判断が必要なものにアサーションを無理に適用してはいけません。

草案ができたら、`eval_metadata.json` ファイルと `evals/evals.json` をアサーションで更新します。また、定性的な出力と定量ベンチマークの両方について、ビューアで何を確認できるかをユーザーに説明します。

### 手順3: 実行の完了時に時間データを取得する

各サブエージェントタスクが完了すると、`total_tokens` と `duration_ms` を含む通知を受け取ります。このデータを直ちに実行ディレクトリの `timing.json` に保存します。

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

このデータを取得できる機会はこれだけです。タスク通知で届き、他には保存されません。まとめて処理しようとせず、通知を受け取るたびに処理してください。

### 手順4: 採点・集計し、ビューアを起動する

すべての実行が完了したら、次を行います。

1. **各実行を採点する** — `agents/grader.md` を読む採点サブエージェントを起動するか、インラインで採点し、各アサーションを出力に照らして評価します。結果は各実行ディレクトリの `grading.json` に保存します。grading.json の expectations 配列は `text`、`passed`、`evidence` フィールドを使う必要があります（`name`、`met`、`details` などの別名は不可）。ビューアはこれらの正確なフィールド名に依存します。プログラムで確認できるアサーションは目視で判断せず、スクリプトを書いて実行します。スクリプトの方が速く、信頼性が高く、反復間で再利用できます。

2. **ベンチマークへ集計する** — skill-creator ディレクトリから集計スクリプトを実行します。

   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```

   これにより、各構成の pass_rate、時間、トークンと、平均 ± 標準偏差、差分を含む `benchmark.json` と `benchmark.md` が生成されます。benchmark.json を手作業で生成する場合は、ビューアが期待する正確なスキーマを `references/schemas.md` で確認してください。
   各 with_skill バージョンは、対応するベースラインより前に置きます。

3. **分析器による確認を行う** — ベンチマークデータを読み、集計統計が隠す可能性のあるパターンを示します。確認項目は `agents/analyzer.md` の「ベンチマーク結果の分析」節を参照してください。スキルに関係なく常に成功するアサーション（判別力がない）、ばらつきの大きい評価（不安定な可能性がある）、時間とトークンのトレードオフなどです。

4. 定性的な出力と定量データを含めて**ビューアを起動する**:

   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```

   反復2以降では、`--previous-workspace <workspace>/iteration-<N-1>` も渡します。

   **Cowork / ヘッドレス環境:** `webbrowser.open()` が使えない、または環境にディスプレイがない場合は、サーバーを起動せず `--static <output_path>` でスタンドアロンHTMLファイルを書き出します。ユーザーが「すべてのレビューを送信」をクリックすると、フィードバックは `feedback.json` としてダウンロードされます。ダウンロード後、次回の反復で読み取れるように `feedback.json` をワークスペースディレクトリへコピーします。

注: ビューアの作成には generate_review.py を使用してください。独自のHTMLを書く必要はありません。

5. **ユーザーへ伝える**。例: 「結果をブラウザで開きました。タブは2つあり、『出力』では各テストケースを確認してフィードバックを残せます。『ベンチマーク』では定量比較を確認できます。終わったらここに戻ってお知らせください。」

### ユーザーがビューアで確認するもの

「出力」タブでは、一度に1つのテストケースを表示します。

- **プロンプト**: 与えたタスク
- **出力**: スキルが生成したファイル（可能なものはインライン表示）
- **前回の出力**（反復2以降）: 前回の反復の出力を示す折りたたみ節
- **正式な採点**（採点を実行した場合）: アサーションの成功・失敗を示す折りたたみ節
- **フィードバック**: 入力中に自動保存されるテキストボックス
- **前回のフィードバック**（反復2以降）: 前回のコメント。テキストボックスの下に表示

「ベンチマーク」タブでは、構成ごとの成功率、時間、トークン使用量の統計要約と、評価ごとの内訳、分析器の観察を表示します。

前へ・次へボタンまたは矢印キーで移動します。完了したら「すべてのレビューを送信」をクリックし、すべてのフィードバックを `feedback.json` に保存します。

### 手順5: フィードバックを読む

ユーザーから完了の連絡を受けたら、`feedback.json` を読みます。

```json
{
  "reviews": [
    {
      "run_id": "eval-0-with_skill",
      "feedback": "グラフに軸ラベルがない",
      "timestamp": "..."
    },
    { "run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..." },
    {
      "run_id": "eval-2-with_skill",
      "feedback": "完璧です。気に入りました",
      "timestamp": "..."
    }
  ],
  "status": "complete"
}
```

空のフィードバックは、ユーザーが問題ないと考えたことを意味します。ユーザーが具体的な指摘をしたテストケースに改善の焦点を当てます。

使い終わったらビューアサーバーを停止します。

```bash
kill $VIEWER_PID 2>/dev/null
```

### 独立検証と報告

最終候補は、作成担当とは別のサブエージェントに、承認済みの実装内容、変更前後の内容、変更ファイル、成果物、テスト結果を渡して検証させます。要件適合、合意外の追加、出力構造と配置、検証の再現性に加え、変更が必要最小限か、重複が増えていないか、元の目的・主要ワークフロー・互換性を維持しているかを確認させます。スクリプトがある場合は、責務境界、実行コマンド、生成tree、同一入力の再実行結果、スクリプトと生成物の対応、生成物が直接編集されていないこと、実物モックと生成物の分離、プロトタイプと完成版の差分も確認させます。レビュアーは無断で修正せず、問題の証拠と推奨修正を返します。利用できる環境では省略しません。

最終報告には、検証担当、検証対象、各項目の合否、検証方法、発見事項と対応、未解決事項に加え、変更前後の指示量、維持した大筋、変更範囲、破壊的変更が必要だった場合の理由を含めます。スクリプトがある場合は、スクリプトと生成物の対応、各runの出自、直接編集の有無、実物モックとの差分も示します。サブエージェントを利用できない場合は制約と自己検証であることを明示し、独立検証として扱いません。候補版が評価と独立検証を通った後、変更内容を短く再掲して正本への反映承認を得ます。承認後に限り、候補版から承認済みの変更を正本へ反映します。

## スキルの改善

ここが反復の中心です。テストケースを実行し、ユーザーが結果をレビューしたら、そのフィードバックに基づいてスキルを改善します。

### 改善の考え方

1. **フィードバックから一般化する。** ここで起きている大きなことは、多様なプロンプトで何百万回も（文字どおり、あるいはもっと多くかもしれません）使えるスキルを作ろうとしていることです。ここでは、より速く進めるために、あなたとユーザーが少数の例を何度も反復しています。ユーザーはこれらの例を熟知しており、新しい出力をすばやく評価できます。しかし、あなたとユーザーが共同開発しているスキルがその例だけで機能するなら、役に立ちません。細かな過学習の変更や、抑圧的に制約する MUST を加えるのではなく、頑固な問題がある場合は、別の比喩を使ったり、異なる作業パターンを推奨したりして、視野を広げてみてください。試すコストは比較的低く、素晴らしい方法にたどり着くかもしれません。

2. **変更前後を比較し、最小で的確な変更にする。** 修正前（新規作成では初稿）と修正後について、目的達成度、指示量、重複、変更範囲、維持した大筋を比較します。最小差分に固執して欠陥を残さず、正しさが同等なら変更量の少ない案を採用します。最終出力だけでなくトランスクリプトも読み、効果のない指示を削除します。

3. **理由を説明する。** モデルに求めるすべてのことについて、その**理由**を説明するよう最大限努めます。今日のLLMは賢く、心の理論をよく備えています。良い枠組みを与えれば、機械的な指示を超えて、実際に物事を成し遂げられます。ユーザーからのフィードバックが簡潔だったり、苛立ちを含んでいたりしても、タスクと、ユーザーがなぜその内容を書いたのか、実際に何を書いたのかを理解し、その理解を指示に反映してください。大文字の ALWAYS や NEVER を書いている、または非常に硬直した構造を使っていると気付いたら、それは注意信号です。可能であれば、モデルが求めることの重要性を理解できるよう、枠組みを変えて理由を説明してください。その方が、より人間的で、強力かつ効果的なアプローチです。

4. **テストケースをまたぐ繰り返し作業を探す。** テスト実行のトランスクリプトを読み、サブエージェントが全員独立して類似のヘルパースクリプトを書いたり、何かに対して同じ複数手順の方法を取ったりしていないか確認します。3つすべてのテストケースでサブエージェントが `create_docx.py` または `build_chart.py` を書いたなら、そのスクリプトをスキルに同梱すべき強い兆候です。一度だけ書き、`scripts/` に置き、スキルへそれを使うよう指示します。これにより、今後の呼び出しごとに車輪の再発明をせずに済みます。

このタスクは非常に重要です（ここでは年間何十億もの経済価値を生み出そうとしています）。思考時間は障害ではないため、時間をかけてよく考えてください。改訂の草案を書き、新たな目で見直して改善することを提案します。ユーザーの立場に立ち、何を望み、何を必要としているのかを理解するため、真剣に最善を尽くしてください。

### 反復ループ

スキルを改善した後は、次を行います。

1. 改善案と影響するファイルを提示し、合意内容を変える場合は再承認後に適用する
2. ベースライン実行を含むすべてのテストケースを、新しい `iteration-<N+1>/` ディレクトリへ再実行する。新しいスキルを作成している場合、ベースラインは常に `without_skill`（スキルなし）であり、反復間で変わりません。既存スキルを改善している場合は、ユーザーが持ち込んだ元のバージョンと前回の反復のどちらをベースラインにするのが適切か判断します。
3. 前回の反復を指す `--previous-workspace` を指定してレビューワーを起動する
4. ユーザーがレビューし、完了を伝えるまで待つ
5. 新しいフィードバックを読み、再び改善して繰り返す

次のいずれかになるまで続けます。

- ユーザーが満足したと言う
- フィードバックがすべて空である（すべて良好に見える）
- 意味のある進捗が得られなくなる

## 高度: 盲検比較

2つのスキルバージョンをより厳密に比較したい場合（たとえばユーザーが「新しいバージョンは本当に良くなった？」と尋ねた場合）は、盲検比較システムがあります。詳細は `agents/comparator.md` と `agents/analyzer.md` を読んでください。基本的な考え方は、どちらがどちらかを伝えずに2つの出力を独立したエージェントへ渡し、品質を判断させることです。その後、勝者が勝った理由を分析します。

これは任意であり、サブエージェントを必要とします。ほとんどのユーザーには不要です。通常は人間によるレビューの反復で十分です。

## 説明の最適化

SKILL.mdフロントマターの description フィールドは、Claudeがスキルを呼び出すかどうかを決める主要な機構です。スキルを作成または改善した後は、トリガー精度を高めるために説明の最適化を提案します。

### 手順1: トリガー評価クエリを生成する

トリガーすべきものとトリガーすべきでないものを混ぜた、20件の評価クエリを作成します。JSONとして保存します。

```json
[
  { "query": "ユーザーのプロンプト", "should_trigger": true },
  { "query": "別のプロンプト", "should_trigger": false }
]
```

クエリは現実的で、Claude CodeまたはClaude.aiのユーザーが実際に入力しそうなものでなければなりません。抽象的な依頼ではなく、具体的かつ詳細な依頼にします。たとえば、ファイルパス、ユーザーの仕事や状況に関する個人的な文脈、列名と値、会社名、URL、少しの背景情報です。小文字だけのもの、略語・タイプミス・くだけた話し方を含むものもあります。異なる長さを混ぜ、明白なものにするよりエッジケースへ焦点を当ててください（ユーザーはそれらを承認する機会があります）。

悪い例: `"このデータを整形して"`、`"PDFからテキストを抽出して"`、`"グラフを作成して"`

良い例: `"えっと、上司からxlsxファイルが送られてきたんだけど（ダウンロードにあって、名前はたぶん「Q4 sales final FINAL v2.xlsx」みたいな感じ）、利益率をパーセントで表示する列を追加してほしいらしい。売上はC列で、コストはD列だったと思う"`

**トリガーすべき**クエリ（8〜10件）については、網羅性を考えます。同じ意図の異なる表現が必要です。フォーマルなものも、くだけたものも含めます。ユーザーがスキル名やファイル種別を明示していないが、明らかに必要としているケースを含めます。珍しいユースケースや、このスキルが別のスキルと競合するが選ばれるべきケースも加えます。

**トリガーすべきでない**クエリ（8〜10件）では、最も価値があるのはニアミスです。スキルとキーワードや概念を共有しているが、実際には別のものを必要とするクエリです。隣接する領域、単純なキーワード一致ならトリガーするがすべきでない曖昧な表現、スキルが行うことに触れてはいるが別のツールがより適切な文脈のケースを考えてください。

避けるべき重要なことは、トリガーすべきでないクエリを明らかに無関係なものにしないことです。PDFスキルのネガティブテストとして「フィボナッチ関数を書いて」は簡単すぎて、何も検証しません。ネガティブケースは本当に難しいものであるべきです。

### 手順2: ユーザーとレビューする

HTMLテンプレートを使って、評価セットをユーザーに提示しレビューしてもらいます。

1. `assets/eval_review.html` からテンプレートを読む
2. プレースホルダーを置き換える:
   - `__EVAL_DATA_PLACEHOLDER__` → 評価項目のJSON配列（JS変数代入のため、引用符で囲まない）
   - `__SKILL_NAME_PLACEHOLDER__` → スキル名
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → スキルの現在の説明
3. 実装承認前に合意した一時パスへ書き出して開く（例: `/tmp/eval_review_<skill-name>.html`）
4. ユーザーはクエリを編集し、トリガーすべきかを切り替え、項目を追加・削除してから「評価セットをエクスポート」をクリックできる
5. 合意したダウンロード先から評価セットを取得する（例: `~/Downloads/eval_set.json`）

この手順は重要です。悪い評価クエリは悪い説明につながります。

### 手順3: 最適化ループを実行する

ユーザーに伝えます: 「これには少し時間がかかります。最適化ループをバックグラウンドで実行し、定期的に状況を確認します。」

評価セットをワークスペースに保存してから、バックグラウンドで実行します。

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

トリガーテストがユーザーの実際の体験と一致するよう、システムプロンプトのモデルID（現在のセッションを動かしているもの）を使います。

実行中は定期的に出力をtailし、どの反復にいるか、スコアがどのようなものかをユーザーへ更新します。

これは完全な最適化ループを自動処理します。評価セットを学習60%とホールドアウトテスト40%に分け、現在の説明を評価します（信頼できるトリガー率を得るため、各クエリを3回実行します）。次に、失敗した内容に基づく改善案をClaudeへ提案させます。各新しい説明を学習とテストの両方で再評価し、最大5回反復します。完了すると、反復ごとの結果を示すHTMLレポートをブラウザで開き、過学習を避けるため学習スコアではなくテストスコアで選択された `best_description` を含むJSONを返します。

### スキルのトリガーの仕組み

トリガー機構を理解すると、より良い評価クエリを設計できます。スキルは名前と説明とともにClaudeの `available_skills` リストへ現れ、Claudeはその説明に基づいてスキルを参照するかを決めます。重要なのは、Claudeは自力で簡単に処理できないタスクに対してのみスキルを参照することです。たとえば「このPDFを読んで」のような単純な1手順のクエリは、説明が完全に一致していてもトリガーしないことがあります。Claudeが基本ツールで直接処理できるためです。複雑、複数手順、または専門的なクエリは、説明が一致すれば確実にスキルをトリガーします。

つまり、評価クエリはClaudeが実際にスキルを参照する恩恵を受けるほど実質的なものであるべきです。「ファイルXを読んで」のような単純なクエリは不適切なテストケースです。説明の品質にかかわらずスキルをトリガーしません。

### 手順4: 結果を適用する

JSON出力から `best_description` を取り出し、変更前後、スコア、想定されるトリガー範囲の変化をユーザーに示します。承認後にSKILL.mdフロントマターを更新します。

### パッケージ化して提示する（`present_files` ツールが利用可能な場合のみ）

実装承認でパッケージ化も承認され、`present_files` ツールにアクセスできる場合は、スキルをパッケージ化してユーザーに提示します。

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

パッケージ化後、ユーザーがインストールできるよう、生成された `.skill` ファイルのパスを案内します。

## Claude.ai固有の指示

Claude.aiでは中心となるワークフロー（草案 → テスト → レビュー → 改善 → 反復）は同じですが、Claude.aiにはサブエージェントがないため、一部の仕組みが変わります。次のように調整します。

**テストケースの実行**: サブエージェントがないため、並行実行はできません。各テストケースについて、スキルのSKILL.mdを読み、その指示に従ってテストプロンプトを自分で達成します。一度に1件ずつ行います。これは独立したサブエージェントより厳密ではありません（あなたがスキルを書き、同時に実行するため、完全な文脈を持つからです）が、有用な健全性確認であり、人間によるレビュー手順が補います。ベースライン実行はスキップし、スキルを使って依頼されたタスクを完了するだけにします。

**結果のレビュー**: ブラウザを開けない場合（たとえばClaude.aiのVMにディスプレイがない、またはリモートサーバー上にいる場合）は、ブラウザレビューワーを完全にスキップします。代わりに、会話内で直接結果を提示します。各テストケースについて、プロンプトと出力を示します。出力がユーザーが確認する必要のあるファイル（.docxや.xlsxなど）なら、ファイルシステムへ保存し、ダウンロードして検査できる場所を伝えます。「これはどう見えますか。変更したい点はありますか？」とインラインでフィードバックを求めます。

**ベンチマーク**: 定量ベンチマークはスキップします。サブエージェントなしでは意味を持たないベースライン比較に依存するためです。ユーザーからの定性的なフィードバックに焦点を当てます。

**反復ループ**: 以前と同じです。スキルを改善し、テストケースを再実行して、フィードバックを求めます。違いは途中にブラウザレビューワーがないことだけです。ファイルシステムがあれば、結果を反復ディレクトリへ整理できます。

**説明の最適化**: この節にはClaude Codeでのみ利用可能な `claude` CLIツール（具体的には `claude -p`）が必要です。Claude.ai上ではスキップします。

**盲検比較**: サブエージェントが必要です。スキップします。

**パッケージ化**: `package_skill.py` スクリプトは、Pythonとファイルシステムがあればどこでも動作します。Claude.aiでは実行でき、ユーザーは生成された `.skill` ファイルをダウンロードできます。

**既存スキルの更新**: ユーザーは新しいスキルの作成ではなく、既存スキルの更新を求めていることがあります。この場合:

- **元の名前を維持する。** スキルのディレクトリ名と `name` フロントマターフィールドを確認し、変更せずに使います。たとえば、インストール済みスキルが `research-helper` なら、`research-helper-v2` ではなく `research-helper.skill` を出力します。
- **編集前に合意済みの書き込み可能な場所へコピーする。** インストール済みスキルのパスは読み取り専用の可能性があります（例: `/tmp/skill-name/`）。
- **手動でパッケージ化する場合も、合意済みの場所でステージングする。** その後に合意済みの出力先へコピーします。

## Cowork固有の指示

Coworkを利用している場合、主に知っておくべきことは次のとおりです。

- サブエージェントがいるため、主要なワークフロー（テストケースの並行起動、ベースライン実行、採点など）はすべて機能します。（ただし、深刻なタイムアウト問題に遭遇した場合は、テストプロンプトを並行ではなく直列で実行して構いません。）
- ブラウザやディスプレイがないため、評価ビューアを生成する際はサーバーを起動せず、`--static <output_path>` を使ってスタンドアロンHTMLファイルを書き出します。その後、ユーザーがクリックしてブラウザでHTMLを開けるリンクを提示します。
- なぜかCoworkのセットアップでは、テスト実行後にClaudeが評価ビューアを生成しにくいようです。そのため繰り返します。CoworkでもClaude Codeでも、テスト実行後は、スキルを自分で改訂して修正を試みる前に、必ず `generate_review.py`（独自の特製HTMLコードではない）を使って、人間が例を確認できる評価ビューアを生成してください。あらかじめ恐縮ですが、大文字で言います。自分で入力を評価する**前に**評価ビューアを生成してください。できるだけ早く人間へ提示したいからです。
- フィードバックの動作は異なります。実行中のサーバーがないため、ビューアの「すべてのレビューを送信」ボタンは `feedback.json` をファイルとしてダウンロードします。その場所から読み取れます（最初にアクセスを要求する必要がある場合があります）。
- パッケージ化は機能します。`package_skill.py` に必要なのはPythonとファイルシステムだけです。
- 説明の最適化（`run_loop.py` / `run_eval.py`）は、ブラウザではなくサブプロセス経由で `claude -p` を使うため、Coworkでも問題なく動作するはずです。ただし、スキルを完全に作り終え、ユーザーが良い状態だと同意するまで実行しないでください。
- **既存スキルの更新**: ユーザーは新しいスキルの作成ではなく、既存スキルの更新を求めていることがあります。上記のclaude.ai節にある更新の指針に従ってください。

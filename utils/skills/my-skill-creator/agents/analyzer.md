# 事後分析エージェント

盲検比較の結果を分析して勝者が勝った理由を理解し、改善案を作成します。

## 役割

盲検比較器が勝者を決定した後、事後分析器はスキルとトランスクリプトを調べて結果の匿名化を解除します。目的は、勝者を優れたものにした要因と、敗者を改善する方法について、実行可能な洞察を抽出することです。

## 入力

プロンプトで次のパラメーターを受け取ります。

- **winner**: 「A」または「B」（盲検比較から）
- **winner_skill_path**: 勝者の出力を生成したスキルへのパス
- **winner_transcript_path**: 勝者の実行トランスクリプトへのパス
- **loser_skill_path**: 敗者の出力を生成したスキルへのパス
- **loser_transcript_path**: 敗者の実行トランスクリプトへのパス
- **comparison_result_path**: 盲検比較器の出力JSONへのパス
- **output_path**: 分析結果の保存先

## 手順

### 手順1: 比較結果を読む

1. comparison_result_path にある盲検比較器の出力を読む
2. 勝者側（AまたはB）、理由、スコアを記録する
3. 比較器が勝者の出力で評価した点を理解する

### 手順2: 両方のスキルを読む

1. 勝者スキルの SKILL.md と主要な参照ファイルを読む
2. 敗者スキルの SKILL.md と主要な参照ファイルを読む
3. 構造上の違いを特定する:
   - 指示の明瞭さと具体性
   - スクリプト・ツールの使用パターン
   - 例の網羅性
   - エッジケースの扱い

### 手順3: 両方のトランスクリプトを読む

1. 勝者のトランスクリプトを読む
2. 敗者のトランスクリプトを読む
3. 実行パターンを比較する:
   - それぞれがスキルの指示にどの程度従ったか
   - どのツールが異なって使われたか
   - 敗者が最適な振る舞いからどこで外れたか
   - どちらかがエラーに遭遇し、回復を試みたか

### 手順4: 指示への追従を分析する

各トランスクリプトについて、次を評価します。
- エージェントはスキルの明示的な指示に従ったか
- エージェントはスキルが提供するツール・スクリプトを使用したか
- スキルの内容を活用できたのに見逃した機会はあったか
- エージェントはスキルにない不要な手順を追加したか

指示への追従を1〜10で採点し、具体的な問題を記録します。

### 手順5: 勝者の強みを特定する

勝者を優れたものにした要因を特定します。
- より良い振る舞いにつながる、より明瞭な指示か
- より良い出力を生んだ、より優れたスクリプト・ツールか
- エッジケースを導いた、より包括的な例か
- より良いエラー処理の指針か

具体的に記述してください。関連する場合は、スキルやトランスクリプトを引用します。

### 手順6: 敗者の弱みを特定する

敗者の足を引っ張った要因を特定します。
- 最適でない選択につながった曖昧な指示か
- 回避策を強いたツール・スクリプトの欠落か
- エッジケースの網羅における不足か
- 失敗を招いた不十分なエラー処理か

### 手順7: 改善案を作成する

分析に基づき、敗者スキルを改善するための実行可能な提案を作成します。
- 具体的に変更すべき指示
- 追加または変更すべきツール・スクリプト
- 含めるべき例
- 対応すべきエッジケース

影響度で優先順位を付けます。結果を変え得た変更に焦点を当ててください。

### 手順8: 分析結果を書く

構造化した分析を `{output_path}` に保存します。

## 出力形式

次の構造のJSONファイルを書きます。

```json
{
  "comparison_summary": {
    "winner": "A",
    "winner_skill": "path/to/winner/skill",
    "loser_skill": "path/to/loser/skill",
    "comparator_reasoning": "比較器が勝者を選んだ理由の簡潔な要約"
  },
  "winner_strengths": [
    "複数ページの文書を扱うための明瞭な段階的指示",
    "書式エラーを検出した検証スクリプトを同梱している",
    "OCRが失敗した際のフォールバック動作を明示している"
  ],
  "loser_weaknesses": [

```

## ガイドライン

- **具体的にする**: 単に「指示が不明瞭だった」と言わず、関連するスキルとトランスクリプトを引用する
- **実行可能にする**: 提案は曖昧な助言ではなく、具体的な変更にする
- **スキル改善に焦点を当てる**: 目的はエージェントを批評することではなく、敗者スキルを改善することである
- **影響度で優先順位を付ける**: どの変更が最も結果を変えそうか
- **因果関係を考慮する**: スキルの弱みが実際に悪い出力を引き起こしたのか、それとも偶然か
- **客観性を保つ**: 起きたことを分析し、論評しない
- **一般化を考える**: この改善は他の評価にも役立つか

## 提案のカテゴリ

改善案は次のカテゴリで整理します。

| カテゴリ | 説明 |
|----------|------|
| `instructions` | スキルの文章による指示の変更 |
| `tools` | 追加・変更するスクリプト、テンプレート、ユーティリティ |
| `examples` | 含める例の入力・出力 |
| `error_handling` | 失敗の扱いに関する指針 |
| `structure` | スキル内容の再構成 |
| `references` | 追加する外部文書・リソース |

## 優先度

- **high**: この比較の結果を変える可能性が高い
- **medium**: 品質は改善するが、勝敗を変えない可能性がある
- **low**: あるとよいが、改善効果は限定的

# ベンチマーク結果の分析

ベンチマーク結果を分析する際、分析器の目的は複数回の実行にまたがる**パターンと異常**を明らかにすることであり、スキル改善を提案することではありません。

## 役割

すべてのベンチマーク実行結果を確認し、ユーザーがスキルの性能を理解する助けになる自由形式のメモを作成します。集計指標だけでは見えないパターンに焦点を当てます。

## 入力

プロンプトで次のパラメーターを受け取ります。

- **benchmark_data_path**: すべての実行結果を含む、作成途中の benchmark.json へのパス
- **skill_path**: ベンチマーク対象のスキルへのパス
- **output_path**: メモの保存先（文字列のJSON配列として保存）

## 手順

### 手順1: ベンチマークデータを読む

1. すべての実行結果を含む benchmark.json を読む
2. テストした構成（with_skill、without_skill）を記録する
3. すでに算出済みの run_summary 集計値を理解する

### 手順2: アサーションごとのパターンを分析する

全実行にわたる各期待値について、次を確認します。
- 両方の構成で**常に成功**しているか（スキルの価値を区別できない可能性がある）
- 両方の構成で**常に失敗**しているか（壊れている、または能力範囲外の可能性がある）
- **スキルありでは常に成功し、なしでは失敗**しているか（スキルが明確に価値を加えている）
- **スキルありでは常に失敗し、なしでは成功**しているか（スキルが悪影響を及ぼしている可能性がある）
- **大きく変動**しているか（不安定な期待値または非決定的な振る舞い）

### 手順3: 評価をまたぐパターンを分析する

評価全体のパターンを探します。
- 特定の評価タイプは一貫して難しい、または容易か
- 一部の評価は大きなばらつきを示し、他は安定しているか
- 期待と矛盾する意外な結果があるか

### 手順4: 指標のパターンを分析する

time_seconds、tokens、tool_calls を確認します。
- スキルは実行時間を大幅に増加させるか
- リソース使用量に大きなばらつきがあるか
- 集計値を歪める外れ値の実行があるか

### 手順5: メモを作成する

自由形式の観察結果を文字列のリストとして書きます。各メモは、具体的な観察を述べ、推測ではなくデータに基づき、集計指標からは分からないことをユーザーが理解する助けになるものとします。

例:

- 「『出力がPDFファイルである』というアサーションは両構成で100%成功しており、スキルの価値を区別できない可能性がある」
- 「評価3は大きなばらつき（50% ± 40%）を示す。実行2には不安定である可能性がある異例の失敗があった」
- 「スキルなしの実行は、表抽出の期待値を一貫して満たせない（成功率0%）」
- 「スキルは平均実行時間を13秒増やすが、成功率を50%改善する」
- 「スキルありのトークン使用量は主にスクリプト出力の解析により80%高い」
- 「評価1のスキルなしの実行3件は、すべて空の出力を生成した」

### 手順6: メモを書く

メモを文字列のJSON配列として `{output_path}` に保存します。

```json
[
  "『出力がPDFファイルである』というアサーションは両構成で100%成功しており、スキルの価値を区別できない可能性がある",
  "評価3は大きなばらつき（50% ± 40%）を示す。実行2には異例の失敗があった",
  "スキルなしの実行は表抽出の期待値を一貫して満たせない",
  "スキルは平均実行時間を13秒増やすが、成功率を50%改善する"
]
```

## ガイドライン

**行うこと:**

- データから観察したことを報告する
- 対象とする評価、期待値、実行を具体的に示す
- 集計指標が隠すパターンを記録する
- 数値の解釈に役立つ文脈を示す

**行わないこと:**

- スキルの改善を提案する（ベンチマークではなく改善手順で行う）
- 主観的な品質判断をする（「出力が良い・悪い」など）
- 根拠なく原因を推測する
- run_summary の集計値にすでにある情報を繰り返す
